| T-16 | **Send queued admin mail automatically inside the existing web service.** Start one non-overlapping polling loop per web process only when `EMAIL_PROVIDER` is explicitly configured for usable delivery. Reuse durable message claims, leases and nonce fencing across instances/redeploy overlap; a failed or uncertain link is revoked, never reconstructed or replayed. Use a 5-second poll delay, at most 10 processing steps or a 20-second claim budget per batch, and a 30-second shutdown drain before preserving Next's native shutdown. Use a separate bounded database pool and count-only logs; the health endpoint stays independent. No loop starts during builds or with an unset/no-op provider. | The one-station MVP does not need another App Platform component or subscription for this bounded workload. There is no new paid component; the loop shares the existing web service's CPU/memory and uses a small separate database pool. Compared with a dedicated worker component, this couples worker lifetime to web availability but reduces deployment/configuration work. Under healthy database/provider operation and an unsaturated queue, polling starts delivery within 60 seconds; outages and backlog can delay delivery. Existing provider timeout, recipient/privacy guards and production activation gates remain in force. | EM implementation choice explicitly delegated by Earl's 6 Nov 2026 instruction to take [WHR-68](https://linear.app/phaneum/issue/WHR-68) to READY. Refines T-07's adapter boundary and T-15's staging delivery; neither is superseded. No cloud resources or live configuration are changed. |

T-16 replaces the manual worker invocation in the staging runbook with automatic web-process polling. Retention/orphan/backup scheduling remains WO-core-16. The polling lifecycle is reusable for approved production delivery, but this decision does not activate a production provider or settle the remaining authentication/token/consent policies. The shutdown integration must be verified against the pinned Next.js runtime so the framework cannot exit before the mail drain.

| T-17 | **Use the confirmed US data centre for staging transactional email.** Supersedes T-15 because Earl's direct API tests established the account's region and an HTTP 201 acceptance response. The adapter permits only `https://cpaas.zoho.com/v1.1/email` or `https://cpaas.zoho.eu/v1.1/email`, by exact match; staging configuration uses the US URL. Accept only HTTP 200 or 201 with an `EM_104` data-array item. Require the raw send-mail token and reject a `Zoho-enczapikey` prefix at startup with safe `token_has_prefix` diagnostics. Preserve environment-only private configuration, exact recipient allowlisting, staging markings, local Mailpit, disabled tracking, bounded responses/timeouts and single-attempt/no-replay behavior. | An HTTP-only success assumption can falsely fail a delivered single-use link; a mismatched region or prefixed token can produce unhelpful provider failures. Safe reason, status and validated provider error codes make these distinguishable without exposing mail or credentials. The production mail loop intentionally remains off pending WHR-42 and explicit production approval; startup reports this as `email.loop_disabled` / `production` where configuration is otherwise valid. Existing fail-fast production safeguards and Q-535 consent requirements remain. | Earl's explicit 6 Nov 2026 session instruction and direct API findings recorded in [WHR-73](https://linear.app/phaneum/issue/WHR-73). [Zoho send-email API](https://www.zoho.com/cpaas/help/api/email-sending.html) documents the US URL, `EM_104` and `data.error_code`; [data-centre docs](https://www.zoho.com/cpaas/help/api/multiple-data-centers.html) document both permitted regions. HTTP 201 acceptance is Earl's observed evidence, beyond the documentation's HTTP 200 example. |
