# Operational endpoints

Part of WO-core-15 (WHR-28). These endpoints describe deployment readiness; they do not expose product records or establish purchase acceptance.

## GET /api/health

Public, read-only health probe for App Platform. No authentication, request body or query parameters are required. It performs a bounded `SELECT 1` database probe without reading customer or staff data.

| Result                                                              | HTTP | JSON                                                                      |
| ------------------------------------------------------------------- | ---- | ------------------------------------------------------------------------- |
| Database probe succeeds                                             | 200  | `{ "ok": true, "version": "<deployment version>", "db": "ok" }`           |
| Missing database configuration, connection/query failure or timeout | 503  | `{ "ok": false, "version": "<deployment version>", "db": "unavailable" }` |

`version` is `APP_VERSION` when supplied by deployment settings, otherwise the package version. The staging web component binds it to its source commit so Earl can compare the response with GitHub. It is a build identifier, never a credential.

Responses use `Cache-Control: no-store`. Staging responses also carry `X-Robots-Tag: noindex`. Errors never include connection strings, database hosts, exception text or stack traces. A successful probe confirms database connectivity; it does not prove that seed jobs, application workflows or storage uploads succeeded. Check deployment job results separately.

### Configuration status — WO-spec-3f / WHR-100

This amendment extends the probe above. Every response adds `fullyConfigured:boolean`. It is true only when every policy in the closed allowlist below is `configured`, including policies whose domain endpoints are not yet implemented. An unavailable evaluator reports `unconfigured`, never an omitted key or assumed success. `ok`, `db`, `version` and HTTP status retain their existing database-probe meanings. Missing policy alone returns 200 with `fullyConfigured:false`; database failure remains 503 even if all policies are configured. Do not rely on a 503 body surviving the platform edge.

Unauthenticated callers see exactly `{ok,version,db,fullyConfigured}`. They receive no policy names, individual statuses, missing-policy counts or diagnostic reasons. The same projection applies to attendants, restricted first-password/recovery sessions, invalid/expired/revoked sessions and admins without `settings`. This limits disclosure of specific security-policy gaps while keeping the deployment probe public. It supersedes WHR-99's public top-level `cardPrint` exposure: that status moves into the protected `policies` object.

Only a full, live admin session with an enabled account and role, matching current auth version and current `settings` permission receives `{ok,version,db,fullyConfigured,policies}`. Recheck authority for each response; never trust cookie claims or a caller-selected role. If authority cannot be established, return only the public projection. No query/header option, attendant cookie or recovery grant selects the protected projection. Earl can inspect the complete listing while signed into the admin portal with `settings` permission. Missing auth configuration never creates a diagnostics bypass.

## Production monitoring and release readiness — WHR-186 / T-22

This specification adds operational consumers and release gates; it changes no HTTP response field, policy name, permission, status code or domain authority. Implement through the separately approved WHR-29/WHR-31 work orders and the existing WHR-154 startup-diagnostics dependency. The current health implementation is not evidence that the production-only auth/delivery/delegation, phone verification or original-device recovery gates are ready.

**Recommendation and reason:** keep platform liveness and bounded database readiness separate from production release acceptance. The existing 200 response can legitimately contain `fullyConfigured:false`; a missing duplicate window must generate an operational warning rather than remain silently disabled (WHR-152). Do not turn every deferred staging policy into a platform restart loop. In production, any missing required policy blocks pilot launch until the approved implementation and configuration exist. No exception list, fixture or invented environment variable establishes production approval.

Monitoring consumers must obey these rules:

- An external HTTPS probe checks `/api/health` every minute with a ten-second deadline. Two consecutive failures, invalid bodies, wrong expected deployment versions or non-200 responses alert Earl's approved technical contact. Parse only the public `{ok,version,db,fullyConfigured}` projection; never give the uptime provider an admin session. Edge-generated failures may have no JSON body and are still failures.
- `fullyConfigured:false` is a configuration alert even when `ok:true`. At deployment and daily staffed opening, an authorized live settings admin examines all twelve protected keys to identify missing/malformed/inactive policies. Startup diagnostics under WHR-154 may emit only allowlisted policy names and configured/unconfigured state into restricted operational logs. Neither channel exposes policy values or reasons publicly. Every protected read repeats current authority checks; no static diagnostics bypass or shared external-monitor admin credential is permitted.
- Treat timing/reconciliation configuration separately from actual campaign values, phone checks, pending blockers and evidence completeness. `configured` and `fullyConfigured` never prove a giveaway can be finalized, that the independent second person exists, or that any held sale is eligible. P-28/P-30 remain authoritative; the staging inventory's earlier “reconciliation evaluator absent” description is historical, not a new policy decision.
- Lookup-receipt key readiness and retained historical admin/lookup verification keys are additional private deployment checks, with **no new health key**. Storage, inbox delivery, job completion, backup coverage and restore success need separate bounded operational checks. Health never contacts providers/storage, inventories photos, runs jobs, creates approvals or changes a domain record.
- Job telemetry is restricted to type/run reference, UTC times, outcome, aggregate counts, last complete watermark, next due/completion deadline and sanitized codes. Alert on missing heartbeats as well as failed runs. Incomplete backup manifests cannot advance last complete recovery coverage. Protected manifests and drill comparisons stay outside public responses, logs and repository artifacts.
- Monitor 5xx/restarts, database pools/disk/CPU, primary and independent storage growth, pending-upload age, cancellation/review discrepancies, delivery failures, job failures and backup freshness using the initial thresholds in [production.md](../../ops/production.md#4-monitoring-alerts-and-redaction). These thresholds trigger human triage only; they never delete/cancel work, change receipt times, extend deadlines, clear holds or grant credit. Staff inspect phone-only queues on the original phones; server telemetry cannot prove their absence.
- Whales names station primary/backup recipients and response hours privately; Earl is proposed technical primary pending agreement. Test failure/recovery notifications and log-redaction canaries before launch and monthly. No names, addresses, personal records, raw exception/provider bodies, credentials, receipt values, signed URLs, full manifests or measurement notes appear in public evidence or alerts. Approve any new monitoring processor before exporting telemetry.

The production release checklist requires the exact reviewed commit, all twelve required policies approved/installed/configured, independently checked receipt keys, functioning storage/delivery, Owner-entered campaign configuration where needed, completed M4 smoke and client decisions, a verified complete paired backup, a passing database-plus-photo restore drill and tested alert/redaction paths. This is stricter release acceptance without changing HTTP 200/503 semantics. No-deletion defaults under WHR-56 remain in force, including pending/held evidence, versions, sheet assets, independent copies and restore copies. Neither a health flag nor a saved retention duration enables removal.

Implementation acceptance for WHR-29/31 must demonstrate: 200 plus any unconfigured policy alerts; a database/edge outage alerts without JSON; missing heartbeat alerts; partial export/object mismatch never becomes backup success; no diagnostic projection leaks after authority revocation; wrong deployment version alerts; canaries absent from web/job/mail/monitoring logs; and no business mutation from health or operational inventory jobs. This spec claims none of those new runtime checks has been implemented or run.

## Restricted operational signals and deploy check — WHR-211

Both require a full live admin session with current `settings` permission, enabled account and role, and current auth version.
