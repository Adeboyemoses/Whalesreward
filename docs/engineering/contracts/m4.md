## Shared protocol

M1 strict schemas, envelopes, types, UTC instants, cookies, no-store and Origin/CSRF apply. M2 permission dependencies, body/string/page bounds, R/W/E rate profiles and Domain idempotency apply. Every endpoint requires a full live admin session, enabled account/role and all listed permissions. Recovery, first-password and attendant sessions are rejected. Every lookup binds station and the full parent chain; absent or foreign IDs return 404 `not_found`. No client-supplied station, actor, permission, rank, total or approval boolean is authoritative.

Common errors: 400 `invalid_request`; 401 `unauthenticated`; 403 `permission_denied`, `password_change_required`, `origin_rejected`; 404 `not_found` for resource calls; 413 `request_too_large`; 429 `rate_limited`; 503 `temporarily_unavailable`. Domain calls add 409 `operation_conflict`, `version_conflict`. All requests reject unknown fields. Only transient 429/503 failures are retryable; policy-unconfigured 409 codes and `export_failed` are not. Read calls have no operation key or mutation; POST reads still check Origin. All domain writes atomically recheck current authority under M2’s security lock, write audit and preserve an immutable same-key result.

Domain replay authenticates and checks the canonical request digest before returning the original historical result, prior to testing now-stale versions, expiry or readiness. It never performs the effect again. New attempts check every current precondition. A lost response retries the same operation; a stale review requires fetching and explicitly reviewing a new proposal, never substituting versions blindly. `reason` is trimmed 1..1000 characters with M3’s no-secret/no-phone validation. Success receipts contain no paths, credentials or download URLs.

`Read / R` means a consistent database snapshot for that response. Pagination uses M2’s limits and scoped opaque cursors. Live leaderboard/report cursors also bind the exact data generation; a changed generation returns 409 `read_view_stale`, requiring a refresh. Frozen snapshot/preview/export cursors bind their immutable parent ID. Pages never rank only their visible subset. Lists with ties use a stable ID solely for display/pagination, never within the spend-only rank expression.

Money sums remain exact kobo, up to NUMERIC(30,0); quantities use NUMERIC(30,6). Counts/ranks are decimal strings, positive for ranks. Currency groups are separate and never converted or added across currencies. MVP ranking requires the configured single currency; reject mixed data with 409 `currency_mismatch`. Reports can return multiple currency groups. UI renders money to two decimals and units explicitly; no double rounding or historical repricing. Bound overflows fail with 422 `aggregate_overflow`, never clipping a total. These errors apply to every aggregate-producing endpoint below.

## Leaderboards — E01; I-14/I-40/I-42–I-45a

| Method and path | Request | Success | Required permission | Idempotency / concurrency | Additional errors |
|---|---|---|---|---|---|
| GET `/api/admin/giveaway/campaign` | None | 200 `{campaign:Campaign|null}` | leaderboards | Read / R | None |
| GET `/api/admin/leaderboards` | `{basis:'campaign_qualifying'\|'recorded_all_time',campaignId?:Id,category?:Category,cursor?,limit?}` | 200 RankingPage | leaderboards | Read / R; data-generation cursor | 409 `read_view_stale`,`currency_mismatch`; 422 `aggregate_overflow` |

Campaign basis requires campaignId; recorded_all_time forbids it. Unset campaign bounds or timing policy return state=unconfigured, no rows, customers='0' and summary=null, with explicit null timing fields. Never label operational spend or demo fixtures as qualifying spend. An all-time view is separately labelled recorded_all_time and cannot be finalized. A configured live campaign is provisional even when a historical final snapshot exists; that snapshot has its own endpoint and label.

Contribute once per purchase from its current accepted revision, only with completed validation, resolved identity, validated evidence and no cancellation, open hold or original-validation block. Proposed late corrections leave that revision effective; suspected duplicates remain included until cancelled. Campaign membership additionally satisfies approved launch/period and upload rules. Product or container never changes the customer’s fixed category. Include only customers with at least one contributing purchase; empty categories return an empty page and exact zero totals.

Rank by exact summed spend descending, overall or recomputed within the selected category. Equal spend always shares rank; transaction count, quantities, purchase days, timestamps and IDs never break the tie. `competition_v1` means 1,1,3; its numbering remains a centrally isolated proposal, not a new prize policy. `sharedRank` is computed over the full selected ranking, including ties crossing pages. Summary covers the whole selected category, not the visible page. Quantities are supplementary and unit-separated. No minimum spend threshold or one-purchase-per-day rule exists.

“View purchases” requires sales permission and opens M3 sales search with exact customerId; it includes all that customer’s records, not just contributing campaign rows. Preserve the chosen leaderboard category on return. Leaderboards permission allows the narrow ranking identity projection, never phone numbers, photos or full sale details. Current cardCode is a display locator only; identity and fixed category remain customer-based across replacement.

**Amended by WO-spec-4a: accepted contributions and campaign membership.** P-20 now uses P-23's closed interval I=[L,U], U=min(R, original offlineExpiresAt). S is the original capturing sign-in; R is first durable details receipt. A verified, bound server-HMAC lookup/registration receipt at T gives L=max(S,T); otherwise L=S. Invalid or mismatched receipts fall back without rejection; cached receipts retain their original T. The signed card link must still be in force at R. Neither lookup T nor U replaces R for deadlines. Late receipt after expiry alone creates no capture hold.

Use the shared M1/M3 evaluator and immutable original context. Phone clocks, UUID time, photo metadata, reauthentication and recovery supply no stronger capture proof. Uniform outside-period membership excludes campaign spend without cancelling an otherwise valid sale. A crossing, invalid interval, missing history or missing configuration stays unresolved. Existing capture blocks require the authorized M3 decision; recomputing a predicate never clears them. Q-528 remains pending.

For P-25-reviewed sales, consume the typed `campaign_membership_uniform` conclusion from protected `review_evaluation` provenance, bound to the same sale, committed decision and campaign/configuration identity. Preserve its inside/outside answer and interval precision. An immutable original `sync_validation.campaign_eligible=false` for a held original cannot veto a later valid inside conclusion or be rewritten to true. A successful decision, `credited=true`, a public audit tag or a cleared hold alone is never campaign-membership proof. See [operational provenance](../../ops/review-evidence.md).

When no membership conclusion was needed, retain the ordinary shared capture evaluation against the applicable campaign settings. A conclusion for another campaign or superseded settings cannot be reused: reevaluate from retained trusted facts against the current version, without automatically clearing existing blocks. Missing, contradictory or unbound proof yields timing_unresolved and blocks relevant finalization. In every case independently enforce launch/period, first-details receipt, complete-photo deadline, current accepted revision, evidence, cancellation, holds and eligibility. All-time operational spend remains separate from campaign membership.

P-26 preserves original basis, entered value, captured rate/version/precision and attribution while storing independently verified effective numbers. Later card/date/capture resolutions must retain those numbers and calculation lineage. A successful meter decision may remain uncredited. Aggregation never re-executes meter tolerance or interprets a meter conclusion as time evidence. Snapshot source revision IDs resolve immutable calculation/provenance internally; public source rows expose only their existing narrow projection. Changed accepted revision IDs require result reconciliation even when totals match.

Every relevant committed receipt, decision, candidate/accepted revision, cancellation, flag or settings change participates in the reporting-state/campaign lock and generation protocol below. Preserve decision/provenance bindings in frozen source lineage internally; never serialize raw evaluation graphs, lookup receipts or meter transcriptions into rankings, report exports or general audit. A cleared flag or rejected proposal can reconcile unchanged; an accepted lineage change cannot silently rewrite a predecessor snapshot.

P-28 fixes launch/start inclusive and cutoff inclusive: a trusted purchase instant must be >=launchAt, >=purchaseStart and <=purchaseCutoff. Both first durable details receipt and approved complete-photo receipt must be <=uploadDeadline; finalization requires trusted now>uploadDeadline. Show exact instants in review; no implicit end-of-minute expansion. Bounded capture intervals use these same inclusive predicates throughout the shared evaluator. M1’s first durable details receipt R remains unchanged and decides its upload-deadline check. Complete-photo deadline evidence additionally needs the approved WHR-54 rule and immutable server-observed receipt facts; PUT acknowledgement, client timestamp or later validation time alone cannot establish timely arrival. Unknown proof stays unresolved. Post-deadline originals remain durable and cannot gain campaign qualification through finalization or a revision.

Readiness uses trusted server time, configured launch/period/deadline, approved policies and current review state. Now must be strictly later than both cutoff and upload deadline, including zero grace. Counts are distinct records per kind and may overlap. Relevant unresolved holds, pending corrections, duplicate decisions, uploads, eligibility blocks or reconciliation work prevent confirmation. A duplicate flag still contributes to live rankings while its unresolved review blocks finalization. Unknown campaign relevance is treated as relevant until proven otherwise. No endpoint knows about unsent phone-only records; an approved reconciliation checklist must address that limitation.

The source universe is every server-known station purchase at the review snapshot, plus every predecessor source; excluded rows retain all applicable reasons. Inclusion requires a current accepted revision. Pending/cancelled/held rows cannot vanish merely because they do not contribute. Excluded monetary summaries use the accepted revision when present, otherwise immutable original, labelled as excluded record values. Reason totals may overlap and are not additive. Campaign-specific unresolved work blocks; proven unrelated records remain excluded without blocking. Missing policy cannot be treated as a passed check.

`reconciliation_required` is a dirty marker, not an unsatisfiable revision prohibition. Prepare reruns the approved checklist against current sources under the campaign lock. If all non-reconciliation checks pass, it records an immutable reconciliation result for the current data/settings/policy versions, clears the dirty marker and saves a preview, returning the new campaign guard. No checkbox or reason alone clears it. Before preparation, canPrepare can be true while canConfirm=false solely because reconciliation_required is set. With policy unset, both are false; no successful preparation exists.

Revision preparation with no effective result change returns ReconciledUnchanged: record the successful checklist, clear dirty state, advance campaign version and write audit/receipt, without creating a preview or snapshot. Compare accepted revision IDs, inclusion/eligibility reasons and exact contributions against the latest snapshot; proposal/review bookkeeping alone is not a result change. This covers rejected corrections and cleared duplicate flags. Existing snapshot content stays untouched. Current reconciliation state is separate from its historical sourceDataVersion. Same-key replay returns the original reconciliation receipt; later mutations can dirty the campaign again.

Readiness canConfirm additionally requires an unexpired, unconsumed preview owned by the caller and matching the current guard. Reconciliation-only success leaves canConfirm=false when no such preview exists. A changed accepted revision ID can require a new snapshot even if its amount is identical; finalization preserves source lineage as well as totals. Initial empty results may be reviewed explicitly; no minimum customer count is invented.

Preview materializes exact source facts, customer display snapshots, overall/category ranks, exclusions and predecessor differences. It saves no final result and changes no purchase. Lifetime is a proposed 15 minutes, checked at confirmation; Keep reviewing/Cancel makes no mutation. Initial requires no predecessor; a revision preview requires the latest snapshot and an accepted source/eligibility change. Preview binds its creator, kind, reason, content digest and resulting guard. A different actor cannot consume it. GET can display expired history, but the UI must obtain a fresh preview to confirm.

Serialize all relevant writers using security lock, station reporting-state row, affected campaigns in ID order, then existing domain locks in their prescribed order. Original durable receipt, evidence-state changes, holds, proposals, accepted revisions, cancellations, duplicate decisions, customer/card display changes and timing/policy changes increment station dataVersion in the same transaction. Such writes dirty affected campaigns and increment campaign.version. Unknown relevance dirties conservatively. This extends M3’s lock boundary; a purchase-only lock is insufficient to prevent phantom inserts or stale snapshot confirmation.

Final confirmation locks the same boundary, rechecks live action permission, exact guard, policy versions, preview ownership/kind/digest/expiry and all readiness checks. It verifies reconciledDataVersion equals current dataVersion and dirty=false, then copies the reviewed immutable content, creates number N+1, consumes the preview, updates latestSnapshotId/version and commits audit+receipt atomically. Any relevant change since review rejects the entire operation. Two distinct confirmations cannot create parallel successors. No long-held transaction spans the user’s review; no background job finalizes. Same-key success replay returns its saved snapshot even if later changes require reconciliation.

Saved results never join mutable customer names/cards, prices, current totals or current revision pointers for historical display. Preserve settings, policy/tie versions, actor/time/reason, source IDs and exact facts, ranks and both sides of changes. Later accepted changes update live totals and dirty the campaign; only giveawayRevise can save the next reviewed snapshot linked to the latest predecessor. Normal M3 corrections/holds still apply. Revision grants no deadline waiver, automatic editing window or credit. No deletion, overwrite, snapshot export, prize allocation or fulfilment endpoint is introduced here.

Both dates are required, inclusive Lagos calendar days; convert to `[start(from),start(dayAfter(to)))`, rejecting nonexistent/reversed dates. Proposed range ceiling is 366 days; exports at most 100,000 source rows. Limits are centralized engineering bounds, not truncation permissions. Product null means all products. Queries, summaries, daily chart, group pages, source pages and exports use exactly the same filters and inclusion predicate. Changing filters invalidates prior results/cursors; never display stale totals after a validation failure. Empty results return zeros, empty groups and daily series.

Operational inclusion uses the same completed accepted contribution as all-time customer totals, independent of campaign cutoff/grace. Use the accepted revision’s verified sale date if present, otherwise the original app-reported calendar date, explicitly labelled reported. This display grouping is not trusted capture proof and cannot confer eligibility. Pending corrections leave the prior accepted values/date; accepted date corrections move the operational day without changing original timestamps. No receipt-time substitution. Reporting records at the original attendant/pump IDs prevents current reassignment from moving sales between groups.

Each report source belongs to exactly one included/excluded bucket: cancelled first, then held/policy-blocked, then incomplete received/photo_pending/finalizing, then remaining ineligible. Excluded sums use accepted values when present, otherwise original values, and never enter completed totals. Pending means server-visible only. Duplicates and late proposals can be included with flags. Source output is a narrow report projection with no customer identity, phone, photo URL, evidence notes or recovery actors; reports permission grants this projection, not M3 sales/photo access.

Group by product, originating attendant or originating pump; identity labels come from captured attribution, using the latest captured label deterministically if one stable ID has several historical labels. Source rows retain each captured label. Sort groups by exact spend descending for the configured currency, then stable key; multi-currency output uses stable key order instead of incomparable sums. Daily series is day ascending and contains days with included purchases; an omitted bar does not establish zero station sales. Sum liquids in litres and gas in kilograms, with product breakdown retained.

Export confirmation captures immutable filters, totals, daily/groups and every source row in one database snapshot after comparing expectedDataVersion. Later corrections cannot change the artifact. Domain replay returns the same export; a new operation captures a new view. Rendering is leased, bounded, restartable and fenced, reading only stored rows. Recheck the creator’s current account and reports+reportExport permission before processing/publishing. Revocation prevents new preparation and downloads; preparation never changes sale status. Errors remain visible through the status route and do not publish partial files.

### Owner setup and lock — P-28

Settings initially has logical version 1, no saved settingsVersionId and campaign=null; earlier retention intent may already have advanced that version. No read/review creates a campaign or settings row. `kind=create` requires campaignId=null and expectedCampaignVersion=null. Confirm allocates the campaign ID, uses initial campaign version 1, and returns it in SettingsChange. The campaign name is a server-derived display label from the station name, not a sixth editable input or a uniqueness key. Exactly one campaign per station is supported; no replacement, deletion, second campaign or rollover route is added.

`kind=update` requires the current same-station campaign ID and its positive expectedCampaignVersion. A mismatched kind/ID/guard shape is 400 invalid_request; unknown/foreign update IDs are 404 not_found. A new create attempt when the station already has a campaign returns 409 campaign_exists (including two different create operations racing), even if the old station version also changed. Existing-campaign stale guards return version_conflict. The historical successful-create replay is the exception below. Update with identical timing inputs returns no_change; a new reason alone is not a change. Do not accept client actor, station, campaign name, policy version, uploadDeadline or approval fields.

Both POST routes check settings permission and the live protected Owner identity (`RoleSummary.isOwner` backed by the current server role, never its display name or equivalent grants). A non-Owner with settings returns 403 owner_required, even with every action grant; a caller without settings gets permission_denied. This authority is nondelegable through settings grants and distinct from giveawayFinalize/giveawayRevise. Read/history permissions and retention authorization are unchanged. Apply live Owner checks under the security lock on confirm and replay; demotion/disable or session revocation after review cannot use a digest or receipt to regain access.

All five fields are required together, nonnull: launchAt <= purchaseStart < purchaseCutoff, explicit supported IANA timezone, whole graceHours >=0 (zero valid). Instants are exact UTC values under M1; timezone is the explicit campaign display/input calendar, not a replacement for immutable UTC facts or the Africa/Lagos correction calendar. Do not change station.timezone or prior sale dates by saving it. Convert local form input explicitly; ambiguous/nonexistent local times require disambiguation/correction before review. Derive uploadDeadline as cutoff + graceHours×3600 elapsed seconds, independent of calendar/DST changes. Reject unsafe/non-integer grace, unsupported timezone, ordering or representability/overflow with 422 timing_invalid. Do not silently round, expand cutoff to minute end, or seed example dates/durations. Missing/malformed fields are 400 invalid_request. `launch_start_unset` is no longer a giveaway-settings error because launch/start are required inputs.

For every new review/confirm, trusted database time must be strictly before the proposed purchaseStart. Updates must ALSO be strictly before the persisted current purchaseStart and have no saved snapshot of any number; creation must have no existing campaign. The current-start check runs before considering a replacement start: moving start into the future cannot unlock an already started campaign. Equality at either start returns 409 timing_locked. Any saved snapshot locks even if a pointer is absent/inconsistent or its dates are future. Check snapshot existence, not just latestSnapshotId. There is no in-progress amendment or administrative override. Launch alone does not lock timing when launch<start.

An existing explicitly unconfigured campaign with purchaseStart=null may receive its first complete setup using kind=update, provided no saved snapshot exists and the proposed start is future. A missing/corrupt pointer or unreadable historical start is not proof of unconfigured state: fail closed rather than treating it as null. Keep old incomplete versions unchanged. `Settings.timingLocked` reflects the persisted start/snapshot rule at the response's trusted time (false when no campaign or explicitly unset start and no snapshot); it is display information, never confirmation authority. Before a proposed start that has elapsed, the Owner must edit and review future values afresh.

### Policy, review, commit and replay
