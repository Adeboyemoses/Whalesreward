## Shared protocol

M1 strict schemas, envelopes, types, UTC instants, cookies, no-store and Origin/CSRF apply. M2 permission dependencies, body/string/page bounds, R/W/E rate profiles and Domain idempotency apply. Every endpoint requires a full live admin session, enabled account/role and all listed permissions. Recovery, first-password and attendant sessions are rejected. Every lookup binds station and the full parent chain; absent or foreign IDs return 404 `not_found`. No client-supplied station, actor, permission, rank, total or approval boolean is authoritative.

Common errors: 400 `invalid_request`; 401 `unauthenticated`; 403 `permission_denied`, `password_change_required`, `origin_rejected`; 404 `not_found` for resource calls; 413 `request_too_large`; 429 `rate_limited`; 503 `temporarily_unavailable`. Domain calls add 409 `operation_conflict`, `version_conflict`. All requests reject unknown fields. Only transient 429/503 failures are retryable; policy-unconfigured 503 codes are not. Read calls have no operation key or mutation; POST reads still check Origin. All domain writes atomically recheck current authority under M2’s security lock, write audit and preserve an immutable same-key result.

Domain replay authenticates and checks the canonical request digest before returning the original historical result, prior to testing now-stale versions, expiry or readiness. It never performs the effect again. New attempts check every current precondition. A lost response retries the same operation; a stale review requires fetching and explicitly reviewing a new proposal, never substituting versions blindly. `reason` is trimmed 1..1000 characters with M3’s no-secret/no-phone validation. Success receipts contain no paths, credentials or download URLs.

`Read / R` means a consistent database snapshot for that response. Pagination uses M2’s limits and scoped opaque cursors. Live leaderboard/report cursors also bind the exact data generation; a changed generation returns 409 `read_view_stale`, requiring a refresh. Frozen snapshot/preview/export cursors bind their immutable parent ID. Pages never rank only their visible subset. Lists with ties use a stable ID solely for display/pagination, never within the spend-only rank expression.

Money sums remain exact kobo, up to NUMERIC(30,0); quantities use NUMERIC(30,6). Counts/ranks are decimal strings, positive for ranks. Currency groups are separate and never converted or added across currencies. MVP ranking requires the configured single currency; reject mixed data with 409 `currency_mismatch`. Reports can return multiple currency groups. UI renders money to two decimals and units explicitly; no double rounding or historical repricing. Bound overflows fail with 422 `aggregate_overflow`, never clipping a total. These errors apply to every aggregate-producing endpoint below.

Campaign basis requires campaignId; recorded_all_time forbids it. Unset campaign bounds or timing policy return state=unconfigured, no rows, customers='0' and summary=null, with explicit null timing fields. Never label operational spend or demo fixtures as qualifying spend. An all-time view is separately labelled recorded_all_time and cannot be finalized. A configured live campaign is provisional even when a historical final snapshot exists; that snapshot has its own endpoint and label.

Contribute once per purchase from its current accepted revision, only with completed validation, resolved identity, validated evidence and no cancellation, open hold or original-validation block. Proposed late corrections leave that revision effective; suspected duplicates remain included until cancelled. Campaign membership additionally satisfies approved launch/period and upload rules. Product or container never changes the customer’s fixed category. Include only customers with at least one contributing purchase; empty categories return an empty page and exact zero totals.

Rank by exact summed spend descending, overall or recomputed within the selected category. Equal spend always shares rank; transaction count, quantities, purchase days, timestamps and IDs never break the tie. `competition_v1` means 1,1,3; its numbering remains a centrally isolated proposal, not a new prize policy. `sharedRank` is computed over the full selected ranking, including ties crossing pages. Summary covers the whole selected category, not the visible page. Quantities are supplementary and unit-separated. No minimum spend threshold or one-purchase-per-day rule exists.

“View purchases” requires sales permission and opens M3 sales search with exact customerId; it includes all that customer’s records, not just contributing campaign rows. Preserve the chosen leaderboard category on return. Leaderboards permission allows the narrow ranking identity projection, never phone numbers, photos or full sale details. Current cardCode is a display locator only; identity and fixed category remain customer-based across replacement.

Purchase-period membership uses P-18’s immutable [capturing sign-in, first durable details receipt] interval and approved evidence-supported review, not phone/UUID/photo metadata. Every possible capture instant must give the same answer; a crossing stays unresolved at zero credit. A verified date can establish membership only when every possible time that day gives the same answer. A constant answer outside the period is excluded. Keep this in the shared capture-policy module; do not duplicate weaker M4 logic. Q-528 still awaits client confirmation.

Timing policy must explicitly define launch/start/cutoff boundary comparisons. The recommended configuration is launch/start inclusive, cutoff inclusive, with exact instants shown in review; no implicit end-of-minute expansion. M1’s first durable details receipt R remains unchanged and decides its upload-deadline check. Complete-photo deadline evidence additionally needs the approved WHR-54 rule and immutable server-observed receipt facts; PUT acknowledgement, client timestamp or later validation time alone cannot establish timely arrival. Unknown proof stays unresolved. Post-deadline originals remain durable and cannot gain campaign qualification through finalization or a revision.

Readiness uses trusted server time, configured launch/period/deadline, approved policies and current review state. Now must be strictly later than both cutoff and upload deadline, including zero grace. Counts are distinct records per kind and may overlap. Relevant unresolved holds, pending corrections, duplicate decisions, uploads, eligibility blocks or reconciliation work prevent confirmation. A duplicate flag still contributes to live rankings while its unresolved review blocks finalization. Unknown campaign relevance is treated as relevant until proven otherwise. No endpoint knows about unsent phone-only records; an approved reconciliation checklist must address that limitation.

The source universe is every server-known station purchase at the review snapshot, plus every predecessor source; excluded rows retain all applicable reasons. Inclusion requires a current accepted revision. Pending/cancelled/held rows cannot vanish merely because they do not contribute. Excluded monetary summaries use the accepted revision when present, otherwise immutable original, labelled as excluded record values. Reason totals may overlap and are not additive. Campaign-specific unresolved work blocks; proven unrelated records remain excluded without blocking. Missing policy cannot be treated as a passed check.

`reconciliation_required` is a dirty marker, not an unsatisfiable revision prohibition. Prepare reruns the approved checklist against current sources under the campaign lock. If all non-reconciliation checks pass, it records an immutable reconciliation result for the current data/settings/policy versions, clears the dirty marker and saves a preview, returning the new campaign guard. No checkbox or reason alone clears it. Before preparation, canPrepare can be true while canConfirm=false solely because reconciliation_required is set. With policy unset, both are false; no successful preparation exists.

Preview materializes exact source facts, customer display snapshots, overall/category ranks, exclusions and predecessor differences. It saves no final result and changes no purchase. Lifetime is a proposed 15 minutes, checked at confirmation; Keep reviewing/Cancel makes no mutation. Initial requires no predecessor; revision requires the latest snapshot and at least one accepted source/eligibility change. Preview binds its creator, kind, reason, content digest and resulting guard. A different actor cannot consume it. GET can display expired history, but the UI must obtain a fresh preview to confirm.

Serialize all relevant writers using security lock, station reporting-state row, affected campaigns in ID order, then existing domain locks in their prescribed order. Original durable receipt, evidence-state changes, holds, proposals, accepted revisions, cancellations, duplicate decisions, customer/card display changes and timing/policy changes increment station dataVersion in the same transaction. Such writes dirty affected campaigns and increment campaign.version. Unknown relevance dirties conservatively. This extends M3’s lock boundary; a purchase-only lock is insufficient to prevent phantom inserts or stale snapshot confirmation.

Final confirmation locks the same boundary, rechecks live action permission, exact guard, policy versions, preview ownership/kind/digest/expiry and all readiness checks. It verifies reconciledDataVersion equals current dataVersion and dirty=false, then copies the reviewed immutable content, creates number N+1, consumes the preview, updates latestSnapshotId/version and commits audit+receipt atomically. Any relevant change since review rejects the entire operation. Two distinct confirmations cannot create parallel successors. No long-held transaction spans the user’s review; no background job finalizes. Same-key success replay returns its saved snapshot even if later changes require reconciliation.

Saved results never join mutable customer names/cards, prices, current totals or current revision pointers for historical display. Preserve settings, policy/tie versions, actor/time/reason, source IDs and exact facts, ranks and both sides of changes. Later accepted changes update live totals and dirty the campaign; only giveawayRevise can save the next reviewed snapshot linked to the latest predecessor. Normal M3 corrections/holds still apply. Revision grants no deadline waiver, automatic editing window or credit. No deletion, overwrite, snapshot export, prize allocation or fulfilment endpoint is introduced here.

Both dates are required, inclusive Lagos calendar days; convert to `[start(from),start(dayAfter(to)))`, rejecting nonexistent/reversed dates. Proposed range ceiling is 366 days; exports at most 100,000 source rows. Limits are centralized engineering bounds, not truncation permissions. Product null means all products. Queries, summaries, daily chart, group pages, source pages and exports use exactly the same filters and inclusion predicate. Changing filters invalidates prior results/cursors; never display stale totals after a validation failure. Empty results return zeros, empty groups and daily series.

Operational inclusion uses the same completed accepted contribution as all-time customer totals, independent of campaign cutoff/grace. Use the accepted revision’s verified sale date if present, otherwise the original app-reported calendar date, explicitly labelled reported. This display grouping is not trusted capture proof and cannot confer eligibility. Pending corrections leave the prior accepted values/date; accepted date corrections move the operational day without changing original timestamps. No receipt-time substitution. Reporting records at the original attendant/pump IDs prevents current reassignment from moving sales between groups.

Each report source belongs to exactly one included/excluded bucket: cancelled first, then held/policy-blocked, then incomplete received/photo_pending/finalizing, then remaining ineligible. Excluded sums use accepted values when present, otherwise original values, and never enter completed totals. Pending means server-visible only. Duplicates and late proposals can be included with flags. Source output is a narrow report projection with no customer identity, phone, photo URL, evidence notes or recovery actors; reports permission grants this projection, not M3 sales/photo access.

Group by product, originating attendant or originating pump; identity labels come from captured attribution, using the latest captured label deterministically if one stable ID has several historical labels. Source rows retain each captured label. Sort groups by exact spend descending for the configured currency, then stable key; multi-currency output uses stable key order instead of incomparable sums. Daily series is day ascending and contains days with included purchases; an omitted bar does not establish zero station sales. Sum liquids in litres and gas in kilograms, with product breakdown retained.

Export confirmation captures immutable filters, totals, daily/groups and every source row in one database snapshot after comparing expectedDataVersion. Later corrections cannot change the artifact. Domain replay returns the same export; a new operation captures a new view. Rendering is leased, bounded, restartable and fenced, reading only stored rows. Recheck the creator’s current account and reports+reportExport permission before processing/publishing. Revocation prevents new preparation and downloads; preparation never changes sale status. Errors remain visible through the status route and do not publish partial files.

PDF includes filter/time/basis metadata, totals, excluded buckets and full grouped figures with page numbers. XLSX contains Report and Source sales sheets, including excluded rows and an explicit Included in totals column. IDs/text are text cells and formula-injection-safe; no executable formulas from data. Numeric cells are written from exact decimal strings only when round-tripping preserves all displayed digits. If any value exceeds Excel’s safe decimal precision, fail XLSX with precision_not_representable and offer PDF; never silently round money or quantities. Summaries come from server exact arithmetic, not spreadsheet recalculation.

Export bytes use private random server-only paths, checksum verification, no public or signed bearer URL. Same-origin download checks creator/station/export binding and current permission, then streams with no-store, safe filename and attachment disposition. Proposed artifact lifetime is 24 hours from preparation; expiry is enforced before streaming even if cleanup has not run. Failed jobs can retry the same frozen source; expired files require a new export. Keep metadata/audit after disposable bytes expire. This artifact lifecycle does not authorize evidence-photo deletion.

Policy configuration must explicitly approve any supported case, and saved snapshot timing is always immutable. Confirm reruns policy/time checks even if review previously succeeded. A changed timing version invalidates affected eligibility evaluations and previews, dirties reconciliation and advances campaign/data versions; no read or mutation can reuse stale campaign eligibility. Operational accepted amounts, original capture facts and saved snapshots are never repriced or overwritten.

Review is a side-effect-free canonical comparison of old and proposed values, reason, actor, expected versions and policy versions. after shows proposed values with current version fields; it is not a saved Settings object. reviewDigest hashes this canonical comparison, excluding asOf; it is not authority. Confirm recomputes it under locks and rechecks current policy, versions and permission. Keep editing/Cancel writes nothing. One successful confirmation inserts a full immutable settings version, typed change history, audit and receipt, then advances the station pointer. Unchanged sections are copied exactly; concurrent section edits conflict rather than overwriting each other.

Retention days is a positive whole integer or null, with a proposed engineering ceiling of 36,500 days. Saving it records intent only. Every M4 response has deletionEnabled=false, and no enable/delete route exists. Never copy an old approval onto a newly saved period. D07 must settle stored originals, start point, exemptions, backups/noncurrent copies and audit before a separate approved removal work order. Unset policy reports storedCopyPolicy=unconfigured; the board’s “Original + compressed” label is not authority. Pending evidence, active holds, snapshots, source lineage and audit remain preserved.

## Audit additions and decision gates

M4 extends M3’s closed audit catalogue: giveaway_review_prepared, giveaway_finalized and giveaway_revised use area=giveaway and target kind=campaign; report_export_requested/prepared/failed use area=reports and target kind=report_export; giveaway_timing_changed and retention_intent_changed use area=settings and target kind=settings (the immutable settings version ID). Record typed version/ID/bound/total changes, actor-at-event, reason and server time. Worker events identify the export service and creator separately. No arbitrary source arrays, customer names, phones, private notes, URLs or secrets enter audit fields. Global audit reads still require audit; section-specific receipts/history use their own permissions.

The following gates are safe specification defaults as of 4 November 2026. They preserve data and block unsupported high-risk actions; they do not approve a client policy or authorize implementation outside its work order.
