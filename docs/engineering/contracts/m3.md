WO-spec-3 / WHR-46. Normative input for WO-core-8/9/10/11 and WO-app-7/8/9/10. This is a contract and storage specification, not implemented endpoints or security controls. Read with [M1](m1.md), [M2](m2.md), the [data model](../data-model.md) and [invariants](../invariants.md).

## Shared protocol and transaction rules

**Amended by WO-spec-3f / WHR-100, 11 Nov 2026.** M2’s [domain status inventory](m2.md#domain-status-inventory--wo-spec-3f--whr-100) applies here: policy-unconfigured failures return 409 with `retryable:false`; transient delivery/storage failures remain 503. Preserve the same codes, M1 error envelope and fail-closed gates. Recovery cannot unlock a queue and a failed review cannot clear a hold or alter contribution merely because its status changed. The [health policy flags](operations.md#get-apihealth) neither grant authority nor settle missing policy.

M1 strict JSON/types/envelopes, exact decimal strings, UTC instants, no-store, Origin/CSRF, secure host-only cookies and M2 bounds/rate/pagination/permission rules apply. `Id`, `Version`, `Entry`, `PriceSnapshot`, `Medium`, `Category`, `Currency`, `Kobo`, `Quantity`, `Digest`, `SaleStatus`, `Actor`, `Count`, `TotalKobo` and `Page<T>` retain their prior meanings. Every protected object lookup is station-scoped, plus originating-account scoped for attendant routes. Absent or foreign IDs return 404 `not_found`, without ownership disclosure. The M1 sync routes retain their existing `sale_not_found` error.

Admin authority means a full, live admin session, current enabled account/role and **all** named permissions. Attendant authority means the live originating attendant session; read endpoints do not renew the offline window. Writes also require the unexpired 24-hour online-sign-in window, otherwise 403 `online_sign_in_required`. Recovery has its own restricted session and grant; neither ordinary admin nor attendant cookies alone authenticate its transfer endpoints. All mutations recheck live authority under the M2 security-state lock through commit, including after slow evidence work. First-password sessions cannot authorize any M3 action.

Common errors on every endpoint: 400 `invalid_request`, 401 `unauthenticated`, 403 `permission_denied`/`origin_rejected`/`password_change_required`, 413 `request_too_large`, 429 `rate_limited`, 503 `temporarily_unavailable`; resource calls add 404 `not_found`. Domain writes add 409 `operation_conflict`/`version_conflict`. `reason` is required trimmed 1..1000 characters; evidence notes use the same bound, contain no secrets or phone numbers, and render as text. Inputs follow M2's 32 KiB body ceiling, except a recovery manifest may be 128 KiB with at most 100 items. Rates R/W/V/T are M2 profiles unless overridden. Retry-After applies to 429 and asynchronous 202; only transient errors are retryable. Lost responses require same-key reconciliation, never new sale identities.

The tables specify request/success, authority, idempotency/rate and concurrency for **every** endpoint. `Read` means side-effect-free, no operation key or version precondition; POST searches still check Origin. `Domain` means M2 durable actor+operation-kind+operationId receipt, canonical digest including route IDs, expected versions and every material field, same-key changed-content conflict, live authorization before replay, original historical result on successful replay. Replaying a successful mutation is checked before testing its now-stale versions; it cannot apply twice. The receipt retains no secret/URL. Retrieve current state separately. Invalid/rolled-back mutations create no success receipt. Decision conflicts require rereading and explicitly reviewing a new operation, never blind version substitution.

`SaleGuard={expectedVersion:Version,expectedRevisionId:Id|null}` compares the purchase aggregate and its current accepted revision (null only when no revision is accepted yet). Every sale mutation, hold/proposal/duplicate change and validation-state change increments purchase.version once in its transaction. A hold decision also supplies expectedHoldVersion; a correction decision expectedCorrectionVersion; a duplicate decision both purchase versions and expectedFlagVersion. These child checks never replace the purchase guard. Lock security state first, then all touched domain aggregates in deterministic ID order; finalization, normal corrections and recovery use the same purchase locks. Serialize customer/card replacement with historical card resolution/finalization so replacement committed before upload cannot be missed.

A successful decision writes its immutable receipt, revision/hold/flag changes, audit and any change to contribution atomically. It clears only its own hold; customer, validated evidence, exact calculations, historical authorization, other holds, trusted timing and applicable eligibility/deadline gates must still pass. A decision may succeed while `credited=false`. Ordinary retries, duplicate flags and recovery never grant acceptance authority. Cancellation is terminal, preserves all history and contributes zero; no restore endpoint exists. Pending late corrections leave the previous accepted contribution unchanged. Totals are derived from current accepted revisions, not additive retry counters. Later changes mark affected finalized campaigns for reconciliation and never rewrite snapshots; M4 finalization APIs are outside this document.

**Amended by WO-spec-3a, 4 Nov 2026.** `policyBlocks` are durable conditions separate from holds: `capture_authorization_unresolved` and `capture_time_unresolved` (P-20 capped interval varies), `retirement_policy_unresolved` (WHR-39), `eligibility_configuration_unset`, `correction_evidence_policy_unset` (legacy/unapproved correction kinds only; P-22 below), `meter_reconciliation_policy_unset` (WHR-50), and `correction_authorship_unverified` (P-19). M1 retains pendingReason='policy_review_required'; M3 exposes individual blocks. Original validation blocks preserve zero credit. Proposal-local blocks preserve the prior accepted contribution.

**Amended by WO-spec-3b, 5 Nov 2026.** P-20 refines P-18: capture lies in [S, U], where S is the original capturing context's immutable online sign-in, R is the purchase's first durable receipt, and U = min(R, that context's offlineExpiresAt). Reauthentication, recovery and retry replace none of these facts. P-02 relies on the app stopping capture at 24 hours; capturing later requires app tampering. Receipt after expiry alone creates no hold. Phone/UUID time and photo metadata supply no evidence. One server policy module evaluates price, assignment and campaign history over [S, U]; Q-528 client confirmation remains pending.

If every instant gives the same applicable price and authorized assignment, with no campaign start/end crossing, proceed through normal validation and credit only when every other gate passes. This proves the relevant answers, not an exact capture instant. A constant answer outside the campaign remains campaign-ineligible; upload deadline still uses R. A configuration-only precision change is not a price change (I-31). Changes strictly after U cannot create capture uncertainty; expiry itself is not an authorization revocation. Evaluate the closed interval conservatively at U, including assignment/revocation events at U. The app still stops capture at expiry. Invalid bounds or missing history cannot establish eligibility.

If the answer varies, a price change opens the existing price hold; an assignment change or context revocation within [S, U] opens capture_authorization_unresolved, and a campaign boundary opens capture_time_unresolved, for M3 capture review at zero credit. Return every applicable condition. These two blocks do not apply merely because capture was offline. Review still requires sufficient evidence; verifying a calendar day cannot establish an assignment or within-day instant. Missing or inconsistent server history cannot establish a uniform answer and remains pending validation without credit. Existing capture blocks clear only through the evidence-backed M3 capture decision; retry, reauthentication or policy reevaluation alone cannot clear them.

No M3 route resolves uncertain historical authorization or within-day time merely by asserting a boolean, clearing a different hold or verifying a calendar day. WHR-39 remains gated. The correction decision below alone may clear correction_authorship_unverified; it records an independent administrative decision without claiming verified attendant authorship.

A correction is a separate immutable operation and revision, never an edit of OriginalSale. Store its **first durable server receipt** before subsequent validation/processing and never replace it on replay. The proposed content, actor, base revision and receipt are immutable. Same ID with changed values conflicts. Creation reserves that proposal and increments purchase.version; the asynchronous validation/decision transition uses the resulting version and cannot overwrite intervening changes. The 201 receipt may be pending_validation; GET reports later progress. Only one pending proposal per sale is allowed; another device must reload it rather than overwrite it. Source data/previous accepted contribution stays intact during pending validation or late review.

The server determines the sale's reliable calendar date and records the midnight boundary and trust/policy version used **at receipt**. Automatic treatment requires receipt strictly before that boundary, own attribution, exact base and all configured correction validation. At midnight or later, state becomes awaiting_review. A server date that cannot be established yields timing=unresolved and awaits authorized review; the phone clock, UUID timestamp or date verification later cannot turn it into an automatic correction or reopen editing. No new midnight window starts at original upload, fresh login or admin date verification. Client automaticEligible is advisory only and a network delay can change the outcome to late review.

For an offline correction, save a second local operation with its original operation ID, immutable base revision/value digest, edit, reason and evidence reference under the same account; never merge it into the original or replace the original blob. Upload/reconcile the original first. If it has not yet acquired an accepted revision, retain the correction locally and report waiting for original validation; do not claim server receipt or invent a base version. When a matching original revision exists, bind that exact base; if effective content changed, require reread/review instead of rebasing silently. The eventual correction's server receipt decides lateness, even when the local edit happened before midnight.

Pending originals/holds and unreliable date policy may therefore delay correction submission; their saved edits must not be discarded.

### Closed evidence resolver registry

The following exact internal categories are exhaustive. Each resolver checks immutable source identity/version, trusted recording time, purchase or original-context binding and station/product/account/card applicability. Shared histories need not belong exclusively to one purchase. Their scope must derive from its original context. An unknown, ambiguous, unrelated or contradictory reference fails without disclosing another record's existence. IDs confer no read authority. A reference cannot be reclassified by client input or configuration.

| Category | Admitted source and permitted conclusion | Limit |
|---|---|---|
| `original_purchase` | Immutable original values/identities and first durable receipt R | Client fields remain assertions; receipt is not capture |
| `capturing_context` | Original sign-in S, original offline expiry, originating account/station/pump/product | Does not prove continuous authorization |
| `frozen_lookup_verification` | This purchase's frozen successful P-23 verification, original lookup T and historical link | No new token verification, exact capture or upload authority |
| `price_history` | Complete effective station/product price activation and captured configuration/precision records | No meter interpretation or capture instant |
| `card_history` | Original old-card/customer linkage, exact replacement event E and associated domain audit | No physical possession; WHR-39 other retirement reasons excluded |
| `assignment_history` | Complete original assignment endings and relevant account/context revocations | Current assignment cannot repair past authorization |
| `campaign_history` | Applicable versioned campaign period, timezone and receipt deadline | Configuration is not evidence of sale time |
| `domain_audit` | Authoritative price activation, card link/replacement, assignment ending/revocation or campaign configuration action, cross-checked against the corresponding category's source record | Only those actions; free text and copied client fields prove nothing |
| `validated_photo` | This purchase's immutable validated bytes/digest and inspectable visible content | No authentic time, identity or authorization; a digest cannot replace bytes |
| `derived_evidence` | Prior same-purchase typed conclusion with reproducible allowed source closure, policy identity, interval, revision binding and precision | No independent witness, stronger precision or new facts |

Every derived dependency must terminate in allowed original server facts. Reject self-reference, cycles, a decision citing itself, cross-purchase conclusions and legacy decisions without reproducible provenance. Re-evaluate applicability against current guarded history and the active policy; a prior approval is not proof. No general admission endpoint or discretionary evidence permission is introduced. Bound traversal; if the complete closure cannot be evaluated within server resource limits, fail closed without accepting a partial graph.

No physical-world time observation is admitted in v1. External receipts transcribed into audit, handwritten/photo timestamps, EXIF, phone/UUID time, upload completion, admin-selected dates and client booleans cannot narrow capture. Neither a note nor two people's attestation replaces source history. The closed registry does not create new upload, photo replacement, external lookup or evidence-reading authority.

### Interval and sufficient combinations

Use closed I=[L,U], with S from the original capturing sign-in, R from first durable receipt and U=min(R, original offline expiry). L=max(S,T) only for the purchase's frozen valid P-23 verification; otherwise L=S. Preserve S/R/expiry/L through retries, recovery and reauthentication. Missing or invalid lookup evidence falls back to S; it does not prove invalidity. New or freshly reverified tokens cannot narrow an old purchase. Missing history, contradictory facts or L>U prevents sufficiency.

Evaluate every instant, including events at L and U, at the stored timestamp precision. Later events strictly after U cannot create interval uncertainty. Verified calendar dates never narrow I for another kind. Receipt still controls upload deadlines and correction midnight; capture evidence controls purchase-period membership. Ordinary automatic validation remains unchanged, and existing review conditions clear only through their authorized decision.

Every sufficient combination includes `original_purchase`, `capturing_context`, the selected `validated_photo`, complete applicable histories, an authorized reasoned decision and the full closure of any derived references. Frozen lookup verification is required only when it supplied L. Count of references, note length and absence of contradictory audit entries are never thresholds. All entries below remain subject to live authority, maker restrictions, SaleGuard, target versions and every independent contribution gate.

| Kind / outcome | Additional sufficient combination | Result and denial boundary |
|---|---|---|

Unknown references, unverified behaviour or mismatched bindings invalidate the profile. The policy digest identifies exact immutable reviewed evaluator artifact bytes, not this Markdown. Its resolver digest must match the installed, approved active `review-evidence-v1` artifact and scope. The active policy approval binds release/digest, configuration revision, full ordered profile identity/version/digest set, resolver dependency, scope and activation time. Reject future activation, unsupported releases, missing evaluators and mismatched approvals. Profile or rule changes require new immutable versions and approval; retain prior bytes and snapshots. Activation, deactivation and rollback each create a higher audited configuration revision; rollback never mutates history.

Pin policy, profiles, resolver configuration and source/history generations during evaluation. Recheck them, live authority and all purchase/hold guards through commit under the existing security/domain locks plus serialized policy state. Deactivation or profile/history change cannot race an acceptance using obsolete facts. Return guarded conflict or reevaluate the complete snapshot before committing; never mix generations. Successful same-key replay checks current authority and returns its immutable original result before current policy/version checks, including after deactivation. Changed content conflicts. New configuration never automatically releases holds or rewrites past decisions.

A manifest cannot add records after confirmation. Larger queues use explicit reviewed batches, not an unbounded grant. Each transfer claims the original account's normal uniqueness namespace, so normal same-account resumption and different recovery grants cannot create a second purchase, correction or contribution. Grant creation does not stamp receipt on unreceived sales.

Receipt is when each original/correction is durably received, never admin authorization time.
