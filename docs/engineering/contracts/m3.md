# M3 corrections, reviews, customer changes, recovery and audit

WO-spec-3 / WHR-46. Normative input for WO-core-8/9/10/11 and WO-app-7/8/9/10. This is a contract and storage specification, not implemented endpoints or security controls. Read with [M1](m1.md), [M2](m2.md), the [data model](../data-model.md) and [invariants](../invariants.md).

Sources: F&R F05–F08 and confirmations of 3 November; TRD Corrections and authoritative time, Price-resolution implementation boundary, Replaced-card offline sales, Unreliable capture-date review and Authorized recovery of stranded outboxes; Sales History, Admin Sales, Admin Customer, Admin Account Recovery, Admin Audit History and Attendant Sale decision notes through 4 November. Board inputs: A09–A11/A14/A19–A22, B03/B04, C02–C05, G01–G05, S01–S04/S06/S07/S09. Board numbers are visual references, never API IDs.

## Shared protocol and transaction rules

M1 strict JSON/types/envelopes, exact decimal strings, UTC instants, no-store, Origin/CSRF, secure host-only cookies and M2 bounds/rate/pagination/permission rules apply. `Id`, `Version`, `Entry`, `PriceSnapshot`, `Medium`, `Category`, `Currency`, `Kobo`, `Quantity`, `Digest`, `SaleStatus`, `Actor`, `Count`, `TotalKobo` and `Page<T>` retain their prior meanings. Every protected object lookup is station-scoped, plus originating-account scoped for attendant routes. Absent or foreign IDs return 404 `not_found`, without ownership disclosure. The M1 sync routes retain their existing `sale_not_found` error.

Admin authority means a full, live admin session, current enabled account/role and **all** named permissions. Attendant authority means the live originating attendant session; read endpoints do not renew the offline window. Writes also require the unexpired 24-hour online-sign-in window, otherwise 403 `online_sign_in_required`. Recovery has its own restricted session and grant; neither ordinary admin nor attendant cookies alone authenticate its transfer endpoints. All mutations recheck live authority under the M2 security-state lock through commit, including after slow evidence work. First-password sessions cannot authorize any M3 action.

Common errors on every endpoint: 400 `invalid_request`, 401 `unauthenticated`, 403 `permission_denied`/`origin_rejected`/`password_change_required`, 413 `request_too_large`, 429 `rate_limited`, 503 `temporarily_unavailable`; resource calls add 404 `not_found`. Domain writes add 409 `operation_conflict`/`version_conflict`. `reason` is required trimmed 1..1000 characters; evidence notes use the same bound, contain no secrets or phone numbers, and render as text. Inputs follow M2's 32 KiB body ceiling, except a recovery manifest may be 128 KiB with at most 100 items. Rates R/W/V/T are M2 profiles unless overridden. Retry-After applies to 429 and asynchronous 202; only transient errors are retryable. Lost responses require same-key reconciliation, never new sale identities.

The tables specify request/success, authority, idempotency/rate and concurrency for **every** endpoint. `Read` means side-effect-free, no operation key or version precondition; POST searches still check Origin. `Domain` means M2 durable actor+operation-kind+operationId receipt, canonical digest including route IDs, expected versions and every material field, same-key changed-content conflict, live authorization before replay, original historical result on successful replay. Replaying a successful mutation is checked before testing its now-stale versions; it cannot apply twice. The receipt retains no secret/URL. Retrieve current state separately. Invalid/rolled-back mutations create no success receipt. Decision conflicts require rereading and explicitly reviewing a new operation, never blind version substitution.

`SaleGuard={expectedVersion:Version,expectedRevisionId:Id|null}` compares the purchase aggregate and its current accepted revision (null only when no revision is accepted yet). Every sale mutation, hold/proposal/duplicate change and validation-state change increments purchase.version once in its transaction. A hold decision also supplies expectedHoldVersion; a correction decision expectedCorrectionVersion; a duplicate decision both purchase versions and expectedFlagVersion. These child checks never replace the purchase guard. Lock security state first, then all touched domain aggregates in deterministic ID order; finalization, normal corrections and recovery use the same purchase locks. Serialize customer/card replacement with historical card resolution/finalization so replacement committed before upload cannot be missed.

A successful decision writes its immutable receipt, revision/hold/flag changes, audit and any change to contribution atomically. It clears only its own hold; customer, validated evidence, exact calculations, historical authorization, other holds, trusted timing and applicable eligibility/deadline gates must still pass. A decision may succeed while `credited=false`. Ordinary retries, duplicate flags and recovery never grant acceptance authority. Cancellation is terminal, preserves all history and contributes zero; no restore endpoint exists. Pending late corrections leave the previous accepted contribution unchanged. Totals are derived from current accepted revisions, not additive retry counters. Later changes mark affected finalized campaigns for reconciliation and never rewrite snapshots; M4 finalization APIs are outside this document.

**Amended by WO-spec-3a, 4 Nov 2026.** `policyBlocks` are durable conditions separate from holds: `capture_authorization_unresolved` and `capture_time_unresolved` (WHR-38 interval varies), `retirement_policy_unresolved` (WHR-39), `eligibility_configuration_unset`, `correction_evidence_policy_unset` (WHR-47), `meter_reconciliation_policy_unset` (WHR-50), and `correction_authorship_unverified` (P-19). M1 retains pendingReason='policy_review_required'; M3 exposes individual blocks. Original validation blocks preserve zero credit. Proposal-local blocks preserve the prior accepted contribution.

**Amended by WO-spec-3a, 4 Nov 2026.** Earl's WHR-38 build default bounds capture by [S, R]: S is the immutable online sign-in that created the original capturing context; R is the original purchase's first durable server receipt. Reauthentication, recovery and retry never replace either bound. Phone time, UUID time and photo metadata supply no evidence. Evaluate historical price and assignment and campaign boundaries over the entire interval in one server policy module; client confirmation remains pending under Q-528.

If every instant gives the same applicable price and authorized assignment, with no campaign start/end crossing, proceed through normal validation and credit only when every other gate passes. This proves the relevant answers, not an exact capture instant. A constant answer outside the campaign remains campaign-ineligible; upload deadline still uses R. A configuration-only precision change is not a price change (I-31).

If the answer varies, a price change opens the existing price hold; an assignment change opens capture_authorization_unresolved, and a campaign boundary opens capture_time_unresolved, for date/authorization review at zero credit. Return every applicable condition. These two blocks do not apply merely because capture was offline. Review still requires sufficient evidence; verifying a calendar day cannot establish an assignment or within-day instant. Missing or inconsistent server history cannot establish a uniform answer and remains pending validation without credit.

No M3 route resolves uncertain historical authorization or within-day time merely by asserting a boolean, clearing a different hold or verifying a calendar day. WHR-39 remains gated. The correction decision below alone may clear correction_authorship_unverified; it records an independent administrative decision without claiming verified attendant authorship.

All strings used as discriminants in these shapes are closed to the enums defined here or in M1; `policyBlocks` uses the list above; hold reason codes remain M1's three codes. `Revision.number` and counters are bounded positive integers; quantity aggregates use non-exponent exact strings with up to six decimals and sufficient integer width. `Values` in ordinary revisions satisfies M1 Entry/calculation rules. In a meter-evidence revision, basis and entered values remain the original capture facts; amount/quantity are independently verified effective values and `calculation:'meter_evidence'` labels the exception. Never relabel those independent values as a normally derived Entry. Original captured price, basis, units and medium remain visible beside every revision.

`SaleDetail` arrays must be bounded: return the latest 25 revisions/corrections/decisions/flags with an additional required `historyCursors:{revisions:string|null,corrections:string|null,decisions:string|null,duplicateFlags:string|null}`. The history endpoint below pages each collection. Do not silently truncate or expose unbounded history. The own-attendant wire types below are separate strict schemas; fields omitted here are absent, never implicitly inherited from full admin objects. They expose no admin identities/reasons, comparison records, replacement-card identifiers or private evidence notes. No navigation can reach another seller's record.

A correction is a separate immutable operation and revision, never an edit of OriginalSale. Store its **first durable server receipt** before subsequent validation/processing and never replace it on replay. The proposed content, actor, base revision and receipt are immutable. Same ID with changed values conflicts. Creation reserves that proposal and increments purchase.version; the asynchronous validation/decision transition uses the resulting version and cannot overwrite intervening changes. The 201 receipt may be pending_validation; GET reports later progress. Only one pending proposal per sale is allowed; another device must reload it rather than overwrite it. Source data/previous accepted contribution stays intact during pending validation or late review.

The server determines the sale's reliable calendar date and records the midnight boundary and trust/policy version used **at receipt**. Automatic treatment requires receipt strictly before that boundary, own attribution, exact base and all configured correction validation. At midnight or later, state becomes awaiting_review. A server date that cannot be established yields timing=unresolved and awaits authorized review; the phone clock, UUID timestamp or date verification later cannot turn it into an automatic correction or reopen editing. No new midnight window starts at original upload, fresh login or admin date verification. Client automaticEligible is advisory only and a network delay can change the outcome to late review.

For an offline correction, save a second local operation with its original operation ID, immutable base revision/value digest, edit, reason and evidence reference under the same account; never merge it into the original or replace the original blob. Upload/reconcile the original first. If it has not yet acquired an accepted revision, retain the correction locally and report waiting for original validation; do not claim server receipt or invent a base version. When a matching original revision exists, bind that exact base; if effective content changed, require reread/review instead of rebasing silently. The eventual correction's server receipt decides lateness, even when the local edit happened before midnight.

Pending originals/holds and unreliable date policy may therefore delay correction submission; their saved edits must not be discarded.

Open A11 in the recorded basis; switching basis clears draft input. Request accepts only the chosen value; server calculates the counterpart exactly with the sale's captured rate/precision and proposed T-10 rounding. Amount-mode money is never reconstructed from display quantity. Product, medium, customer/card, seller, assignment, timestamp and rate are not editable in this numeric contract. EvidenceAssetId must be the sale's retained validated photo. WHR-47 gates production acceptance until the approved correction-evidence policy exists; this is not a decision that other correction fields or replacement evidence can never be supported. If current values come from an independent meter-evidence revision, ordinary correction fails sale_not_correctable until that extension policy is settled; it must not erase the exception by recalculation.

**Amended by WO-spec-3a, 4 Nov 2026.** An unverified_recovery proposal enters ordinary late review regardless of receipt time. The decision requires live sales AND corrections permissions and a normal admin session. For both approve and reject, the caller must differ from the recovery executor and the grant-authorizing admin recorded at first receipt; otherwise 403 permission_denied. Replays recheck these restrictions. The reviewer sees correction_authorship_unverified, originatingSeller and submittedBy; the successful decision atomically clears only that proposal block and records actor, reason and trusted time. Authorship remains unverified_recovery in history; approval does not fabricate attendant authorship. The proposal base must still be current; otherwise 409 base_revision_changed, no overwrite. Rejection may close a stale-base proposal using current purchase/proposal versions; it changes no accepted value.

Both decisions append actor/reason/trusted time. Approval replaces the accepted revision once and re-evaluates all contribution gates without clearing holds; rejection retains it. Transaction count stays one for a continuously eligible sale, never increments for each revision. Cancelled sale cannot accept a correction; pending proposals are closed as rejected with the cancellation decision recorded.

## Duplicate and independent hold decisions — S02–S07

`ReviewEvidence={assetId:Id,notes:string,referenceIds:Id[]}`; max 20 reference IDs. References must resolve to immutable server-recorded context, replacement/audit events or previously admitted evidence for this purchase. A string claiming that a shift sheet exists is not proof. Evidence admissibility is governed by the named policy; no arbitrary external URL or upload path is accepted. Existing photo alone does not prove date or historical assignment. With no approved sufficient evidence, keep the hold; do not infer trust from a nonempty reason.

Duplicate flags are pair records, never holds. Detection thresholds are configurable evaluation work, not a one-minute fixture rule. There is no M3 arbitrary flag-creation endpoint: B04's button requires a later clarified contract. `purchases` contains exactly the flag's two IDs once each; `cancelPurchaseId` must be one member. Keep both closes only that flag, changes neither accepted content nor credit eligibility, and cannot clear other pair flags or holds. Cancellation removes only the selected sale's contribution, leaves the comparison sale's accepted record unchanged and retains both originals. Lock the pair and flag so two admins cannot cancel opposite members from stale reviews.

If either sale was already cancelled, reject a new decision rather than offering keep-both as restoration; existing duplicate flags may remain historical/open with actions unavailable. Historical reasons do not establish another flag's resolution.

Price accept uses captured values only if no newer effective numeric revision would be overwritten; otherwise require a fresh evidence correction or leave held. It resolves price validity, not capture authorization/time. Correct-meter accepts positive exact independent money and quantity within captured product precision, rejects unchanged pairs, and uses an explicit `meter_evidence` revision with original basis/price retained. Neither field is derived from the sync-time rate or from the other field. Any implied rate is display-only exact decimal arithmetic; never a new configured price. WHR-50 gates its reconciliation policy. Cancel invalid sale requires evidence/reason and cannot be used by another permission. All three actions preserve original evidence and other review history.

Card confirm requires proof of a valid purchase **before** the trusted replacement event. Resolve the old card's historical customer; never attach to the new card/customer or reactivate the old card. Unknown timing stays held under WHR-38. Other retirement reasons stay under WHR-39 and cannot use this endpoint. Cancel needs an evidence-supported invalidity decision; uncertainty alone is not invalidity.

Date verification accepts a real Lagos calendar date no later than the server receipt's Lagos day; no browser-time comparison. Store separately from appCapturedAt and trusted receipt. It creates a versioned date resolution retaining effective numeric values (including a prior meter-evidence exception); it never copies old original amounts over an accepted correction. It clears only the date hold. A verified day does not supply a within-day instant, prove an old assignment, waive the upload deadline or reopen correction access. A later amendment of an admin date decision has no endpoint pending policy. Leave pending/Keep reviewing is local navigation with no decision write. There is no date-uncertainty cancellation endpoint.

Decisions without a prior accepted revision stage the selected original/resolution values durably while other holds remain. `currentRevisionId` remains null until `accept_purchase` accepts the fully validated candidate. Subsequent resolutions build on the latest resolution candidate, not immutable original values, so clearing date/card last cannot lose an earlier meter correction. SaleDetail displays original when there is no accepted pointer and exposes the candidate through decisions/revisions; it never labels candidate values credited. This candidate pointer is protected by purchase.version (model below).

The phone-verification adapter sends a cryptographically generated one-time code **only to the current registered normalized phone** for purpose replace_card. Provider/channel, code format/entropy, expiry, attempt cap, resend interval and delivery configuration must be approved/configured under WHR-49; unset means no send or verification, never a sample code. Adapter interface is server-only `request(customerId,purpose,generation)` and `verify(challengeId,code)`, with allowlisted outcomes; it cannot change customers/cards itself. Application verifier is keyed HMAC with key version (low-entropy codes must not be plain-hashed); provider-managed verification must enforce equivalent binding/attempt semantics.

Issuance uses a durable delivery intent and a new generation under the customer lock, revoking all older challenges **and verified-but-unused authorizations** for the customer/purpose. Explicit resend is another issuance operation; same-key retry never sends a new code. Apply customer/purpose and actor/IP buckets across generations; resend cannot reset the cumulative abuse limit. Verification binds customer, purpose, target phone HMAC, customer version, active card ID/version, issuer admin/session and current generation. Under lock, check expiry, attempts, current live permission and all bindings before constant-time comparison. Successful same-key replay returns the historical IdentityChange even though the challenge is now consumed; a different operation cannot reuse it. Phone/card change, resend, logout/session revocation or permission removal makes the authorization unusable.

Old card remains retired forever; historic purchases retain its code and customer, and queued uploads encounter replacement review. No OTP is added to ordinary purchases/registration.
