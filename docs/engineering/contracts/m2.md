# M2 access, station, customers and card contracts

WO-spec-2 / WHR-40. Normative interface specification for WO-core-5/6/7 and WO-app-4/5/6; no endpoint, migration, security control or screen is claimed implemented. Read with [M1](m1.md), the [data model](../data-model.md) and [invariants](../invariants.md). Sources: F&R F02/F03/F08/F12 and November 3 refinements; TRD authentication, verified-email recovery, verification UI, immediate activation, reassignment, sensitive grants and cards; Admin Access, Account Recovery, Users and Roles, Pump and Price, Attendant, Customer, Loyalty Cards and Customer Registration decision notes (through November 4).

## Boundaries and shared rules

M1 wire types, strict objects, envelopes, UTC instants, exact decimal strings, cookie protections, Origin/CSRF checks and no-store rules apply. `Id`, `Version`, `Kobo`, `Currency`, `Category`, `CardCode`, `ProductCode`, `Unit`, `Instant` and `PriceSnapshot` mean the M1 types. A response type below is the envelope's `data` unless explicitly binary or 204. `Count` is a nonnegative base-10 integer string (aggregates may exceed JavaScript safe integers); `TotalKobo` is an exact nonnegative integer string up to NUMERIC(30,0). No floats in price or totals. Optional fields use `?`; nullable fields are present with `null`. Object IDs refer to the entity's UUID, not its display code.

All admin calls require a live admin-kind session, enabled account and role, matching current auth version and the named permission, except explicitly public or restricted-session calls. First-password sessions cannot call normal APIs. Attendant calls require the current attendant session and an unexpired online-sign-in window; expiry gives 403 `online_sign_in_required`. Permissions come from the server, never from request fields or a selected UI role. Host-only secure cookies for the two surfaces have separate names; an attendant session never authenticates an admin wrapper. Better Auth implementation/adapter remains behind these wrappers (T-13).

Common errors for every endpoint: 400 `invalid_request`; 403 `origin_rejected`; 429 `rate_limited` with integer `Retry-After`; 503 `temporarily_unavailable`. Protected calls also have 401 `unauthenticated`, 403 `permission_denied`, `password_change_required`. Public calls do not test arbitrary caller identity. Resource calls add 404 `not_found` for absent/inaccessible IDs without distinguishing another scope. Domain mutations add 409 `operation_conflict`, `version_conflict`. Errors otherwise use the M1 envelope and retryability rule. Business conflicts are not retryable without rereading/reviewing the state. An uncertain network response is not proof of failure.

Every mutation that changes a domain record uses `operationId:Id`; `expectedVersion:Version` applies to an existing aggregate. New objects omit it unless an endpoint names a related version. `reason` is trimmed nonempty text, 1..1000 characters, rendered as text. Browser Review/Keep editing/Cancel are local states; only explicit Confirm sends the mutation. Confirm rechecks live permission, all relevant versions and constraints in the transaction; no mutable review draft grants authority. A conflict returns no partial write and requires a new review and new operation ID.

### Idempotency profiles

| Profile | Rule |
|---|---|
| Read | No operation ID; side-effect-free, retry can see newer data. Read-only POSTs still check Origin. |
| Domain | Unique `(actor user ID, endpoint operation kind, operationId)`; canonical request digest and result reference committed with business changes and audit. Normalize before hashing; include target IDs, expected versions and all material inputs. Same key/different content is 409. On replay reauthorize before returning the original operation result (including applied version/time), not reapplying it. Keep receipt/key for the lifetime of the target; later current state is fetched separately. Rollbacks create no success receipt. A concurrent identical attempt waits for the transaction or returns 503 to retry the same key. |
| Credential | Domain receipt, but compare password-bearing requests using keyed HMAC, never plaintext or an unkeyed password digest. Persist only result references and HMAC/key version; secret fields never enter audit, JSON result, logs or traces. Retain key-verification capability for retained receipts. |
| Sign-in | M1 sign-in replay policy: `Idempotency-Key:Id`, five-minute live-session replay after credential revalidation, no new anchor/session on replay; 409 `sign_in_retry_expired` afterwards, tombstone at least 24h. Reuse after revocation fails 401. |
| Sign-out | `Idempotency-Key:Id`; 204 repeatedly, including absent/stale cookie; only revoke that surface's current session. Retain session-scoped key 24h. |
| Token consume | The purpose-bound token itself is single-use. No success replay grants a session or repeats the effect. A lost response followed by reuse returns 422 `link_unavailable`; verification can be checked by the account holder/admin later, reset user returns to sign-in. |
| Public mail | `Idempotency-Key:Id`; generic 202 for every syntactically valid address. Server-secret HMAC of trusted IP scopes a 24h key/dedup record; request comparison uses HMAC of normalized email, with no raw email/result existence indicator. Repeats do not enqueue again; different address with the same key and IP still gets generic 202, no extra send. After expiry or an IP change a request may send a replacement link subject to the address rate bucket, never change the password. |

Replays of registration after an account change return the original receipt, explicitly historical; the UI must perform current card lookup before starting a new sale. Receipts contain no reusable token, password, email content or download URL. A grant revoked between request entry and commit cannot authorize a mutation: authorization-changing and privileged write transactions serialize their live authority check against the same security lock/version protocol. A handler checking authorization only before opening its transaction is insufficient.

Distributed limits apply across instances; trusted proxy configuration supplies IP. Numbers below are requests/60 seconds, burst equal to limit; all listed dimensions apply. Public identity buckets use secret HMACs, never raw identifiers in telemetry. Account existence does not change public throttling behavior.

| W domain write | 20/account + 60/IP |

Input bounds are engineering proposals under D08: display names 1..120, role/batch/pump names 1..120, search 1..120, username 3..40 ASCII `[a-z0-9._-]` after trim/lowercase (existing sign-in still accepts M1's 1..64 bound), email <=254 after trim/case-fold with syntactic validation and no provider-specific dot/plus rewriting. New/temporary passwords 12..1024 characters, exact/no trimming; confirmation must match; first-password/reset reject the current password. Never ship a demo default password. Display codes <=64, batch count 1..1000 (engineering ceiling, not the prototype's 20-card capacity), quantities per M1. Password history beyond the current credential is not specified; B12's wording is not authority to invent a history policy.

Phone input <=32 characters; the proposed local validation adapter accepts Nigerian national mobile input or its +234 form, strips presentation spaces/hyphens/parentheses, and produces a canonical E.164 string before equality/uniqueness. Reject malformed/truncated inputs, extensions and unsupported formats; no suffix matching on attendant lookup. D08 must approve supported numbering rules before pilot; do not normalize by blindly dropping leading digits. Canonical storage is unique regardless of input spelling. Admin list search may use the last four visible digits, with bounded pagination; it is not an identity proof.

List parameters: `cursor?:string` <=512 opaque server-issued, `limit?:integer` 1..100 default 25. `Page<T>={items:T[],nextCursor:string|null}`. Cursor binds filters/sort and scope, is validated server-side and never bypasses permissions. Default order createdAt descending then UUID descending; histories use server occurrence time descending then UUID. Unsupported sort/filter fields are rejected. Search involving names/phones uses POST bodies, never URLs/access logs. Lists are not repeatable snapshots across pages unless stated. JSON request body ceiling is 32 KiB (engineering limit); oversized bodies return 413 `request_too_large` before parsing. Query execution is parameterized, and raw request/response bodies are not logged.

All permissions are explicit grants; Owner is a protected role containing the catalogue, not an authorization bypass. `—` means no parent view. Owner has 28; proposed Operations has 17; proposed Read-only has 7. The five confirmed Owner-only initial grants are queueRecovery, cardEligibility, dateReview, giveawayFinalize and giveawayRevise; each is independently grantable. Finalizing never implies revising. priceReview initially Owner-only is a proposal. Other starting allocations and final delegation policy remain D06, tracked in [WHR-43](https://linear.app/phaneum/issue/WHR-43). Default for this specification: preserve presets for review, do not auto-provision them into production until explicitly configured/approved. New custom-role editor starts with no grants. Existing assignments are not silently rewritten by seed/config changes.

Delegation's minimum safe rule is enforced on create user, assign role, enable user and create/edit role: actor needs users or roles as applicable; the complete target role's grants must be a subset of the actor's current effective grants AND configured delegable grants (including parent views). For any existing-user mutation, including disabling, both the target account’s current role grants and the proposed role grants must satisfy that same subset/delegation check under the security lock; lowering the proposed role cannot authorize control of a more privileged current account. A non-Owner cannot create/promote/reactivate an Owner or modify an Owner account.

Role edits check both old and new grants against delegation scope so an actor cannot control a more powerful role by removing grants. All memberships affected by a role edit are protected; there is no self-escalation via custom roles, stale role versions or a users-only role picker. Final stricter delegation policy is configurable; unset production delegation policy denies access mutations. This is a conservative engineering guard, not approval of D06's final matrix.

Owner role code/name/grants/status cannot be edited, disabled or deleted through these APIs. No role delete endpoint exists. Serialize all user role/status and role-grant changes on a singleton authorization lock, then lock affected users/roles in deterministic order, recheck actor authority and expected versions, and require at least one enabled admin with enabled Owner role at commit. Concurrent demotions/disables must not remove the last Owner. Initial Owner provisioning is a separate approved bootstrap operation, never a public signup. Any role or status change bumps affected auth versions and revokes their sessions in the same transaction. Preserve actor IDs and historical attribution. A zero-permission role is valid and its session lands on a no-access state, never Overview by default.

|---|---|---|---|---|---|

| POST `/api/admin/password-reset/inspect` | `{token:string}` | 200 `{email:string,expiresAt:Instant}` | Valid reset token, no session required | Read / T | 422 `link_unavailable` |
| POST `/api/admin/password-reset/confirm` | `{token,newPassword,confirmPassword}` | 200 `{reset:true,returnTo:'/admin/sign-in'}`; no new session | Valid reset token | Token consume / T | 422 `link_unavailable`, `password_policy`, `password_mismatch`, `password_unchanged` |
| POST `/api/admin/users/:adminId/verification-requests` | `{operationId,expectedVersion}` | 202 `{delivery:'queued',emailVerified:false}` | users; target within delegation scope | Domain / V | 409 `verification_not_available`; 503 `delivery_unconfigured` |
| POST `/api/admin/email-verification/inspect` | `{token:string}` | 200 `{email:string,expiresAt:Instant}` | Valid verify-email token | Read / T | 422 `link_unavailable` |
| POST `/api/admin/email-verification/confirm` | `{token:string}` | 200 `{verified:true,email:string,returnTo:'/admin/sign-in'}`; no session | Valid verify-email token; explicit recipient confirmation | Token consume / T | 422 `link_unavailable` |

Unknown user, disabled account, wrong kind and bad password share invalid_credentials, status and comparable work. Session GET does not extend absolute or offline lifetimes. Admin idle/absolute/restricted-session durations must be configured under D06; unconfigured production authentication fails closed. First-password checks the live credential and consumes the restriction atomically, revokes all sessions, sets mustChangePassword=false and issues one new full session with rotated cookie. Racing restricted sessions cannot each change it. If the success response/cookie is lost, the user signs in with the new password; a revoked restricted session never replays a full session. Sign-out clears in-memory admin queries/drafts; show B18 only after server revocation succeeds. A network failure locks local UI, with online revocation pending.

Tokens are opaque CSPRNG values with at least 256 bits of entropy (max wire length 256), stored only as cryptographic hashes, bound to purpose, immutable account ID and exact current normalized address. Verification/reset landing GETs never consume a token; inspect performs current validity checks without mutation. Request logs, analytics, referrers, errors and mail-provider metadata redact tokens and addresses; landing pages have `Referrer-Policy: no-referrer`, no third-party scripts/assets and no-store. Read a link token into short-lived page memory and remove it from the visible URL/history before subsequent navigation; never persist it in browser storage. No open redirect parameter exists.

Consume locks account and challenge, then rechecks purpose, current target, enabled status, expiry (`now >= expiresAt` invalid), attempts/revocation and unconsumed state. Reset additionally requires currently verified email. All invalid/used/replaced/mismatched cases share link_unavailable; inspect discloses the address only to a currently valid token holder. Bad password errors are returned only after token validation. Single-use consume, password/verification change and audit commit together. Reset clears first-password restriction, increments auth version, revokes every existing session, invalidates outstanding reset links, and queues a security notification to the verified address in the same transaction; no automatic sign-in. Verification changes only that matching email status, never credentials or role.

Each verification/reset issuance increments a purpose-specific generation under the account lock, revokes earlier challenges and supersedes queued earlier mail before committing a new mail request. Worker checks current generation, target and account again. A resend is a new operation; same-operation retry does not invalidate its own link. Email change (when later authorized) atomically clears verification, increments both generations and revokes old challenges/queued sends. Disable revokes challenges and queued sends; reenable does not restore them. No manually-verified field, Owner password reset or lost-email bypass is exposed.

Mail delivery is asynchronous behind an adapter. Public reset requests always return generic 202, including unknown, unverified, disabled, suppressed or unconfigured delivery cases; processing is asynchronous to avoid timing enumeration. Authenticated verification enqueue reports delivery_unconfigured rather than falsely claiming mail sent. A queued response proves neither delivery nor ownership. Creation below commits the unverified account and verification delivery intent; delivery failures leave a recoverable unverified account with an authorized resend action. Security-notification delivery failures do not roll back a successful password reset.

Challenge delivery workers generate raw secrets only in memory, commit their hashes, then send. A crash/uncertain send is not permission to reconstruct plaintext from storage or resend obsolete tokens: mark that attempt failed/uncertain, revoke its challenge and require a fresh request for a new link. Generation fencing prevents superseded requests creating a current challenge; delayed obsolete mail may arrive but its link cannot redeem. Secret-free security notifications can retry idempotently. Sender/provider, exact token durations, idle/reauth policy and initial Owner process remain D06; no cloud setup is authorized by this contract.

### Assignment-ending offboarding — P-21, WO-spec-2a (WHR-79)

Earl's [WHR-76 decision](https://linear.app/phaneum/issue/WHR-76) of 6 November 2026 resolves the leaver gap: an attendant with no active assignment cannot sign in or capture. Ending the assignment revokes all their sessions immediately on the server. This extends the existing `handover='unassigned'` state without an attendant disable/reset endpoint or pump deactivation. P-10 reassignment remains distinct: it inserts a replacement assignment and requires fresh online sign-in before using it. This section specifies future lane:core work; WO-core-3/6 do not yet implement the complete offboarding rule. UI implementation and board parity are not claimed.

The end endpoint uses the shared strict schema, same-origin/CSRF protection, no-store envelope, entered reason and explicit confirmation rules. A live full admin with `attendants` OR `pumps` may end an assignment, matching existing reassignment authority; neither grant exposes outbox contents or grants queue recovery. Resolve the attendant within the sole station, including historical assignment scope when unassigned; absent/inaccessible IDs return 404 `not_found`. A disabled attendant account returns 422 `attendant_unavailable`. Recheck the admin's live permission at commit, including on replay. Common domain errors and rate profile W apply.

The assignment guard is `{expectedVersion,expectedAssignmentId}`: compare the attendant aggregate version AND the exact active assignment ID, analogous to M3's SaleGuard. Both are required; null is invalid for ending. A mismatched version or a different active assignment returns 409 `version_conflict`; an already-unassigned target with the current reviewed version returns 409 `no_change`. Failed guards change nothing and need a reread, review and new operation ID. Ending versus reassignment, two end requests, and ending versus account provisioning/sign-in/first-password completion serialize so only a request authorized by the reviewed state can commit.

In one transaction, lock security state first, then affected auth-user, attendant and assignment records in deterministic order. Serialize the boundary with sign-in and every attendant protected read/write, including sync/finalize after storage work; use the same assignment-history synchronization as capture validation. Choose trusted server time T strictly after the assignment's start and previous boundary; never accept client effective time or backdate. Close only its `effective_until=T`, increment attendant.version once, increment auth_user.auth_version, revoke all full/restricted auth sessions, and set previously unrevoked capture contexts' revoked_at=T. Preserve earlier revocation timestamps. Commit receipt and audit together; failures roll everything back.

The receipt's attendant is the applied snapshot: `assignment=null`, `handover='unassigned'`, incremented version. `ended` identifies the closed interval, its unchanged assignmentVersion, pump, trusted end time, admin actor and normalized reason. Domain idempotency scopes the key to actor, operation kind and operationId; the digest includes target, both guards and reason. An identical successful replay returns this original snapshot even after later reassignment, without closing another interval, bumping versions or revoking new sessions. A changed target/body under the same key conflicts. Rollbacks leave no success receipt; concurrent identical requests follow the shared Domain rule.

Write a secret-free `assignment_ended` audit event with actor, attendant target, old assignment/pump and aggregate/auth versions, new unassigned state/versions, reason, operation ID and T. Existing assignment history still returns the original interval with effectiveUntil set; its opening actor/reason remain unchanged. The audit supplies the ending actor/reason; do not fabricate a zero-length assignment or rewrite an opening event as an ending event. Past purchases, accepted revisions, attribution, capture bounds and frozen snapshots do not change. No account deletion, credential change or queue deletion is part of offboarding.

Check for an active assignment after credential validation and before issuing either a ready OR first-password session, creating a capture context, or replaying sign-in. Unknown users, wrong passwords and wrong kinds retain generic 401 `invalid_credentials`. Valid credentials with no active assignment receive 422 `assignment_unavailable`, message “Sign-in is unavailable. Ask a station manager for help.” Reveal no username, pump, assignment history or offboarding reason. Issue no cookie/context/online anchor. Revoked sign-in receipts still fail 401, never create a replacement session. Restricted attendant first-password/session paths cannot bypass the leaver check. Admin first-password behavior is unchanged.

After termination commits, stale attendant cookies fail 401 `unauthenticated` on every protected call, including session/configuration reads, lookup, registration, sync, upload permission and finalize. Checks serialize at the read/mutation boundary; a request ordered before termination may finish, while one ordered after cannot authorize from stale claims. An already-issued storage PUT may finish within its TTL, but cannot finalize with revoked authority. A disconnected phone cannot observe server revocation immediately: it may locally save within its original 24-hour window. On observing revocation, lock capture/uploads and the account partition, clear visible personal data and retain every original/blob/operation ID. Never claim instant remote erasure or cancellation.

The unassigned leaver cannot obtain ordinary upload authority by signing in. Stranded records use the existing M3 online, original-phone recovery grant (`sales` AND `queueRecovery`), or a later authorized reassignment plus fresh same-account online sign-in. Neither restores revoked sessions/contexts nor renews original capture bounds. Queues never move to the manager or another attendant. Recovery is submission authority only: P-20 evaluates original S, first durable R and U=min(R, original offlineExpiresAt). Termination/revocation within closed [L,U] under P-23 (otherwise [S,U]), including at U, opens `capture_authorization_unresolved` at zero credit; events strictly after U add no capture uncertainty. Late delivery alone adds none.

An existing capture block clears only via evidence-backed M3 capture review (`sales` AND `dateReview`), confirming supported authorization/time or cancelling; retry, reassignment and recovery do not clear it. Other photo, price/card/date, deadline and eligibility gates still apply. Missing/inconsistent history cannot prove eligibility. Reassignment after an unassigned period creates the next assignment version from the maximum historical assignment version plus one, not from zero because no interval is active; the gap remains visible. It enables future sign-in only, without reauthorizing that gap or changing existing sales.

Required lane:core verification (not implemented tests here): no-assignment sign-in for ready/first-password accounts with generic failure and no cookie/context; revoked replay and all protected routes; multi-device revocation; end versus end/reassign/sign-in/first-password/finalize races; permission removal while waiting; exact guard conflicts and rollback; same-key lost-response replay after reassignment without new revocation; immutable opening history plus ending audit; reassignment after a gap with increasing versions; retained, isolated queues and scoped recovery; P-20 end before/at/after U, original bounds/receipt on retries, and capture review clearing only its own blocks. No new automated coverage or UI parity is claimed by this specification.

## Attendant first-password completion — WO-core-6

Provisioned attendant accounts have `must_change_password=true`. Credential-validated
`POST /api/attendant/sign-in` and `GET /api/attendant/session` return the restricted
response `{state:'password_change_required',account:{id,staffCode,name,username},
sessionExpiresAt,serverTime}` until completion. The account ID is the attendant ID.
The 15-minute restricted cookie has no assignment or capture context, grants no
capture/upload/configuration authority, and does not start an offline capture window.
Normal M1 ready-session responses are unchanged.

`POST /api/attendant/first-password` requires that live restricted attendant cookie,
Origin and JSON `{operationId,currentPassword,newPassword,confirmPassword}`. It uses
Credential idempotency, a server-secret keyed request digest, 5/session + 30/IP per
minute, the shared security lock and current credential verification. New password is
12..1024 exact characters, confirmation matches and the current password is rejected. Attendant provisioning, sign-in and first-password fields share the same no-control-
characters validation (U+0000..U+001F and U+007F rejected); spaces and other Unicode
are preserved exactly. Existing sign-in length compatibility remains 1..1024. Success is 204 and clears the cookie, revokes every account session, records a
secret-free audit, and requires fresh online sign-in to acknowledge assignment and
start the 24-hour capture window.

A revoked cookie cannot replay a success; a fresh
live account session may retrieve the original credential receipt without repeating
the change. Other normal sessions cannot initiate this first-password-only operation. Errors add 422 `password_policy`, 401 `invalid_credentials` and 403
`password_change_required`; ordinary origin/session/rate errors apply.

The app's restricted-state display and password form are tracked separately in WHR-77;
this backend contract does not claim that current attendant screens implement them.

## Registration lookup evidence — P-23 (WHR-91)

`RegistrationReceipt.lookupReceipt` is the additive nullable M1 LookupReceipt field. On first successful registration, mint it for the live session's capture context after the new link exists, within the same atomic registration/operation-receipt transaction. Its issuedAt is server time no earlier than linkedAt; rollback exposes no receipt. Use the M1 signing/binding/lifetime rules. An expired or absent eligible capture context yields null without changing registration eligibility. The phone may use this initial response to start the new sale without an extra lookup.

Idempotent registration replay returns the original lookupReceipt unchanged, including original time/context or null. Never re-sign it at replay time or bind it to the current session. A replay remains historical: revalidate through the M1 card lookup before composing a new sale, especially after relogin, replacement or account-context change. The phone snapshots resulting evidence before composing the draft. The registration mutation receipt may persist this noncredential evidence with its existing protected response snapshot; it grants no session, access or credit.

Exact-phone CustomerLookup is unchanged and does not mint receipts. Its new-sale navigation must use the card lookup when cardUsable is true; unusable/null cards permit no invented replacement. No phone search or registration PII enters Dexie. Store only the M1 minimal Lookup projection plus receipt under the originating account. Registration concurrency, uniqueness, authorization and existing rate limits remain unchanged.
