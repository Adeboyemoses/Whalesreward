# Application build handover

Every production Next build creates an opaque, non-secret build ID. The same value is the Next build ID, compiled `NEXT_PUBLIC_WHR_BUILD`, and the `x-whr-build` header on `/api/**` responses, including errors. An explicit non-secret `NEXT_PUBLIC_WHR_BUILD` may identify a release; it must change with each build. Production start reads the saved build ID rather than generating another. A differing ID requests an update; opaque IDs express difference, not chronological ordering. No API body shapes change.

The attendant adapter observes the header before parsing. A malformed response with a different build produces `app_update_required` and “A newer version is ready. Reload to continue.” A malformed response from the same/unstamped build retains the contract error. Valid authorization errors retain their ordinary treatment. Header observations never grant session or capture authority.

The attendant provider checks the worker on build mismatch, reconnect and visibility changes; it also observes installed waiting workers. A waiting worker must receive explicit agreement from every same-origin attendant window before `skipWaiting`. Every page freezes interaction before asynchronously checking all local partitions for unsent records. A capture, unsupported route, storage failure, missing response or newly discovered window refuses the handover. The internal pending query returns only a boolean, never another account's records or count to the UI. It uses authoritative terminal server status rather than trusting a local state label.

On controller change, only prepared pages may reload, after another capture/outbox check. Other pages retain their current state. The worker claims clients without forcing navigation. A refused handover releases the page freeze immediately, with a five-second fallback if release is lost; another safe attempt follows. The initial worker installation activates normally without an update handshake or reload. A first controller claim releases any preparation requested by another tab. Navigation still uses the existing bounded network-first generic precache fallback. APIs, personal responses and IndexedDB are never cached, cleared or rewritten by the handover.

A page from before this feature has no prepare handler and cannot be remotely given one. It blocks automatic handover until all such old attendant windows are closed once and reopened. This bootstrap limitation must not be worked around with unconditional activation or a forced reload during capture/queued sales. Subsequent releases use the guarded protocol without clearing site data.
