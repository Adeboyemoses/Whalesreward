# M1 attendant and sync contracts

WO-spec-1 / WHR-36. Normative input to `src/shared/contracts` (lane:core) and `src/client/api.ts`/Dexie (lane:app). This specifies M1 interfaces, not implemented endpoints. Sources: F&R F01–F05, TRD auth/sync and November 3 refinements, T-03–T-05/T-11–T-13, [data model](../data-model.md), [invariants](../invariants.md). Corrections, registration, recovery authorization and admin review endpoints are later work orders, not defined here.

## Common wire rules

All endpoints are same-origin HTTPS JSON, `Cache-Control: no-store`; no browser/SW HTTP caching of API responses. Cookies are Secure, HttpOnly, SameSite=Lax with host-only scope; every mutation checks Origin/CSRF. Session credentials never enter JSON, localStorage, Dexie, logs or the SW. Better Auth remains behind these attendant wrappers; WO-core-3 confirms its adapter, not a public client dependency. Check current enabled account, attendant kind, revocation and authorization on every protected call, not cached session claims.

Objects are strict: reject unknown fields. All listed fields are required unless `?` (optional); `T|null` is present but nullable. JSON numbers are allowed only for bounded integer counters, bytes, precision and versions. All identifiers denoted `Id` are canonical UUIDv7 strings; UUID timestamps carry no authority. Dates are RFC3339 instants with explicit UTC `Z` or numeric offset; responses use UTC `Z`. Calendar dates are `YYYY-MM-DD`, validated as real dates. Strings are Unicode; reject controls. Proposed engineering length/rate/size limits below live in centralized configuration and must be validated on pilot devices; they do not settle client policy D02/D06/D08.

| Type | Definition |
|---|---|
| Id | UUIDv7; route IDs validated identically to JSON IDs |
| Kobo | String matching `0|[1-9][0-9]*`, within signed positive BIGINT bound; sale amount and rate >0 |
| Quantity | Non-exponent decimal string, `0|[1-9][0-9]*` optionally followed by 1–6 decimal digits; >0, <=14 integer digits and no finer digits than captured precision |
| Currency | ISO currency code; M1 configured supported value NGN (provisional client currency) |
| Unit | `litre|kilogram` |
| ProductCode | `pms|diesel|kerosene|cooking_gas` |
| Medium | `vehicle|keg|three_wheeler|bike|cylinder`; gas only cylinder, other products only the four liquid choices |
| Category | `car_owner|commercial_bus_driver|three_wheeler_user|bike_user|keg_buyer|cooking_gas_customer` |
| CardCode | Trim surrounding whitespace and uppercase, then configured alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, length 7 (proposal isolated in one constant); no fuzzy match |
| Digest | 64 lowercase hex SHA-256 characters |
| Version | Integer 1..2147483647 |

HTTP success bodies are `{data:T, serverTime:Instant, requestId:Id}`. Failure bodies are `{error:{code:ErrorCode,message:string,retryable:boolean,fields?:Array<{path:string,code:string}>},serverTime:Instant,requestId:Id}`. Messages contain no credentials, raw submitted payload or existence leakage across accounts. Error codes are exhaustive per endpoint plus common errors. HTTP 204 sign-out has no body.

Common errors: 400 `invalid_request` (schema/format); 401 `unauthenticated` (missing/expired/revoked session); 403 `permission_denied` (wrong account kind/action), `origin_rejected`; 429 `rate_limited` with integer `Retry-After` seconds; 503 `temporarily_unavailable`. Retryable is true only for 429/503 and explicitly listed pending transport/storage failures. Network loss is an unknown result: keep local data and retry/reconcile the same identity. All authenticated object endpoints query by both originating account and ID, returning 404 `sale_not_found` for absent or foreign objects without revealing ownership.

Writes use UUIDv7 `operationId` in the body, except sign-in/out which use `Idempotency-Key`. Keys never grant authorization. Each retry rechecks live authority; replay cannot revive a revoked session or bypass a hold. For domain writes persist canonical payload digest alongside key and result; changed payload under the same key gives 409 `operation_conflict`. Normalize numeric spellings and code before hashing with a versioned canonical JSON scheme; exclude transport fields, never exclude immutable sale facts or photo digest. Original sale keys are scoped to originating attendant and kept for the lifetime of its record; corrections never reuse them. Short request caches for other actions are described below.

## Shapes

```ts
// Type notation for schema authors; all time fields use Instant above.
type PriceSnapshot = {
  priceVersionId: Id; version: Version; rateKobo: Kobo; currency: Currency;
  quantityPrecision: number; // integer 0..6
  effectiveFrom: Instant; fetchedAt: Instant;
};
type Session = {
  account: { id: Id; staffCode: string; name: string; username: string };
  station: { id: Id; code: string; name: string; timezone: string };
  assignment: { id: Id; version: Version };
  pump: { id: Id; code: string };
  product: { id: Id; code: ProductCode; unit: Unit };
  price: PriceSnapshot;
  captureContextId: Id;
  lastOnlineSignInAt: Instant; offlineExpiresAt: Instant;
  sessionExpiresAt: Instant; serverTime: Instant;
  reassignmentRequiresSignIn: boolean;
};
type Lookup = {
  cardCode: CardCode; customer: { id: Id; name: string; category: Category };
  lookedUpAt: Instant;
};
type Entry =
  | { basis: 'amount'; enteredAmountKobo: Kobo; amountKobo: Kobo; quantity: Quantity }
  | { basis: 'quantity'; enteredQuantity: Quantity; amountKobo: Kobo; quantity: Quantity };
type OriginalSale = {
  operationId: Id; captureContextId: Id; assignmentId: Id;
  cardCode: CardCode; appCapturedAt: Instant;
  priceVersionId: Id; rateKobo: Kobo; currency: Currency;
  quantityPrecision: number; unit: Unit; medium: Medium; entry: Entry;
  photo: { sha256: Digest; bytes: number; mediaType: 'image/jpeg' };
};
type Hold = { kind: 'price'|'card'|'date'; reasonCode: string };
type SaleStatus = {
  purchaseId: Id; operationId: Id; saleCode: string; version: Version;
  state: 'received'|'photo_pending'|'finalizing'|'credited'|'held'|'cancelled';
  detailsReceived: true; photoValidated: boolean;
  credited: boolean; currentRevisionId: Id|null;
  customer: { id: Id; name: string; category: Category }|null;
  holds: Hold[]; cancellationReason: string|null;
  pendingReason: 'lookup_pending'|'photo_required'|'validation_pending'|'policy_review_required'|null;
  serverReceivedAt: Instant;
};
```

Response text fields: codes max 64 chars, display name 1..120, username 1..64, station/pump labels 1..120. `reasonCode` is a closed enum: `price_uncertain|replaced_card|capture_date_uncertain`, corresponding to the hold kind. Cancellation reason is `customer_not_found|invalid_purchase`; UI can map these to approved plain language. Quantities and amount validation use the data model's `validate_sale_calculation`, including exact amount preservation and one rounding in quantity mode. Rounding mode/quantity limits are centralized; half-up is provisional T-10. Reject overflow before persistence.

`credited` is true iff state=credited, currentRevisionId nonnull, photoValidated, resolved customer, all eligibility checks passed and no open holds. Other states have credited=false. Held requires validated details/photo and at least one hold or pending policy check; cancelled requires cancellationReason, others require null. A photo-complete held result is durably uploaded, not Synced. Return all independent holds; UI must not infer eligibility from a single cleared hold. `received` may still be resolving a customer; never equate null customer in a transient state with cancellation.

## Endpoint catalog

Rate limits are initial server engineering defaults in a versioned configuration: token buckets shared across all app instances, never reset by a process restart. Listed numbers are requests per 60 seconds, burst equal to limit. Apply both account and IP dimensions where specified; trusted proxy configuration determines IP. Return Retry-After without echoing sensitive keys. Upload permission limits do not replace object-size/storage quotas. Operational values can change without changing response shapes.

### POST /api/attendant/sign-in — A01, A18; I-01–I-05, I-09

Body `{username:string,password:string,deviceId:Id}`; username 1..64, password 1..1024 (do not trim password), deviceId is an installation identifier, not proof of device possession. Required `Idempotency-Key:Id`. Reply 200 Session and secure cookie. Validate current account/credential and load current assignment/product/price. A missing configured assignment returns 422 `assignment_unavailable`; invalid credentials, unknown user, disabled account and wrong account kind share 401 `invalid_credentials` and generic message. No customer/account enumeration.

Limit 5/min per normalized username+IP and 30/min/IP, with generic throttling responses. A successful sign-in creates one immutable server anchor and capture context; offlineExpiresAt = lastOnlineSignInAt +24h, never extended by retry. Same key/body retry within 5 minutes returns the same still-live session/anchor after credential revalidation; reissues cookie as necessary. Do not store raw password or plain digest of it for replay; use server-secret HMAC of canonical request for short-lived comparison. After cache expiry a reused key fails 409 `sign_in_retry_expired`; user explicitly starts a fresh sign-in with a new key. Replays after session revocation fail 401, never create a fresh anchor automatically. Server retains expired-key tombstones for at least 24h; older requests require a new key and fresh authentication.

No retry result is stored on phone beyond the in-flight sign-in attempt.

### POST /api/attendant/sign-out — A12, A13; I-06

Body `{}`; required Idempotency-Key. 204 after revoking the caller's session and clearing cookie. Repeat with the same session or no session is 204; key scoped to session for 24h; no authentication error is needed to clear a stale cookie. Other errors only common Origin/rate/service errors. Limit 10/min/session and 30/min/IP. Sign-out never deletes outbox rows or photo blobs.

Phone offers upload-first or explicit leave-pending. Stop local sync immediately on sign-out; close account views, clear in-memory personal data and lock the partition. If offline or the request fails, locally lock immediately, persist a sign-out-pending marker, and perform online server revocation before session restoration/switching. Never treat a lingering cookie or session GET as permission to unlock a logged-out partition. Fresh online sign-in is required to resume it; no secret background uploader survives handover.

### GET /api/attendant/session — A02, A12, A27; I-03–I-05a

No body/parameters. 200 Session. Limit 60/min/account and 120/min/IP. Common errors only plus 422 `assignment_unavailable` if the acknowledged configuration is unusable. No idempotency key: read-only. It returns the original acknowledged assignment and sign-in anchor; configured reassignment is signalled by reassignmentRequiresSignIn and never silently replaces this context. May return a newer price for future captures on the acknowledged product. Existing form/outbox snapshots remain immutable. An expired offline window does not renew on GET; caller must sign in afresh. Session response is persisted only as the minimal account partition context described below.

### POST /api/attendant/cards/lookup — A02, A03, A24, A27; I-16–I-17, I-27, I-50

Body discriminated union `{source:'code',code:string}` or `{source:'qr',qr:string}`; raw code max 32 chars, QR max 256. QR v1 is exactly the normalized printed CardCode, isolated in one parser; arbitrary URLs are never followed. Future approved QR formats require versioned parser and producer changes. 200 Lookup. Read-only POST needs Origin check but no idempotency key; retries may reflect current linkage.

Limits 30/min/account and 120/min/IP. 404 `customer_not_found` only after authoritative lookup establishes no linked customer; 422 `card_unavailable` for retired/replaced cards on a *new* sale. Network/storage errors are 503 and never mapped to not-found. Online new captures require a resolved customer, while offline cache miss may save pending lookup. This lookup response cannot retrospectively cancel queued originals: submit resolves historical linkage and replaced-card holds independently.

### POST /api/sync/sales — A05, A08; I-22–I-30, I-31–I-35

Body OriginalSale; operationId is the durable idempotency key. 201 SaleStatus on first durable insertion; 200 SaleStatus on identical replay (current state, not stale cached success). Limit 60/min/account and 180/min/IP. Require a current online-authenticated session for the originating account and its unexpired 24-hour window at submission. Historical captureContextId remains on an old queued sale after same-account reauthentication. Server derives seller/station/pump/product from that historical context and validates context/assignment ownership and authorization history. No client-supplied account or seller field is accepted.

Additional errors: 403 `online_sign_in_required` (window elapsed; preserve and pause), 409 `operation_conflict`, 422 `capture_context_invalid`, `calculation_invalid`, `medium_invalid`, `photo_metadata_invalid`, `policy_review_required`. Uncertain historical timing/authorization is preserved as pending validation, with zero credit; it is not rejected merely because the current assignment differs. A 422 policy response requires needs-attention and retained data, not deletion. Payload bytes/digest limits: compressed JPEG >0 and <=8 MiB, <=16 megapixels and <=6000 px per dimension after decode; these are initial safety ceilings, distinct from trial compression targets.

Persist original and first durable server receipt before customer resolution. A definitive absent customer yields a durable cancelled SaleStatus, not a transport error; transient lookup failure yields received/lookup_pending or 503 with safe same-key retry. Historical replaced card resolves its historical customer and opens a card hold. Price comparison uses captured version/history and trusted capture evidence, never only the latest sync-time rate. Uncertain time/price stays pending/held; UUID/device timestamp alone is insufficient.

**Amended by WO-spec-3a, 4 Nov 2026.** Earl's WHR-38 build default bounds capture by [S, R]: S is the immutable online sign-in that created the original capturing context; R is the original purchase's first durable server receipt. Reauthentication, recovery and retry never replace either bound. Phone time, UUID time and photo metadata supply no evidence. Evaluate historical price and assignment and campaign boundaries over the entire interval in one server policy module; client confirmation remains pending under Q-528.

If every instant gives the same applicable price and authorized assignment, with no campaign start/end crossing, proceed through normal validation and credit only when every other gate passes. This proves the relevant answers, not an exact capture instant. A constant answer outside the campaign remains campaign-ineligible; upload deadline still uses R. A configuration-only precision change is not a price change (I-31).

If the answer varies, a price change opens the existing price hold; an assignment change opens capture_authorization_unresolved, and a campaign boundary opens capture_time_unresolved, for date/authorization review at zero credit. Return every applicable condition. These two blocks do not apply merely because capture was offline. Review still requires sufficient evidence; verifying a calendar day cannot establish an assignment or within-day instant. Missing or inconsistent server history cannot establish a uniform answer and remains pending validation without credit.

### POST /api/sync/sales/:purchaseId/upload-permission — A08; I-25, I-48

Body `{operationId:Id,sha256:Digest,bytes:number,mediaType:'image/jpeg'}`. Response 200 `{uploadId:Id,method:'PUT',url:string,headers:Record<string,string>,expiresAt:Instant,maxBytes:number}`. URL is HTTPS storage staging URL, max 4096 chars; headers include the fixed media type and any signed integrity headers. Never persist/log the URL. Limits 10/min/purchase and 60/min/account plus 180/min/IP. Additional 403 online_sign_in_required, 404 sale_not_found, 409 operation_conflict/sale_not_uploadable, 422 photo_metadata_invalid. Metadata must exactly match immutable original; permission is only for its pending photo, random staging key, no public ACL or final-key permission.

Key scope purchaseId+operationId. Same key/body replays the same permission while valid. Expired permission gives 409 `upload_permission_expired`; generate a new permission operation ID to obtain a fresh unique staging location for the unchanged sale/blob. The expired attempt cannot replace a selected validated asset. Signed permission TTL initially five minutes (server config); account revocation prevents renewal/finalization but cannot revoke an already issued URL instantly. Storage enforces signed method/key/content restrictions; finalizer also enforces actual bytes and bounds. Direct PUT failure leaves local blob intact. Successful PUT alone changes no loyalty state.

### POST /api/sync/sales/:purchaseId/finalize — A04, A14; I-25–I-26, I-31–I-35

Body `{operationId:Id,uploadId:Id,expectedVersion:Version}`. 200 SaleStatus if settled; 202 SaleStatus(finalizing) with Retry-After if processing. Key scope purchaseId+operationId, durable; identical replay returns current result, even if expectedVersion has since advanced due to that same operation. Different body conflicts. Limit 10/min/purchase, 60/min/account and 180/min/IP.

Additional errors: 403 online_sign_in_required; 404 sale_not_found; 409 operation_conflict, stale_version, sale_not_uploadable; 422 upload_not_found, photo_invalid; 503 storage_unavailable. photo_invalid includes bounded field reason `digest_mismatch|decode_failed|size_exceeded|type_invalid`; server never echoes image contents/paths. Transport failures are retryable; invalid immutable photo cannot be repaired by mutating the original operation. Keep local record for support/admin resolution; a fresh sale must not silently replace it and double-count.

Validate upload ownership, actual decoded bytes, digest and dimensions; create immutable server-only final object then atomically recheck current authority, purchase version, resolved customer, evidence ownership and every eligibility/hold condition. Credit with accepted revision+audit once, or return held with zero contribution. Races with another finalize cannot create two current revisions. A lost response is reconciled by status before uploading again. Finalize retry never clears a hold. Current session revocation is rechecked at the commit boundary, including after slow storage work.

### GET /api/sync/sales/by-operation/:operationId — A04, A08, A14, A23

No body/query. 200 SaleStatus; common errors +404 sale_not_found. Limit 120/min/account and 240/min/IP. No idempotency key, read-only. Scope is current originating account and operation ID, so the phone can recover when submit response containing purchaseId was lost. Reads never renew offline access, assign ownership, validate photos or resolve holds. Status can be read with a live session even when capture/uploads need fresh sign-in; ordinary foreign-account lookup is always 404.

## Local records and state machine

Dexie version 1 logical store contract; implementation migrations belong to WO-app-2 and require offline-engineer review. Primary outbox key `[originatingAccountId+operationId]`; indexes `[originatingAccountId+state]`, `[originatingAccountId+nextAttemptAt]`. Every read/write/upload scopes the originating account, never only operationId. The ordinary UI and background uploader have no API to enumerate another partition. Local partitioning is not encryption against physical access; managed-device/local-data protection is a separate security constraint, never claim that a name filter secures storage.

```ts
type OutboxRow = {
  schemaVersion: 1; originatingAccountId: Id; operationId: Id;
  original: OriginalSale; // immutable after atomic save
  captureDisplay: { sellerName:string; sellerUsername:string; staffCode:string;
    stationId:Id; stationCode:string; pumpId:Id; pumpCode:string; product:ProductCode };
  customerCache: Lookup|null; // display hint, never authority
  photoBlob: Blob; photoDigest: Digest; // same compressed JPEG as original.photo
  state: 'saved'|'submitting'|'photo_pending'|'uploading'|'finalizing'|
    'credited'|'held'|'cancelled'|'needs_attention';
  purchaseId: Id|null; serverVersion: Version|null; serverStatus: SaleStatus|null;
  uploadOperationId: Id|null; uploadId: Id|null;
  finalizeRequest: {operationId:Id;uploadId:Id;expectedVersion:Version}|null;
  attempts: number; nextAttemptAt: Instant|null; lastErrorCode: string|null;
  localSavedAt: Instant; syncLease: {owner:string;expiresAt:Instant}|null;
};
type OfflineWindow = {
  schemaVersion:1; originatingAccountId:Id; deviceId:Id; captureContextId:Id;
  lastOnlineSignInAt:Instant; offlineExpiresAt:Instant;
  lastTrustedServerTime:Instant; elapsedAtCheckpointMs:number;
  wallTimeAtCheckpoint:Instant; runtimeId:Id;
  locked:boolean; logoutPending:boolean; session:Session;
};
```

Before the first finalize call, atomically persist finalizeRequest in Dexie; its body remains immutable across restarts and status reconciliation, separate from mutable serverVersion/serverStatus. Replay that exact body and operation ID after an unknown result. A definitive stale_version may create a new finalize operation/body only after reconciling authoritative status; never reuse a key with a new expectedVersion.

Original, captureDisplay and photo blob/digest are saved in one Dexie transaction before “Saved on phone”. A quota/transaction failure shows save failure and keeps the draft; no success receipt or removal of photo. State bookkeeping may change, original cannot. Separate correction operations are future work, never rewrite a queued original. Do not delete the blob when only details/PUT arrived. This M1 contract retains the local blob through authoritative credited/held/cancelled status and has no automatic purge; a later bounded retention/migration policy must preserve pending evidence. Held records leave the upload-waiting count only after details+photo are durable, stay visible as awaiting review, and never masquerade as Synced.

Transitions: saved→submitting→photo_pending→uploading→finalizing→credited|held|cancelled. Server received keeps client submitting until resolution/photo_pending. Retryable failures return to the last durable stage with same IDs; unknown submit/finalize response first checks by-operation status. 404 after unknown submit permits retry of the same original, not a new operation. Interrupted submitting/uploading/finalizing on restart reconciles status and reclaims only an expired local lease. 401/403 pauses the partition without deleting or rewriting stage. Conflict/invalid payload becomes needs_attention, with original and blob retained. Any terminal state is derived from server status; local network events cannot set it. Held→credited/cancelled comes only from refreshed server status after authorized review.

Foreground retry uses exponential backoff from 1s to 60s with jitter, honors Retry-After and stops on offline/session lock. Manual retry respects the same server limits; only one lease per account+operation can upload, while server idempotency remains authoritative across tabs/devices. No background retry while logged out, after offline expiry or under a different account. A23 means no records still need upload, not every purchase was credited.

Minimal customer cache has key `[originatingAccountId+cardCode]`, value Lookup only. No phone numbers, lists, photos or credentials. Clear visible cache on logout/account switch; retained data is partitioned and locked. Revalidate online before new capture; stale cache only labels offline pending capture and never authorizes credit. `lookedUpAt` is informational, not proof of current linkage.

## Offline window and service worker

Only successful online sign-in creates OfflineWindow. Binding is account+device+captureContext, not username. Persist server anchor and expiry unchanged across restart. Within one runtime use monotonic elapsed time anchored to server time; never subtract time when wall clock moves backwards. On launch/resume and before capture/save/upload, compute a conservative lower bound from saved checkpoint, monotonic elapsed and wall elapsed; if elapsed >=24h, expire. If restart/clock discontinuity makes elapsed time untrustworthy, lock capture/uploads until trusted online time validation or fresh same-account sign-in. A trusted time read may verify remaining time against the existing anchor, never renew it. Deliberate device/storage manipulation cannot be reliably defeated by browser state alone; server capture eligibility still requires trusted evidence, and uncertainty cannot grant credit.

No fake “secure timer” guarantee.

Sign-out always locks regardless of remaining time; only fresh same-account online sign-in unlocks. Server session expiry/revocation may prohibit uploads before 24h; an offline client cannot instantly detect revocation. Regaining signal, reopening, session refresh and price refresh never reset lastOnlineSignInAt. At exactly 24h, pause capture and uploads, retain original queue and show A18.

SW scope `/attendant/`. Allowlist only static generic attendant route shells, versioned JS/CSS, nonpersonal icons/manifest and fonts. Navigation fallback is generic shell, no server-rendered account data. Exclude all `/api/**`, `/admin/**`, auth redirects/responses, customer data, signed URLs, photos and uploads; network-only/no-store. Dexie is separate from Cache Storage and never copied into SW caches. Updates keep queues and use transactional, versioned, tested migrations; no `clear site data` recovery. Offline admin/registration/sign-in are unavailable. Background sync is optional and may only run while current account/window authorization permits; foreground/manual retry is mandatory.
