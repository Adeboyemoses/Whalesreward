# M1 attendant and sync contracts

WO-spec-1 / WHR-36. Normative input to `src/shared/contracts` (lane:core) and `src/client/api.ts`/Dexie (lane:app). This specifies M1 interfaces, not implemented endpoints. Sources: F&R F01–F05, TRD auth/sync and November 3 refinements, T-03–T-05/T-11–T-13, [data model](../data-model.md), [invariants](../invariants.md). Corrections, registration, recovery authorization and admin review endpoints are later work orders, not defined here.

## Common wire rules

All endpoints are same-origin HTTPS JSON, `Cache-Control: no-store`; no browser/SW HTTP caching of API responses. Cookies are Secure, HttpOnly, SameSite=Lax with host-only scope; every mutation checks Origin/CSRF. Session credentials never enter JSON, localStorage, Dexie, logs or the SW. Better Auth remains behind these attendant wrappers; WO-core-3 confirms its adapter, not a public client dependency. Check current enabled account, attendant kind, revocation and authorization on every protected call, not cached session claims.

Objects are strict: reject unknown fields. All listed fields are required unless `?` (optional); `T|null` is present but nullable. JSON numbers are allowed only for bounded integer counters, bytes, precision and versions. All identifiers denoted `Id` are canonical UUIDv7 strings; UUID timestamps carry no authority. Dates are RFC3339 instants with explicit UTC `Z` or numeric offset; responses use UTC `Z`. Calendar dates are `YYYY-MM-DD`, validated as real dates. Strings are Unicode; reject controls. Proposed engineering length/rate/size limits below live in centralized configuration and must be validated on pilot devices; they do not settle client policy D02/D06/D08.

| Type | Definition |
|---|---|
| Id | UUIDv7; route IDs validated identically to JSON IDs |
| Kobo | String matching `0|[1-9][0-9]*`, within signed positive BIGINT bound; sale amount and rate >0 |
| Quantity | Non-exponent decimal string, `0|[1-9][0-9]*` optionally followed by 1–6 decimal digits; >0, <=14 integer digits and no finer digits than captured precision |
| Currency | ISO currency code; M1 configured supported value NGN (provisional client currency) |
| Unit | `litre|kilogram` |
| ProductCode | `pms|diesel|kerosene|cooking_gas` |
| Medium | `vehicle|keg|three_wheeler|bike|cylinder`; gas only cylinder, other products only the four liquid choices |
| Category | `car_owner|commercial_bus_driver|three_wheeler_user|bike_user|keg_buyer|cooking_gas_customer` |
| CardCode | Trim surrounding whitespace and uppercase, then configured alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, length 7 (proposal isolated in one constant); no fuzzy match |
| Digest | 64 lowercase hex SHA-256 characters |
| Version | Integer 1..2147483647 |

HTTP success bodies are `{data:T, serverTime:Instant, requestId:Id}`. Failure bodies are `{error:{code:ErrorCode,message:string,retryable:boolean,fields?:Array<{path:string,code:string}>},serverTime:Instant,requestId:Id}`. Messages contain no credentials, raw submitted payload or existence leakage across accounts. Error codes are exhaustive per endpoint plus common errors. HTTP 204 sign-out has no body.

**Amended by WO-spec-3f / WHR-100, 11 Nov 2026.** The ten domain codes in [M2’s status inventory](m2.md#domain-status-inventory--wo-spec-3f--whr-100) return 409 with `retryable:false`, retaining this error envelope. The existing `print_layout_unconfigured` remains 409. Policy failures remain fail-closed; no remap cancels a saved sale, clears a hold or authorizes credit. `code_allocation_unavailable`, `delivery_unavailable` and `storage_unavailable` remain transient 503 errors. Health configuration flags are informational only; see the [operations contract](operations.md#get-apihealth).

Common errors: 400 `invalid_request` (schema/format); 401 `unauthenticated` (missing/expired/revoked session); 403 `permission_denied` (wrong account kind/action), `origin_rejected`; 429 `rate_limited` with integer `Retry-After` seconds; 503 `temporarily_unavailable`. Retryable is true only for transient 429/503 and explicitly listed pending transport/storage failures; the remapped 409 codes are never automatically retried. Network loss is an unknown result: keep local data and retry/reconcile the same identity. All authenticated object endpoints query by both originating account and ID, returning 404 `sale_not_found` for absent or foreign objects without revealing ownership.

Writes use UUIDv7 `operationId` in the body, except sign-in/out which use `Idempotency-Key`. Keys never grant authorization. Each retry rechecks live authority; replay cannot revive a revoked session or bypass a hold. For domain writes persist canonical payload digest alongside key and result; changed payload under the same key gives 409 `operation_conflict`. Normalize numeric spellings and code before hashing with a versioned canonical JSON scheme; exclude transport fields, never exclude immutable sale facts or photo digest. Original sale keys are scoped to originating attendant and kept for the lifetime of its record; corrections never reuse them. Short request caches for other actions are described below.

## Shapes

WO-core-3 implementation mapping: `Session.account.id` is the immutable attendant profile UUID (`attendant.id`), also used for the phone's originating-account partition and historical capture-context ownership. The underlying Better Auth user UUID stays server-side; username changes never change this partition key.

```ts
// Type notation for schema authors; all time fields use Instant above.
type PriceSnapshot = {
  priceVersionId: Id; version: Version; rateKobo: Kobo; currency: Currency;
  quantityPrecision: number; // integer 0..6
  effectiveFrom: Instant; fetchedAt: Instant;
};
type Session = {
  account: { id: Id; staffCode: string; name: string; username: string };
  station: { id: Id; code: string; name: string; timezone: string };
  assignment: { id: Id; version: Version };
  pump: { id: Id; code: string };
  product: { id: Id; code: ProductCode; unit: Unit };
  price: PriceSnapshot;
  captureContextId: Id;
  lastOnlineSignInAt: Instant; offlineExpiresAt: Instant;
  sessionExpiresAt: Instant; serverTime: Instant;
  reassignmentRequiresSignIn: boolean;
};
// Opaque evidence, not an authentication credential. Server verifies the inner strict claims.
type LookupReceipt = string; // ASCII, <=2048 bytes; encoding specified below
// Receipt-capable response; legacy response omits lookupReceipt entirely.
type Lookup = {
  cardCode: CardCode; customer: { id: Id; name: string; category: Category };
  lookedUpAt: Instant; lookupReceipt: LookupReceipt|null;
};
type Entry =
  | { basis: 'amount'; enteredAmountKobo: Kobo; amountKobo: Kobo; quantity: Quantity }
  | { basis: 'quantity'; enteredQuantity: Quantity; amountKobo: Kobo; quantity: Quantity };
type OriginalSale = {
  operationId: Id; captureContextId: Id; assignmentId: Id;
  cardCode: CardCode; appCapturedAt: Instant; lookupReceipt?: unknown;
  priceVersionId: Id; rateKobo: Kobo; currency: Currency;
  quantityPrecision: number; unit: Unit; medium: Medium; entry: Entry;
  photo: { sha256: Digest; bytes: number; mediaType: 'image/jpeg' };
};
type Hold = { kind: 'price'|'card'|'date'; reasonCode: string };
type SaleStatus = {
  purchaseId: Id; operationId: Id; saleCode: string; version: Version;
  state: 'received'|'photo_pending'|'finalizing'|'credited'|'held'|'cancelled';
  detailsReceived: true; photoValidated: boolean;
  credited: boolean; currentRevisionId: Id|null;
  customer: { id: Id; name: string; category: Category }|null;
  holds: Hold[]; cancellationReason: string|null;
  pendingReason: 'lookup_pending'|'photo_required'|'validation_pending'|'policy_review_required'|null;
  serverReceivedAt: Instant;
};
```

Response text fields: codes max 64 chars, display name 1..120, username 1..64, station/pump labels 1..120. `reasonCode` is a closed enum: `price_uncertain|replaced_card|capture_date_uncertain`, corresponding to the hold kind. Cancellation reason is `customer_not_found|invalid_purchase`; UI can map these to approved plain language. Quantities and amount validation use the data model's `validate_sale_calculation`, including exact amount preservation and one rounding in quantity mode. Rounding mode/quantity limits are centralized; half-up is provisional T-10. Reject overflow before persistence.

`credited` is true iff state=credited, currentRevisionId nonnull, photoValidated, resolved customer, all eligibility checks passed and no open holds. Other states have credited=false. Held requires validated details/photo and at least one hold or pending policy check; cancelled requires cancellationReason, others require null. A photo-complete held result is durably uploaded, not Synced. Return all independent holds; UI must not infer eligibility from a single cleared hold. `received` may still be resolving a customer; never equate null customer in a transient state with cancellation.

## Endpoint catalog

Rate limits are initial server engineering defaults in a versioned configuration: token buckets shared across all app instances, never reset by a process restart. Listed numbers are requests per 60 seconds, burst equal to limit. Apply both account and IP dimensions where specified; trusted proxy configuration determines IP. Return Retry-After without echoing sensitive keys. Upload permission limits do not replace object-size/storage quotas. Operational values can change without changing response shapes.

### POST /api/attendant/sign-in — A01, A18; I-01–I-05, I-09

Body `{username:string,password:string,deviceId:Id}`; username 1..64, password 1..1024 (do not trim password), deviceId is an installation identifier, not proof of device possession. Required `Idempotency-Key:Id`. Reply 200 Session and secure cookie. Validate current account/credential and load current assignment/product/price. A missing configured assignment returns 422 `assignment_unavailable`; invalid credentials, unknown user, disabled account and wrong account kind share 401 `invalid_credentials` and generic message. No customer/account enumeration.

Limit 5/min per normalized username+IP and 30/min/IP, with generic throttling responses. A successful sign-in creates one immutable server anchor and capture context; offlineExpiresAt = lastOnlineSignInAt +24h, never extended by retry. Same key/body retry within 5 minutes returns the same still-live session/anchor after credential revalidation; reissues cookie as necessary. Do not store raw password or plain digest of it for replay; use server-secret HMAC of canonical request for short-lived comparison. After cache expiry a reused key fails 409 `sign_in_retry_expired`; user explicitly starts a fresh sign-in with a new key. Replays after session revocation fail 401, never create a fresh anchor automatically. Server retains expired-key tombstones for at least 24h; older requests require a new key and fresh authentication.

No retry result is stored on phone beyond the in-flight sign-in attempt.

P-21 offboarding amendment (WO-spec-2a, 6 November 2026): no active assignment means no ready or restricted attendant sign-in, capture context or online anchor. Valid credentials receive 422 `assignment_unavailable` with “Sign-in is unavailable. Ask a station manager for help.” Invalid credentials remain generic 401. Ending an assignment atomically revokes every attendant session; sign-in replays cannot revive them. See [M2 offboarding](m2.md#assignment-ending-offboarding--p-21-wo-spec-2a-whr-79) for guards, revocation races and scoped recovery. Ordinary P-10 reassignment still requires fresh online sign-in without rewriting old contexts.

### POST /api/attendant/sign-out — A12, A13; I-06

Body `{}`; required Idempotency-Key. 204 after revoking the caller's session and clearing cookie. Repeat with the same session or no session is 204; key scoped to session for 24h; no authentication error is needed to clear a stale cookie. Other errors only common Origin/rate/service errors. Limit 10/min/session and 30/min/IP. Sign-out never deletes outbox rows or photo blobs.

Phone offers upload-first or explicit leave-pending. Stop local sync immediately on sign-out; close account views, clear in-memory personal data and lock the partition. If offline or the request fails, locally lock immediately, persist a sign-out-pending marker, and perform online server revocation before session restoration/switching. Never treat a lingering cookie or session GET as permission to unlock a logged-out partition. Fresh online sign-in is required to resume it; no secret background uploader survives handover.

### GET /api/attendant/session — A02, A12, A27; I-03–I-05a

No body/parameters. 200 Session. Limit 60/min/account and 120/min/IP. Common errors only plus 422 `assignment_unavailable` if the acknowledged configuration is unusable. No idempotency key: read-only. It returns the original acknowledged assignment and sign-in anchor; configured reassignment is signalled by reassignmentRequiresSignIn and never silently replaces this context. **Amended by WO-spec-3l / WHR-125:** return the current committed price for the acknowledged station/product in the existing `price` field, following P-27 below. Composed draft/outbox snapshots remain immutable. An expired offline window does not renew on GET; caller must sign in afresh. Persist only the minimal account partition context described below.

### POST /api/attendant/cards/lookup — A02, A03, A24, A27; I-16–I-17, I-27, I-50

Body discriminated union `{source:'code',code:string}` or `{source:'qr',qr:string}`; raw code max 32 chars, QR max 256. QR v1 is exactly the normalized printed CardCode, isolated in one parser; arbitrary URLs are never followed. Future approved QR formats require versioned parser and producer changes. 200 Lookup. Read-only POST needs Origin check but no idempotency key; retries may reflect current linkage.

**Amended by WO-spec-3l / WHR-125:** successful lookup can additionally carry `priceRefresh` under the independent P-27 capability below. P-23 receipt negotiation remains independent; error envelopes and request bodies are unchanged.

Limits 30/min/account and 120/min/IP. 404 `customer_not_found` only after authoritative lookup establishes no linked customer; 422 `card_unavailable` for retired/replaced cards on a *new* sale. Network/storage errors are 503 and never mapped to not-found. Online new captures require a resolved customer, while offline cache miss may save pending lookup. This lookup response cannot retrospectively cancel queued originals: submit resolves historical linkage and replaced-card holds independently.

### POST /api/sync/sales — A05, A08; I-22–I-30, I-31–I-35

Body OriginalSale; operationId is the durable idempotency key. 201 SaleStatus on first durable insertion; 200 SaleStatus on identical replay (current state, not stale cached success). Limit 60/min/account and 180/min/IP. Require a current online-authenticated session for the originating account and its unexpired 24-hour window at submission. Historical captureContextId remains on an old queued sale after same-account reauthentication. Server derives seller/station/pump/product from that historical context and validates context/assignment ownership and authorization history. No client-supplied account or seller field is accepted.

Additional errors: 403 `online_sign_in_required` (window elapsed; preserve and pause), 409 `operation_conflict`, 422 `capture_context_invalid`, `calculation_invalid`, `medium_invalid`, `photo_metadata_invalid`, `policy_review_required`. Uncertain historical timing/authorization is preserved as pending validation, with zero credit; it is not rejected merely because the current assignment differs. A 422 policy response requires needs-attention and retained data, not deletion. Payload bytes/digest limits: compressed JPEG >0 and <=8 MiB, <=16 megapixels and <=6000 px per dimension after decode; these are initial safety ceilings, distinct from trial compression targets.

Persist original and first durable server receipt before customer resolution. A definitive absent customer yields a durable cancelled SaleStatus, not a transport error; transient lookup failure yields received/lookup_pending or 503 with safe same-key retry. Historical replaced card resolves its historical customer and opens a card hold. Price comparison uses captured version/history and trusted capture evidence, never only the latest sync-time rate. Uncertain time/price stays pending/held; UUID/device timestamp alone is insufficient.

**Amended by WO-spec-3b, 5 Nov 2026.** P-20 refines P-18: capture lies in [L, U] under P-23 below (otherwise [S, U]), where S is the original capturing context's immutable online sign-in, R is the purchase's first durable receipt, and U = min(R, that context's offlineExpiresAt). Reauthentication, recovery and retry replace none of these facts. P-02 relies on the app stopping capture at 24 hours; capturing later requires app tampering. Receipt after expiry alone creates no hold. Phone/UUID time and photo metadata supply no evidence. One server policy module evaluates price, assignment and campaign history over [L, U]; Q-528 client confirmation remains pending.

If every instant gives the same applicable price and authorized assignment, with no campaign start/end crossing, proceed through normal validation and credit only when every other gate passes. This proves the relevant answers, not an exact capture instant. A constant answer outside the campaign remains campaign-ineligible; upload deadline still uses R. A configuration-only precision change is not a price change (I-31). Changes strictly after U cannot create capture uncertainty; expiry itself is not an authorization revocation. Evaluate the closed interval conservatively at U, including assignment/revocation events at U. The app still stops capture at expiry. Invalid bounds or missing history cannot establish eligibility.

If the answer varies, a price change opens the existing price hold; an assignment change or context revocation within [L, U] opens capture_authorization_unresolved, and a campaign boundary opens capture_time_unresolved, for M3 capture review at zero credit. Return every applicable condition. These two blocks do not apply merely because capture was offline. Review still requires sufficient evidence; verifying a calendar day cannot establish an assignment or within-day instant. Missing or inconsistent server history cannot establish a uniform answer and remains pending validation without credit. Existing capture blocks clear only through the evidence-backed M3 capture decision; retry, reauthentication or policy reevaluation alone cannot clear them.

P-21 assignment termination does not discard queued originals or change this interval. Revoked leaver sessions cannot call ordinary sync/finalize; an unassigned account cannot sign in to resume uploads. Existing original-phone M3 recovery, or later authorized reassignment and fresh same-account sign-in, supplies upload authority only. A termination within [L,U], including at U, opens the capture authorization block; one strictly after U does not create uncertainty. Preserve original context, seller, assignment, operation ID, photo, bounds and first receipt. An offline phone locks and pauses on observing revocation, retaining its partition; it cannot detect server revocation instantly.

### POST /api/sync/sales/:purchaseId/upload-permission — A08; I-25, I-48

Body `{operationId:Id,sha256:Digest,bytes:number,mediaType:'image/jpeg'}`. Response 200 `{uploadId:Id,method:'PUT',url:string,headers:Record<string,string>,expiresAt:Instant,maxBytes:number}`. URL is HTTPS storage staging URL, max 4096 chars; headers include the fixed media type and any signed integrity headers. Never persist/log the URL. Limits 10/min/purchase and 60/min/account plus 180/min/IP. Additional 403 online_sign_in_required, 404 sale_not_found, 409 operation_conflict/sale_not_uploadable, 422 photo_metadata_invalid. Metadata must exactly match immutable original; permission is only for its pending photo, random staging key, no public ACL or final-key permission.

Key scope purchaseId+operationId. Same key/body replays the same permission while valid. Expired permission gives 409 `upload_permission_expired`; generate a new permission operation ID to obtain a fresh unique staging location for the unchanged sale/blob. The expired attempt cannot replace a selected validated asset. Signed permission TTL initially five minutes (server config); account revocation prevents renewal/finalization but cannot revoke an already issued URL instantly. Storage enforces signed method/key/content restrictions; finalizer also enforces actual bytes and bounds. Direct PUT failure leaves local blob intact. Successful PUT alone changes no loyalty state.

### POST /api/sync/sales/:purchaseId/finalize — A04, A14; I-25–I-26, I-31–I-35

Body `{operationId:Id,uploadId:Id,expectedVersion:Version}`. 200 SaleStatus if settled; 202 SaleStatus(finalizing) with Retry-After if processing. Key scope purchaseId+operationId, durable; identical replay returns current result, even if expectedVersion has since advanced due to that same operation. Different body conflicts. Limit 10/min/purchase, 60/min/account and 180/min/IP.

Additional errors: 403 online_sign_in_required; 404 sale_not_found; 409 operation_conflict, stale_version, sale_not_uploadable; 422 upload_not_found, photo_invalid; 503 storage_unavailable. photo_invalid includes bounded field reason `digest_mismatch|decode_failed|size_exceeded|type_invalid`; server never echoes image contents/paths. Transport failures are retryable; invalid immutable photo cannot be repaired by mutating the original operation. Keep local record for support/admin resolution; a fresh sale must not silently replace it and double-count.

Validate upload ownership, actual decoded bytes, digest and dimensions; create immutable server-only final object then atomically recheck current authority, purchase version, resolved customer, evidence ownership and every eligibility/hold condition. Credit with accepted revision+audit once, or return held with zero contribution. Races with another finalize cannot create two current revisions. A lost response is reconciled by status before uploading again. Finalize retry never clears a hold. Current session revocation is rechecked at the commit boundary, including after slow storage work.

### GET /api/sync/sales/by-operation/:operationId — A04, A08, A14, A23

No body/query. 200 SaleStatus; common errors +404 sale_not_found. Limit 120/min/account and 240/min/IP. No idempotency key, read-only. Scope is current originating account and operation ID, so the phone can recover when submit response containing purchaseId was lost. Reads never renew offline access, assign ownership, validate photos or resolve holds. Status can be read with a live session even when capture/uploads need fresh sign-in; ordinary foreign-account lookup is always 404.

## Local records and state machine

Dexie version 1 logical store contract; implementation migrations belong to WO-app-2 and require offline-engineer review. Primary outbox key `[originatingAccountId+operationId]`; indexes `[originatingAccountId+state]`, `[originatingAccountId+nextAttemptAt]`. Every read/write/upload scopes the originating account, never only operationId. The ordinary UI and background uploader have no API to enumerate another partition. Local partitioning is not encryption against physical access; managed-device/local-data protection is a separate security constraint, never claim that a name filter secures storage.

```ts
type OutboxRow = {
  schemaVersion: 1; originatingAccountId: Id; operationId: Id;
  original: OriginalSale; // immutable after atomic save
  captureDisplay: { sellerName:string; sellerUsername:string; staffCode:string;
    stationId:Id; stationCode:string; pumpId:Id; pumpCode:string; product:ProductCode };
  customerCache: Lookup|null; // display hint, never authority
  photoBlob: Blob; photoDigest: Digest; // same compressed JPEG as original.photo
  state: 'saved'|'submitting'|'photo_pending'|'uploading'|'finalizing'|
    'credited'|'held'|'cancelled'|'needs_attention';
  purchaseId: Id|null; serverVersion: Version|null; serverStatus: SaleStatus|null;
  uploadOperationId: Id|null; uploadId: Id|null;
  finalizeRequest: {operationId:Id;uploadId:Id;expectedVersion:Version}|null;
  attempts: number; nextAttemptAt: Instant|null; lastErrorCode: string|null;
  localSavedAt: Instant; syncLease: {owner:string;expiresAt:Instant}|null;
};
type OfflineWindow = {
  schemaVersion:1; originatingAccountId:Id; deviceId:Id; captureContextId:Id;
  lastOnlineSignInAt:Instant; offlineExpiresAt:Instant;
  lastTrustedServerTime:Instant; elapsedAtCheckpointMs:number;
  wallTimeAtCheckpoint:Instant; runtimeId:Id;
  locked:boolean; logoutPending:boolean; session:Session;
};
```

Before the first finalize call, atomically persist finalizeRequest in Dexie; its body remains immutable across restarts and status reconciliation, separate from mutable serverVersion/serverStatus. Replay that exact body and operation ID after an unknown result. A definitive stale_version may create a new finalize operation/body only after reconciling authoritative status; never reuse a key with a new expectedVersion.

Original, captureDisplay and photo blob/digest are saved in one Dexie transaction before “Saved on phone”. A quota/transaction failure shows save failure and keeps the draft; no success receipt or removal of photo. State bookkeeping may change, original cannot. Separate correction operations are future work, never rewrite a queued original. Do not delete the blob when only details/PUT arrived. This M1 contract retains the local blob through authoritative credited/held/cancelled status and has no automatic purge; a later bounded retention/migration policy must preserve pending evidence. Held records leave the upload-waiting count only after details+photo are durable, stay visible as awaiting review, and never masquerade as Synced.

Transitions: saved→submitting→photo_pending→uploading→finalizing→credited|held|cancelled. Server received keeps client submitting until resolution/photo_pending. Retryable failures return to the last durable stage with same IDs; unknown submit/finalize response first checks by-operation status. 404 after unknown submit permits retry of the same original, not a new operation. Interrupted submitting/uploading/finalizing on restart reconciles status and reclaims only an expired local lease. 401/403 pauses the partition without deleting or rewriting stage. Conflict/invalid payload becomes needs_attention, with original and blob retained. Any terminal state is derived from server status; local network events cannot set it. Held→credited/cancelled comes only from refreshed server status after authorized review.

Foreground retry uses exponential backoff from 1s to 60s with jitter, honors Retry-After and stops on offline/session lock. Manual retry respects the same server limits; only one lease per account+operation can upload, while server idempotency remains authoritative across tabs/devices. No background retry while logged out, after offline expiry or under a different account. A23 means no records still need upload, not every purchase was credited.

Minimal customer cache has key `[originatingAccountId+cardCode]`, value Lookup only. No phone numbers, lists, photos or credentials. Clear visible cache on logout/account switch; retained data is partitioned and locked. Revalidate online before new capture; stale cache only labels offline pending capture and never authorizes credit. `lookedUpAt` is informational, not proof of current linkage.

## Offline window and service worker

Only successful online sign-in creates OfflineWindow. Binding is account+device+captureContext, not username. Persist server anchor and expiry unchanged across restart. Within one runtime use monotonic elapsed time anchored to server time; never subtract time when wall clock moves backwards. On launch/resume and before capture/save/upload, compute a conservative lower bound from saved checkpoint, monotonic elapsed and wall elapsed; if elapsed >=24h, expire. If restart/clock discontinuity makes elapsed time untrustworthy, lock capture/uploads until trusted online time validation or fresh same-account sign-in. A trusted time read may verify remaining time against the existing anchor, never renew it. Deliberate device/storage manipulation cannot be reliably defeated by browser state alone; server capture eligibility still requires trusted evidence, and uncertainty cannot grant credit.

No fake “secure timer” guarantee.

Sign-out always locks regardless of remaining time; only fresh same-account online sign-in unlocks. Server session expiry/revocation may prohibit uploads before 24h; an offline client cannot instantly detect revocation. Regaining signal, reopening, session refresh and price refresh never reset lastOnlineSignInAt. At exactly 24h, pause capture and uploads, retain original queue and show A18.

SW scope `/attendant/`. Allowlist only static generic attendant route shells, versioned JS/CSS, nonpersonal icons/manifest and fonts. Navigation fallback is generic shell, no server-rendered account data. Exclude all `/api/**`, `/admin/**`, auth redirects/responses, customer data, signed URLs, photos and uploads; network-only/no-store. Dexie is separate from Cache Storage and never copied into SW caches. Updates keep queues and use transactional, versioned, tested migrations; no `clear site data` recovery. Offline admin/registration/sign-in are unavailable. Background sync is optional and may only run while current account/window authorization permits; foreground/manual retry is mandatory.

## Signed lookup lower bound — P-23, WO-spec-3d (WHR-91)

P-23 supersedes only P-20's unconditional lower bound. Let T be a valid lookup receipt's server time, L=max(S,T), and U=min(R, original offlineExpiresAt). Without usable evidence, L=S. One server policy module evaluates card linkage, price, assignment/revocation and campaign history over closed [L,U]. Preserve S, R and the original expiry; upload deadlines still use R. The receipt proves composition order under the app-integrity assumption, not the exact capture instant or present authorization.

### Receipt format and issuance

New clients send `X-WR-Lookup-Receipt: 1` on card lookup and registration. Only that exact capability opts into the strict response shapes containing lookupReceipt; absent/other values preserve the legacy response shape with the field omitted entirely. Both shapes reject unknown fields. The header changes response projection only, never authorization or the mutation's semantic digest. Responses remain no-store. Deploy core support first; app rollout enables the header only after core is available. Old submissions omit the field and retain L=S.

Registration always freezes its original nullable evidence in the protected durable result, even when the caller requests the legacy projection. On replay, project that same result according to the request capability; never mint evidence at replay time. Pre-P-23 durable results have null evidence in the new projection and remain unchanged in storage. An updated client must not treat an absent legacy field as a decoding failure during transition: explicitly accept the strict legacy or strict receipt-capable shape and normalize missing evidence to null locally.

The server emits `lookupReceipt` on successful card lookup; absence of an eligible capture context yields null. Derive context, originating account and station from the live authenticated attendant session, never a client-selected context. Ordinary lookup authorization, errors and rate limits remain unchanged. Issue only before that context's offline expiry, after observing a usable card/customer link in a consistent snapshot serialized with link/retirement changes. Registration issuance follows M2 below. Never sign a client-supplied time or identity.

Wire encoding is `lr1.<kid>.<payload>.<mac>`, at most 2048 ASCII bytes. `kid` matches `[A-Za-z0-9_-]{1,32}`. Payload and MAC use canonical unpadded base64url; reject noncanonical encodings. Payload is UTF-8 canonical JSON with exactly the following keys, in the shown order, with no whitespace or duplicate keys. UUIDs use canonical lowercase spelling; timestamps use UTC milliseconds (`YYYY-MM-DDTHH:mm:ss.sssZ`). The verified object is strict; unknown keys or other versions invalidate the evidence.

```ts
type LookupReceiptClaims = {
  version: 1; purpose: 'capture_lookup';
  captureContextId: Id; originatingAccountId: Id; stationId: Id;
  cardId: Id; cardCode: CardCode; customerId: Id; cardCustomerLinkId: Id;
  issuedAt: Instant; expiresAt: Instant;
};
```

MAC is HMAC-SHA-256 over the ASCII bytes of `lr1.<kid>.<payload>`, using a dedicated, random server-only key of at least 256 bits. Verify the fixed 32-byte MAC in constant time before trusting claims. Select only allowlisted key IDs; no algorithm negotiation or key locations from input. Keys are environment-separated and never sent to clients or committed. Rotation preserves verification keys for outstanding evidence; unrecognized or retired keys cause fallback, never sale rejection. Receipts contain no phone/name, password, session credential or storage URL; redact receipt bytes from logs and general audit.

`expiresAt` equals the original context's offlineExpiresAt: evidence supports composition from issuedAt until that unchanged expiry. Validate S<=T<expiresAt and T<=U, with exact equality at U permitted. Expiry does not impose an upload deadline: R and processing may occur later, including recovery after fresh upload authorization. Verification uses original facts, never current time, a replacement context or the upload session's expiry. Freeze a successful verification result at first durable receipt so later key rotation cannot rewrite it.

### Submission, fallback and immutable replay

`OriginalSale.lookupReceipt` is optional evidence. Its outer schema deliberately accepts any JSON value within the existing request-size limit; the inner receipt schema is strict. Missing, null, wrong type, oversize receipt, malformed encoding, unknown fields/version/key, invalid MAC, invalid timing or mismatched binding all produce L=S, with no receipt-specific rejection. Unknown sale fields and malformed sale facts retain normal errors. This distinction prevents strict receipt parsing from rejecting an otherwise valid saved sale.

Before using T, match the verified claims against the original capture context/account/station, normalized submitted card code, immutable card ID and historical customer/link IDs. Replaying evidence across contexts, accounts or cards is refused as evidence and falls back; it never transfers ownership or grants upload authority. Check the signed link is in force throughout [L,U] and still in force at R (`linkedAt<=L`, `endedAt` absent or strictly greater than R). Replacement at/before R still triggers existing card review even if it occurs after U. Missing history never proves eligibility.

At first durable submission, preserve the submitted evidence value, its verification outcome, policy version and L atomically with the immutable original and R. Include the evidence field in the versioned semantic payload digest: omission and null canonicalize identically; all other values are immutable canonical JSON. Legacy absent-receipt payload digests retain their existing namespace. Same operation plus changed evidence conflicts under I-22; it cannot replace an earlier bound or clear a hold. Ordinary retry, finalize, correction and recovery reuse this evidence and result, never fetch or attach a newer receipt.

### Phone storage and accepted threat boundary

Snapshot the selected receipt into the draft before photo/save, then atomically store it inside OriginalSale with the original and photo blob. Lookup refreshes may update the minimal account-partitioned customer cache, but never a composed draft or saved outbox record. Cached evidence keeps its original timestamp and context unchanged. A cache entry from another context provides no lower-bound authority; a new online lookup is needed for new evidence. Legacy drafts/rows without receipts remain valid using S; migrations preserve their payloads, IDs and blobs.

The HMAC prevents forging time or bindings; it does not prove camera timing. Attaching a later genuine receipt to an earlier sale requires tampering with the app, the same boundary P-02 accepts for its capture window. Same-context receipt reuse for later genuine sales is allowed. Cross-context/account reuse is refused. No receipt renews the offline window, bypasses live session checks, loosens lookup throttling or authorizes credit itself. Dexie may store this evidence, but HTTP/SW caches must not; existing minimal-cache and partition rules apply.

### Expected outcomes and follow-on work orders

Register-then-sell no longer varies across the pre-link part of the shift when the receipt observes the new link. A price activation before lookup no longer creates interval uncertainty if the captured rate matches throughout [L,U]. A card, price, assignment or campaign change after lookup and at/before U still varies and follows existing review. Changes after U do not affect capped capture checks, but replacement/link ending at/before R still requires card review. Other failed checks remain; P-23 never automatically clears existing holds or policy blocks.

Rook should draft these separate high-tier work orders after this specification merges; neither is implementation scope here:

- **Core: P-23 receipt issuance and settlement.** Add strict signed claims and response fields, registration replay handling, key lifecycle, submission fallback/digest persistence, shared policy L and historical link-at-R checks. Test register-then-sell, before/after-lookup changes, exact boundaries, tampering/binding failures, malformed evidence fallback, delayed upload, rotation, concurrent replacement and immutable retries/recovery. Include price, assignment and campaign outcomes plus independent holds.
- **App: P-23 draft and outbox evidence.** After the core contract is available, store lookup/registration evidence in the minimal partitioned cache; freeze it in drafts and atomic outbox saves; send unchanged on retries/recovery. Test offline cached lookup, fresh context/account switches, registration replay, draft refresh races, legacy migration, quota failure and lost responses. Never backfill a newer receipt onto a saved sale.

WHR-38 remains a closed engineering decision gate, refined by P-20 and P-23; client Q-528 confirmation remains pending. WO-core-9 (WHR-16) still owns independent price/card/date and capture review, with unchanged permissions. A receipt does not resolve uncertain history or authorize any new reviewer. Rook should mirror P-23 in the read-only product documents. No runtime fix or test coverage is claimed by this amendment.

## Online price refresh — P-27, WO-spec-3l (WHR-125)

**Amended by WO-spec-3l, 12 Nov 2026.** Earl approved learning the current pump price through calls the online phone already makes, applying it to new drafts and showing a price-updated notice. Saved, queued and settled sales never change. This extends price distribution under P-08/I-32; it supersedes no capture or settlement rule. The open-draft recommendation below keeps the already-approved captured-price rule from the Attendant Sale decisions and M2. This is specification only; core and app implementation require separate approved work orders.

### Responses and strict compatibility

Use successful `GET /api/attendant/session` and `POST /api/attendant/cards/lookup` only. A ready Session keeps its existing shape and returns the current committed `PriceSnapshot` in `price`. Sign-in retains its existing initialization/replay rules. Restricted/password-change responses have no price. No refresh is added to registration, configured-assignment, sync, finalize, status or recovery responses. Registration-to-sale already performs an online card lookup; consume that lookup's snapshot before composing the new sale. Error responses carry no refresh.

On lookup only, send `X-WR-Price-Refresh: 1`. Only the exact value `1` opts into the additional required-but-nullable `priceRefresh` member on successful `data`. Absent or other header values omit that member entirely. `X-WR-Lookup-Receipt: 1` continues to control only `lookupReceipt`. Neither header changes authorization, receipt semantics, rate limits or request content. Both response envelopes and nested objects remain strict. Deploy core first, then enable the app capability; no version-wide permissive decoder or unknown-field stripping.

```ts
type PriceRefresh = {
  captureContextId: Id; originatingAccountId: Id; stationId: Id;
  assignmentId: Id; pumpId: Id; productId: Id;
  price: PriceSnapshot;
};
// LookupBase = existing cardCode, customer and lookedUpAt fields, without extensions.
// Select one strict shape according to the two independent request capabilities:
type LookupWire = LookupBase
  | (LookupBase & { lookupReceipt: LookupReceipt|null })
  | (LookupBase & { priceRefresh: PriceRefresh|null })
  | (LookupBase & { lookupReceipt: LookupReceipt|null;
                    priceRefresh: PriceRefresh|null });
```

| Lookup receipt header = `1` | Price refresh header = `1` | Additional successful fields |
|---|---|---|
| No | No | None; original strict legacy shape |
| Yes | No | `lookupReceipt` only, nullable |
| No | Yes | `priceRefresh` only, nullable |
| Yes | Yes | Both, independently nullable |

An updated client explicitly accepts all four strict shapes during rollout/rollback; normalize absent extensions to null locally. A legacy server's missing field is not a decoding failure. A present malformed extension, unknown key, invalid enum or out-of-range number fails response validation and cannot update price or lookup state; retain existing drafts and local data. A valid null refresh leaves the last known price unchanged and does not turn successful customer lookup into failure. Missing/null is never a zero rate, authorization signal or reason to clear storage.

All `PriceSnapshot` rules apply: positive bounded integer-kobo string, supported currency, quantity precision 0..6, UUIDv7 price ID, Version counter and UTC response instants. `effectiveFrom <= fetchedAt`; both are server values. `version` increases for every station/product configuration activation, including precision-only changes. `fetchedAt` records this read; it is neither a version ordering key nor capture evidence. Never compare UUID order, local time or rate magnitude to decide which version is newer; a newer version can reduce the rate.

### Server scope and snapshot consistency

Derive every binding from the live authenticated attendant's acknowledged capture context, never request-supplied account/pump/product IDs or the admin's configured replacement assignment. Read that station/product's latest committed configuration, not the sign-in price. Keep account-kind, enabled-account, session revocation, Origin and throttling checks. A lookup without a usable acknowledged capture context/configuration returns null refresh; ordinary authorization failures still fail. Session retains its existing `assignment_unavailable` behavior. A refresh never acknowledges reassignment, unlocks a partition or creates a capture context.

Select price fields and version from one consistent database snapshot serialized with price activation. On a lookup that also issues P-23 evidence, observe the card link, price and receipt issuance instant consistently: the returned price must be the version in force at that instant. An activation racing the read may be observed entirely before or after, never as mixed fields or an old price with a post-activation receipt. This does not prevent activation immediately after the read. Preserve P-23 signing, expiry, binding and fallback rules; refresh needs no new signed token.

All responses remain HTTPS/no-store, excluded from HTTP and service-worker caches. Snapshot metadata contains no new customer fields or credentials. The client stores only the latest applicable price in its existing account/context window; do not keep price histories or copy refresh metadata into customer-cache rows, outbox originals, signed receipts or sync payloads. Existing price/version/precision fields on each sale remain its frozen facts. This adds no sale-schema migration or backfill and cannot alter the operation digest.

### Atomic adoption and ordering

Treat Session.price with its surrounding context as the same candidate as lookup.priceRefresh. Before adopting either, match originating account, capture context, station, assignment, pump and product against the active acknowledged local context. Check the request's sign-in/logout generation and current partition again inside the write transaction. A response from an earlier sign-in, switched account, expired/locked context or logout-pending state cannot install a price. A mismatched response changes no price; retain normal session-mismatch/authorization locking behavior. Matching price metadata never substitutes for those checks.

Within the account/context transaction compare against the latest persisted price, not the request-start value. Adopt a strictly greater version as one whole snapshot. Ignore lower versions, including delayed session responses after a newer lookup. Equal version plus identical immutable fields is a no-op; differences in `fetchedAt` alone are harmless. Equal version with different price ID, rate, currency, precision or activation time is inconsistent: reject the candidate, keep the known snapshot and expose the existing invalid-response path. Multiple tabs use the same transactional comparison before starting drafts; no last-writer-wins rollback.

Update only the price portion of the current window. Preserve sign-in anchor, expiry, context, assignment, lock/logout state and nondecreasing elapsed-time checkpoints. Ordinary session processing may validate trusted remaining time under existing rules, but a price read never extends it. Publish the adopted value to the active UI only after persistence succeeds. A failed transaction retains the previous price and gives no success notice; retain draft and queue. Fresh explicit sign-in initializes a new context normally; comparisons never import price state from a different context.

### New and open drafts

A new draft snapshots the latest persisted applicable price atomically with context validation. Do not freeze a sale merely because an empty screen mounted or a card code was typed/scanned. Composition starts on selecting the resolved customer, entering an amount/quantity, choosing a medium, or starting the meter photo, whichever comes first. Automatic defaults do not start composition. For an empty form's online lookup, commit the refresh before selecting the customer and freezing the draft; the ordinary lookup therefore benefits this sale, not just the following customer. Offline uncached capture starts when the attendant enters sale details, as before.

**Recommend keep and warn for an open composed draft.** Preserve its price/version/precision, basis, values, selected lookup evidence, photo, identity and capture time. Display “Price updated to ₦X for new sales. This sale keeps ₦Y. Check the meter before saving.” Use exact two-decimal NGN formatting and the applicable per-litre/per-kilogram unit. Keep the warning visible while this draft's rate differs from the latest adopted rate. Saving remains subject to existing validation and historical review; the warning is not a promise of credit. No automatic repricing, mandatory re-entry or silent draft replacement.

The attendant may deliberately discard the unsaved draft and start a new sale using the current price. That action clears its entered values, photo and selected receipt; the new sale obtains its own normal lookup selection and fresh photo. Never reuse the earlier photo under a newer price or attach a later receipt to the old draft. If refresh arrives during save, that save uses the already-frozen snapshot; the next draft uses the adopted price. If local save fails, keep the original draft and its snapshot for retry.

On an adopted rate change without an open composed draft, show “Price updated to ₦X per litre” or “Price updated to ₦X per kilogram” and use it for the next draft. Show once per adopted version in the active view, not on every lookup or repeat response. A precision-only version updates future drafts but says “Quantity precision updated for new sales”; an open draft keeps its precision with a corresponding persistent notice. An initial sign-in or missing/null extension is not a price-change notification. No UI parity is claimed here; the app work order owns the brief and accessible notice.

### Capture bounds, offline behavior and request limits

P-20/P-23 remain unchanged: S is original sign-in, T comes only from valid signed lookup evidence, L=max(S,T) or S, and U=min(first durable R, original expiry). `effectiveFrom`, `fetchedAt`, response time and adoption time create no new bound or proof of capture. Normal P-23 lookup may supply its existing evidence to a new draft; refreshing price alone cannot. All price, assignment, card, campaign, photo and review gates still apply. A change after lookup and at/before U can still cause a hold; this reduces stale captured rates, not every cause of price review.

Saved/queued originals, settled sales, corrections, accepted revisions, totals and giveaway snapshots are untouched. No refresh changes S/T/L/U/R, clears a hold, verifies a date, rewrites evidence or recalculates existing amounts/quantities. I-31 still distinguishes a historical rate mismatch from a precision-only version change. P-25/P-26 meter review and T-10 exact arithmetic/half-up are untouched. Queued uploads/recovery preserve the original payload and operation identity even when the phone now displays a newer price.

Offline behavior is unchanged: new offline drafts use the latest locally adopted snapshot within the original 24-hour window; composed drafts retain theirs. Network failure or missing refresh preserves that snapshot, original queue and existing error behavior. The app cannot know an offline price activation instantly. Reconnect, resume and refresh never renew sign-in or bypass expiry. At expiry capture/uploads pause as before. Price freshness is not a new prerequisite for capture, and a failed lookup follows its existing customer-resolution rules.

This feature adds **zero requests solely for price refresh**: piggyback on already-needed session reads and user-driven card lookups. No interval polling, new reconnect/resume fetch, hidden-tab loop, background/SW fetch, push channel or refresh-specific retry. Existing lookup/session limits (30/60 per minute per account, respectively, plus their IP limits) are ceilings, not polling targets. Honor existing Retry-After/backoff and deduplication. An idle online phone may retain an older price until its next ordinary call; do not promise immediate distribution. A new user-driven call reads again normally.
