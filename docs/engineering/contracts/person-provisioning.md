Specification only, 23 Nov 2026. Earl commissioned an **Earl-run operator command** on 22 November and directly authorized this specification session. The command, ledger and invalidation rules below are proposed implementation work, not installed functionality or permission to mutate data. Rook reviews, then Earl approves the open choices. [T-24](../decisions/technical.md) records the settled delivery approach only. [Operator walkthrough](../../ops/person-provisioning.md).

Read with [M3 P-29](m3.md#people-and-access), [M4 P-30](m4.md), [review-evidence operations](../../ops/review-evidence.md), and Earl's decisions on [WHR-144](https://linear.app/phaneum/issue/WHR-144) and [WHR-158](https://linear.app/phaneum/issue/WHR-158). Different accounts/sessions never establish different people. Permissions, original-attendant/recovery exclusions and independent approval remain required.

## Why provisioning is needed

At base `0bccb61`, migration `20261116010000_held_release` defines `held_release_person` and `held_release_person_binding`; production has no writer for either. Tests alone insert identities. `release-people.ts` selects the latest binding version and denies absent/unverified identity. `release-v2.ts:assertReleaseV2Installation` requires two distinct verified people among enabled admins; its mutation default additionally requires a verified latest binding for **every enabled auth_user**, including attendants. Preparation skips only that second global test; it grants no mutation authority.

`giveaway/phones.ts` manager designation and independent exclusion decisions, `projection-selections.ts` manager candidates, and `phone-readiness.ts` also depend on these bindings independently of v2 activation. Thus installing v2 tables or granting Owner alone fixes neither blocker. A verified person is not a role, permission, email verification, phone verification or proof of paper truth.

## Recommended identity and verification model

One station person has one permanent opaque UUIDv7 and many admin/attendant accounts. Each `(station_id,user_id)` has at most one effective association, defined by its highest immutable binding version; it is usable only if `verified=true`. Never search for the latest *verified* historical row after a newer revocation. Reuse the canonical person for every alias of the same human. Do not infer identity from equal/different names, emails, account kinds or sessions. Customer IDs are never staff person IDs.

Recommend **manual operator verification** for the pilot ([WHR-224](https://linear.app/phaneum/issue/WHR-224)): Earl privately checks the station's authorized staff roster and account ownership/control with its responsible human, confirms every known alias, and confirms that people intended as independent reviewers are different humans. Password sharing is not account control; account creation and successful sign-in alone are insufficient. Record an opaque reference to a dated private attestation describing the checks and exact account/person association. No identity-document upload, biometric collection or new processor is needed. Reason: this supplies an explicit accountable trust boundary using Earl's existing database authority.

`verification-reference` and `authorization` are distinct non-secret opaque references, each 1–200 ASCII letters/digits/dots/underscores/hyphens. Neither is a URL, evidence text, person's name, email, phone number, credential or document number. The authorization identifies Earl's approval of the exact environment, station, action, account/person IDs, expected versions and next revision. The verification reference resolves in existing access-controlled operational custody, outside repo/Linear/logs, to the attestation. Retain that record with binding/audit history; an unresolvable reference cannot verify identity. Do not collect extra personal data. Person rows themselves contain no name; existing account profiles remain the only application display-name source. Runtime identities and private evidence never go into source, fixtures, public review evidence or tickets.

Verification belongs to a **specific binding version**, not a transferable person-wide badge. Creating a person or binding a new alias never implicitly verifies it. Rebinding requires fresh verification of the destination association, even if another alias is verified. Lost certainty requires revocation, not guessing. No unattended import, self-service linking, Owner UI or automatic duplicate-person merge in this work order.

## Command contract

Proposed entry point: `pnpm ops:people <action>`. It is not yet a package script. Unknown flags/positionals, conflicting flags, malformed IDs, unsafe references, missing scope and cross-station targets fail before writes with safe closed error codes; never echo raw values/errors. Bind SQL parameters throughout. No connection-string/file/dotenv option. All invocations except `--help` require explicit `--station <UUID>` and `--environment development|test|staging|production` and compare the exact persisted database comment as below.

| Action and material flags | Proposed effect | Recommendation and reason |
|---|---|---|
| `create-person --person <new-UUIDv7>` | Insert one identity; no binding or verification | Operator chooses a fresh opaque ID before preview so apply's reviewed target is stable; never reuse an existing ID as an upsert |
| `bind --user <auth_user-UUID> --person <UUID> --expected-binding-version 0` | Version 1 association, `verified=false`; account must have no binding history | Separates identity assertion from verification; no silent overwrite |
| `rebind --user <UUID> --person <different-UUID> --expected-binding-version V` | Append V+1 to the new person, `verified=false` | Explicitly exposes a change of human; never carries verified authority forward |
| `unbind --user <UUID> --expected-binding-version V` | Append V+1 with prior person and `verified=false` | Schema requires a non-null person; this is an append-only revocation, not deletion |
| `disable-person --person <UUID>` | Append unverified successors for every currently verified alias of that person, including disabled accounts, atomically | Revokes all known alias bindings, preserving person/history; it does not disable auth accounts or prevent later expressly authorized re-verification |
| `verify --user <UUID> --person <UUID> --expected-binding-version V --verification-reference <REF>` | Append V+1 for that exact current person with `verified=true` | Fresh accountable check for each alias; no `--verified true` shortcut on bind/rebind |
| `list [--user <UUID> | --person <UUID>] [--history] [--cursor <opaque>] [--limit 1..100]` | Read-only bounded inventory, default 25; no mutation options | Safe inventory and uncertain-commit reconciliation without granting authority |

All writes additionally require `--authorization <REF>` and `--reason-code initial_provisioning|alias_link|identity_correction|identity_uncertain|offboarding|verification_completed` appropriate to their action; no free-text reason. `verify` requires `verification_completed`; rebind requires `identity_correction`; unbind/disable-person allow `identity_uncertain|offboarding`. Create/bind allow initial provisioning or alias link. UUIDs must be existing account/person IDs in the selected sole station, except new person creation. `--user` means `auth_user.id`, never admin/attendant profile ID. The one-station deployment must resolve exactly one station matching `--station`; neither a role nor an assignment moves an account to another station. Disabled historical accounts can be bound and verified for exclusions; their login/role state remains disabled. Binding an auth account does not grant any role, reset a password or bypass first-password change.

A rebind to the same person, verify of an already verified association, revocation of an already unverified association or disable-person with no verified aliases returns `no_change`, with no new revision/audit. Use `rebind` after any prior binding, including an unbound tombstone, when changing person; `bind` never restarts at version 1. Re-verification after unbind of the same person is explicit `verify`. Missing rows, foreign targets, overflow or inconsistent history refuse safely. No batch `verify-all` or raw SQL escape exists.

### Database identity, authority and privacy

Earl alone executes from a reviewed checkout with `DATABASE_URL` supplied privately in his shell through the existing credential workflow; managed TLS must validate certificates. An application session, admin role or agent is not operator authority. Recommend existing deployment database access as the trust boundary, with no new database role/secret issued by this spec. Runtime request handlers must never expose these operations. Audit actor is `system:person-provisioning`, backed by Earl's authorization reference, never a fabricated admin/session actor. This identifies an authorized operator attestation; a reference string cannot authenticate a human by itself.

Every list, preview and apply reads `pg_catalog.shobj_description(oid,'pg_database')` for `current_database()` and requires exact `whr.environment=<explicit-environment>`. Missing, malformed, extra-text or mismatched comment refuses even list/dry run. Ignore `WHR_ENV`, `NODE_ENV`, custom settings and session/role/startup overrides as identity evidence. The command never sets/repairs the comment. Only Earl may perform the separate null-only owner setup in the [existing runbook](../../ops/review-evidence.md#one-time-database-identity-earl-only); stop on any non-null mismatch. Recheck inside the apply transaction. A prior custom-parameter identity is not sufficient (T-19's historical wording is clarified by WHR-143).

Operator terminal output is protected operational data, not application logs. Return only scope, IDs, binding versions/verified flags, revision, reference IDs, categorical result and aggregate blocker/invalidation counts; no display names, usernames, email, phone, raw database errors, evidence contents, connection details, asset paths or signed URLs. Do not capture runtime output in CI, repo, Linear or chat. `list` has no audit side effect, uses a read-only repeatable-read transaction, keyset order `(person_id,user_id,version,id)` (person-only entries use a defined null-first account position), and a scope/filter/revision-bound cursor that refuses changed inventory. It includes unbound accounts, people without accounts and disabled accounts, plus current effective state; history is opt-in. A page reports inventory revision, next cursor and aggregate enabled-account gaps/distinct verified admins. Read-only lists expose no verification/authorization reference by default; explicit exact-revision reconciliation below may show those opaque references privately.

### Preview, revision and transaction semantics

Dry run is default; `--dry-run` is equivalent, mutually exclusive with `--apply`. It uses a read-only snapshot, computes intended new rows and invalidations, and prints the exact apply arguments. It reserves nothing. All mutations require `--apply --expected-revision N`, where N is the **next** station/environment provisioning revision shown by preview (1 for an empty ledger), not an account binding version or release-policy revision. No forced revision, missing compare guard or blind version substitution. After a concurrent change, preview again and obtain authorization covering the new next revision. IDs specified in arguments remain stable; database insertion timestamps are generated at commit, never preview timestamps or operator-supplied backdates.

Specify an additive immutable `person_provisioning_event` ledger with unique `(station_id,environment,revision)`: UUIDv7 event ID, action, operator actor code, authorization/reference, reason code, trusted recorded time, target person/user IDs, old/new binding IDs/versions/verified states, verification reference only for verify, exact alias set for disable-person and affected campaign IDs/generations. Initial revision derives from **all** ledger rows under lock, not a mutable counter supplied by the operator. Large alias/campaign sets use linked immutable child rows rather than an unbounded log JSON. Binding rows keep the existing schema, FK and append-only UPDATE/DELETE/TRUNCATE guards. Extend typed operations/audit allowlists with these exact fields/actions; never weaken the general audit serializer or expose private evidence through audit reads. Existing manual/test rows without operator provenance must be investigated privately before rollout; no guessed verification backfill.

Apply takes the existing exclusive `security_state` lock first; all runtime identity consumers keep the same lock through commit. Then acquire the provisioning scope advisory lock, reporting lock/state, and affected campaigns/purchases in deterministic ID order following the existing shared writer order. Review-policy activation's installation/person check must also participate in this security lock; the CLI-only revision lock cannot exclude runtime approvals or activation. Re-read scope identity, accounts, latest bindings/alias set, revision and expected binding version under these locks. Compute `max(revision)+1`, compare N, then atomically append person/binding/event/audit and invalidate dependants. Unique constraints also enforce versions/revisions. Rejection, rollback, preview, list and no-change produce no business audit or event. Advancing station reporting data version occurs once per effective binding mutation, not once per alias. Person creation without a binding changes inventory revision but needs no giveaway invalidation.

One successful mutation has one provisioning event and one typed audit event (`person_created`, `person_account_bound`, `person_account_rebound`, `person_account_unbound`, `person_bindings_disabled`, `person_binding_verified`); no per-alias duplicate business events for disable-person. Audit contains the minimum non-secret target and old/new state references, reason code, authorization and trusted time; verification reference remains in the protected operator ledger, not general audit projections. All changes roll back if audit/invalidation fails. Account disable/role changes stay in their existing authorized workflows and retain I-08 last-Owner protection.

Uncertain commit: return `commit_unknown`, do not retry automatically. `list --revision N` is a separate exact-event read (incompatible with other list filters/history/cursor); it returns that event and its protected immutable row references, or `not_recorded`. Reconcile scope/action/targets/authorization/binding versions privately. The same already-consumed expected revision refuses and never appends twice. Absence of an acknowledgement is not rollback evidence; after confirming no event, fresh preview and matching authorization precede retry. No network/provider work occurs while locks are held.

## Downstream behavior and safe identity corrections

Recommend station-wide invalidation for effective binding changes ([WHR-225](https://linear.app/phaneum/issue/WHR-225)): pilot volume is small and complete dependency tracking is harder to prove. All affected actions recheck current authority and identity under the shared security lock. Revocation must remain possible even if it makes v2 installation unready; never run readiness as a precondition to unbind/disable-person. Inventory previews show resulting gaps and counts.

| Dependant | Required behavior after binding/reverification/rebind/revocation, or auth disable |
|---|---|
| Pending P-29 proposal | Immutable proposer binding ID/version is pinned. Any change to that binding makes approval `proposal_stale`, even if reverified to the same person. Re-evaluate latest identities of attendant/recovery actors; deny unknown/aliases. Stale proposals remain pending giveaway blockers until an ordinary authorized rejection or supersession; operator command never closes them |
| P-29 uploads | Changed uploader binding denies validation/attachment under existing checks; retained assets/history are not deleted or relabelled |
| Manager designation | Retain immutable designation history. If a manager binding changes or account is disabled, clear the campaign's **live designation pointer**, increment campaign.version, require normal Owner+settings redesignation and a fresh phone check. Same-account redesignation works after pointer clearance; do not hit existing `no_change` guard |
| Phone checks and previews | Every effective binding mutation increments station data generation, marks campaigns reconciliation-required, clears live phone-check pointers and increments campaign versions. Old selection views, prepared tokens and all initial/revision/unchanged confirmations refuse stale state. Preserve old check/census/exclusion/history rows and saved snapshots |
| Pending unavailable-phone proposal | Changed proposer binding or designation/census/settings invalidates approval with `exclusion_stale`; aliases deny `independent_admin_required`, absent binding denies. It remains a global blocker. Add a non-crediting rejection path described below; never silently approve, rebase or drop it |
| Approved phone exclusions | Keep the original approved record immutable; identity change makes its old designation/census/check unusable for fresh certification. A new check cannot recycle old exclusions across changed designation/census; ordinary new proposal/independent approval is required |
| Release configuration | Keep immutable approval/configuration rows and runtime setting unchanged. All-account install check fails closed for new v2 mutations while a latest enabled-account binding is unverified or distinct enabled-admin people fall below two. Restoring bindings can restore the prerequisite for an already approved active configuration; that is not new policy activation. If stopping policy itself is desired, Earl separately uses the deactivate command |
| Prior successful decisions/receipts/snapshots | Preserve original actor/person/binding attribution and frozen contribution history. Replay only after current authority/independence checks; never recalculate prior decision identity using a rebind. Suspected erroneous historical approval requires explicit investigation and the existing authorized sale/campaign revision process, not automatic reversal or deletion |

**Rejection must remain reachable.** Current `phones.ts:decide` resolves the proposer's live verified binding before both approve/reject and checks frozen binding equality, so unbind/rebind can strand a pending exclusion. The single core work order must add a rejection-only branch: a currently enabled verified admin with the original kind's live `sales`, `leaderboards` and giveaway action grant may reject using the stored immutable proposer person and all known historical/current alias exclusions, even if proposer authority/binding, designation, deadline/predecessor or policy is now stale. Require expected current proposal and campaign versions plus a reason and immutable receipt/audit; no source sufficiency or current policy activation is needed for rejection. Do not alter approve checks. Use existing `exclusion_stale` for stale approval and version conflicts for changed rejection guards. Apply the same historical-proposer rejection-only requirement to **P-29**: `release-service.ts:decide` currently calls `independent(..., proposer_id)` before outcome branching in both preflight and commit, so its existing route also fails after proposer unbind. In both phases, a rejection must resolve the frozen proposer person plus retained historical/current aliases without requiring the proposer's latest binding to remain verified or its grant to remain live. The decider still needs a current verified binding and live `sales` plus the proposal kind's action permission, independent of the frozen proposer and all known original-attendant/recovery people. Retain current purchase/revision/proposal guards, same-operation receipt behavior and atomic rejection audit; absent historical exclusion evidence denies rather than guesses. Approval keeps its live proposer/installation/evidence checks unchanged. A rejection never certifies a phone or clears unrelated blockers.

**Rebinding cannot launder self-review.** For P-29 excluded original attendant/recovery users, and for rejection against an immutable proposer, compare the reviewer's current canonical person against the union of all previously verified person associations and the current association of each excluded account. Unknown current excluded identity still denies P-29 approval. Include the original frozen proposer person in exclusions even if it differs from its current person. Preserve those associations forever. This deliberately conservative extension of latest-only `release-people.ts` is required before the command ships: changing an account from human A to B must not let A approve its own earlier sale/proposal. It may deny a genuinely unrelated reviewer after correction; use another independent verified person, never erase history to bypass. Ambiguous/incomplete historical evidence stays held for investigation. No person deletion/merge or account reuse policy is introduced.

Auth disable retains canonical bindings so disabled original attendants/recovery actors remain identifiable. It removes current actor authority immediately and must trigger the same giveaway invalidation/manager clearance through the existing access workflow. Re-enable/new-account creation must expose missing binding readiness before v2 use. A person binding mutation does not revoke the ordinary sale capture window or touch an offline outbox; it affects only identity-dependent approval/certification.

## Enabled attendants: retain the current gate

Recommend **keep every enabled account bound** ([WHR-223](https://linear.app/phaneum/issue/WHR-223)), plus at least two distinct enabled-admin people. Every new attendant must be explicitly bound and verified before v2 mutations resume. Reason: the attendant and recovery actors participate in the same different-person exclusion; an admins-only gate hides rollout omissions until an individual sale is reviewed. Narrowing installation would not remove per-sale identity checks and risks pressure to bypass them. Do not weaken `assertReleaseV2Installation` to make smoke pass. The existing preparation exception can remain advisory. Disabled historical actors still require resolvable verified identity when a particular sale references them; the global enabled-account inventory is not a guarantee that every historical sale has enough evidence or two eligible reviewers.

No requirement is added to ordinary attendant capture/registration solely because v2 is inactive. Two distinct admins are a minimum installation prerequisite, not proof that their per-kind grants, exclusions or live sessions qualify. A third independent person can be necessary when one admin also sold/recovered the target purchase.

Unit-test safe CLI output/error redaction. Run full core gates plus integration; flow changes also require e2e. Staging smoke in the linked runbook is **planned**, not passing evidence.
