# Data model

WO-spec-1 / WHR-35. Schema specification for WO-core-2; no migration or implemented test coverage is claimed. Sources: TRD “Data model and integrity”, “Authentication and pump authorization”, “Offline capture and synchronization protocol” and the November 3 refinements; F&R F01–F12; [invariants](invariants.md); decisions T-03–T-05 and T-13. Only implementation necessities are recorded here.

## Representation and enforcement

Every entity has `id UUID PRIMARY KEY` generated as UUIDv7 and immutable `created_at TIMESTAMPTZ NOT NULL` from server time unless a table below states a composite primary key. UUID time bits never establish capture time. All fields are NOT NULL unless marked `?`. `ref(table)` means UUID foreign key to `table.id`, ON DELETE RESTRICT, ON UPDATE RESTRICT. All FKs have a lookup index. No cascading deletion of financial or attribution history. Mutable aggregates have `version INTEGER CHECK(version > 0)` and compare-and-swap updates; version increments once per committed change. Unlisted columns are not implicitly allowed.

`money` means BIGINT kobo, range 0..9223372036854775807; sale amounts and rates must be strictly positive. Each money group includes `currency CHAR(3)` checked against supported currency configuration (initially NGN). `quantity` means NUMERIC(20,6), positive, at most 14 integer digits; `quantity_precision SMALLINT` is 0..6 and entered quantities cannot contain finer digits. Unit is `litre|kilogram`. All decimal parsing, division, multiplication and rounding use exact arithmetic; no binary floats. Amount-mode quantity is a rounded representation at captured precision, never a source for reconstructing spend. Precision-only changes do not establish a price mismatch.

Enums below are closed sets, implemented as PostgreSQL enums or CHECK constraints. Text identifiers and reasons must be nonempty; UI/input length limits belong to contracts. Cross-row rules require named transaction/service checks or deferred constraint triggers, not a misleading row CHECK. WO-core-2 supplies concurrency tests for those checks. Immutable fields are protected by restricted repository writes plus database update guards; audit/snapshot append-only permissions are enforced in SQL. App roles cannot bypass those guards.

A new sign-in loads the current assignment; old queues retain their capture_context and assignment. Price snapshots may advance within a session for future captures, without moving the offline anchor. **Amended by WO-spec-3b, 5 Nov 2026.** P-20 refines P-18 to [S, U], narrowed to [L,U] by P-23 below: S=capture_context.signed_in_at, R=purchase.server_received_at, U=min(R,capture_context.offline_expires_at). These immutable original facts survive retry, reauthentication and recovery. Late receipt alone creates no hold; price, assignment/revocation and campaign history are evaluated through U, while upload deadline uses R. Compare immutable historical intervals, not the current assignment or phone clock. Store the policy version and evaluated history references in validation/audit; missing history cannot prove uniformity. One server policy module owns the rule, pending client Q-528 confirmation.

### P-21 assignment-ending transaction (WO-spec-2a, 6 November 2026)

`end_assignment` in [M2](contracts/m2.md#assignment-ending-offboarding--p-21-wo-spec-2a-whr-79) checks attendant.version and exact active assignment ID under the security/assignment-history lock protocol. At trusted T strictly after start, close only assignment.effective_until, increment attendant.version and auth_user.auth_version, revoke every full/restricted auth_session, and set all previously unrevoked capture_context.revoked_at=T. Never replace an earlier revocation time. Audit and Domain receipt commit atomically with those changes; no synthetic assignment, deletion or credential mutation. Sign-in, restricted completion, protected reads and sync/finalize commit checks serialize with termination so stale authority cannot survive its commit.

The receipt preserves the applied unassigned attendant snapshot and ended interval/actor/reason/time. Assignment history keeps its opening actor/reason; the `assignment_ended` audit records the end's old/new assignment/pump, aggregate/auth versions and operation ID without secrets. An identical authorized replay returns the receipt, even after later reassignment, without ending or revoking anything again. The next reassignment allocates max historical assignment_version+1, preserving any unassigned gap. Never-having or ending the active assignment prevents ready/restricted attendant sign-in; configured absence is not an account deletion or a replacement for immutable assignment history.

Historical purchase attribution, context signed_in_at/offline_expires_at and first receipt remain immutable. P-20 includes termination/context revocation within [L,U] under P-23 (otherwise [S,U]) as unresolved capture authorization, and ignores events strictly after U for capture uncertainty. Recovery does not renew an original context or grant credit. Existing accepted contributions and frozen snapshots are untouched by the termination itself. This is a schema/service specification for a later lane:core work order; no migration, application change or new implemented test is claimed.

The original payload is immutable. Workflow fields are explicitly separated from it. Server attribution comes from stored capture context, not the phone's name, username or account claim. All foreign-key tuples must agree: context belongs to originating attendant; assignment owns pump; pump owns station/product; price version owns station/product. Enforce with composite FKs/unique tuples where possible and `validate_capture_context` transaction checks otherwise.

`validate_sale_calculation` applies to both purchase and every proposed/accepted revision. It enforces ck_entry_basis and positive bounds on both tables: amount mode has only entered_amount_kobo, amount_kobo equals it, and quantity is amount/rate rounded exactly at captured quantity_precision; quantity mode has only entered_quantity, quantity equals it with no finer digits than captured precision, and amount_kobo is roundOnce(entered_quantity × captured rate_kobo). Captured rate/currency/unit/precision must agree with the referenced price snapshot. Explicit meter-evidence price corrections may retain independently verified amount and quantity under the separate authorized resolution policy; represent that exception with a new revision kind and evidence-backed decision, never silently bypass the ordinary calculation guard. Its detailed reconciliation policy remains D02 and must be settled before implementing such exceptions.

`accept_purchase` verifies the evidence composite ownership, validated state and actual digest equals purchase.expected_photo_digest (or a separately bound immutable expected digest on a future correction operation); no purchase may reference another purchase's photo as its evidence.

`expected_photo_digest` is SHA-256 hex of the compressed saved blob; validation bounds are configuration, not supplied by the browser. Receipt may be committed before customer resolution; infrastructure failure leaves received, not cancelled. Only a definitive authoritative missing customer cancels. A replaced card resolves its historical customer and opens a card hold. Other retirement cases remain unresolved under D05.

Server state transitions:

| From → to | Trigger and atomic guard |
|---|---|
| phone submitted → server received | Authenticated submission; persist unique operation+digest+first receipt before processing. Existing same digest returns existing result; differing digest conflicts. |
| received → photo_pending | Resolution completes or creates applicable holds; definitive absent customer instead cancels with reason. |
| photo_pending → finalizing | Finalize claims purchase version and durable lease; retry sees same in-flight attempt. |
| finalizing → photo_pending | Retryable upload/validation interruption releases claim; preserves original, receipt and blob. Invalid image gives actionable error, no credit. |
| finalizing → held | Validated details/photo but one or more independent holds/eligibility checks unresolved. |
| finalizing → credited | `accept_purchase` commits accepted revision, pointer, state and audit exactly once after all checks. |
| held → held / credited / cancelled | Dedicated authorized hold resolution, expected purchase/hold/revision versions; clears only its kind, reruns all gates. No ordinary retry clears holds. |
| credited → credited | Accepted correction replaces pointer transactionally; prior revision becomes superseded. Pending late correction leaves old pointer/count intact. |
| credited / held / received / photo_pending → cancelled | Authorized cancellation or definitive missing customer where applicable; immutable original retained, contribution zero, audit. |

Cancelled is terminal for this MVP. `finalizing` is a recoverable lease, not evidence of credit: use a maintenance lease or a dedicated finalization claim with purchase_id unique, owner nonce, expiry and fencing version. Finalize writes validated bytes to a fresh server-only final object before DB acceptance. A failed DB commit may leave an orphan; a retry must revalidate/reuse the immutable candidate safely. Cleanup must exclude active claims and referenced objects. Client staging write permissions can never overwrite final objects.

Hold transitions are open→resolved or open→cancelled, independently for price/card/date. Price resolution accepts captured values, writes a meter-evidence revision, or cancels; card resolution confirms historical eligibility or cancels without reactivation; date resolution records evidence-supported verified date <= trusted receipt's station day, without manufacturing within-day time. Actor/reason/server time required. Unknown authorization, capture time or policy cannot become credited through a retry or by clearing another hold.

Revision transitions are proposed→accepted/rejected by normal original validation, authorized before-midnight own correction, or authorized admin review. Accepted→superseded happens only with replacement of current pointer. Cross-row guard requires exactly one current accepted revision at most; an old revision remains immutable history. Late correction receipt, not app time, decides review; correction and original are distinct operations.

Public noneligible reset requests use a uniform generic response without creating an account-bound intent.

The first-password write uses the credential receipt format but revoked restricted sessions cannot replay a full session; after a lost response the new password is used for fresh sign-in. No sensitive-domain mutation may rely on cached authorization or an actor check made before the security lock. Domain transaction deadlocks/serialization failures may retry the same operation, never duplicate successful mutations. All policy configuration reads relevant to authorization must participate in the same version protocol.

## P-23 lookup evidence storage — WO-spec-3d (WHR-91)

This is a schema specification, not a migration. Add immutable purchase fields `lookup_receipt_input JSONB?`, `lookup_receipt_status valid|fallback`, `lookup_receipt_claims JSONB?`, `capture_lower_bound TIMESTAMPTZ`, and `capture_policy_version TEXT`. Claims use the strict verified M1 shape, never raw client assertions; they are present iff status=valid. Fallback keeps L=S and no trusted claims. Original receipt input is protected evidence, excluded from general audit/logs. Implementation storage refinement (WO-core-7a): also persist immutable `lookup_receipt_input_json TEXT?`, the authoritative canonical JSON serialization for every new submission. PostgreSQL JSONB cannot represent valid JSON containing NUL or unpaired-surrogate escapes, including object keys; retain their exact canonical JSON in this text field and leave the optional JSONB projection SQL NULL. Such evidence still falls back without rejection; its original value remains in the semantic digest. Legacy rows remain unchanged. Distinguish canonical invalid JSON values from omission/null when hashing, following M1; never change legacy absent-receipt digests.

At first durable receipt, atomically freeze R, verification result and L=max(S,T) for valid evidence, else L=S. Verify context/account/station/card/customer/link consistency against authoritative rows. Retain original S and expiry, and enforce S<=L<=U=min(R,original expiry) for a usable interval; inconsistent original bounds remain zero-credit validation uncertainty. History/evaluation references include the signed link and original policy version. Key rotation, retry, reauthentication and recovery cannot change persisted evidence or lower bound. No backfill fabricates evidence for old purchases; they use L=S.

Card linkage must cover [L,U] and remain in force at R, including when R exceeds U. Link ending/replacement at R fails the in-force check; its existing hold/resolution path remains. All price, assignment/revocation and campaign policy evaluation uses [L,U]. Capture-review evaluation records must carry original S/R/U plus L and verified evidence references when P-23 applies; existing M3 permission, evidence and independent-hold rules are unchanged. Previously accepted revisions and frozen snapshots are never recomputed by this amendment.

Registration's durable mutation response snapshot includes the original nullable lookupReceipt. Replay preserves it without reissuance. The client stores the opaque noncredential evidence in the account-partitioned minimal cache and immutable OriginalSale, never SW cache. Keep the original evidence and verified claims with purchase history under existing protections; receipt signing keys remain server configuration, never database response fields.
