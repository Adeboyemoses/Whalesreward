# Report-only evidence inventory

WHR-210 / WO-core-16a implements the two inventory commands from [production §3](production.md#3-scheduled-jobs-and-prohibitions). It does not provision or schedule anything, approve deletion, perform backup/copy/restore, or prove deployed readiness. Earl performs staging and eventual production checks separately. WHR-56 keeps deletion, version expiry, lifecycle changes and multipart expiry disabled even when retention intent is configured.

## Commands and bounded execution

Run `pnpm job:orphans` hourly (UTC) and `pnpm job:reconcile-uploads` every 15 minutes from the reviewed application image. Each command executes a bounded slice: at most 20 logical pages of 25 entries, persisted as individual object/version checkpoints, ten minutes total, 10 seconds per provider LIST/GET including retries/body streaming, 8 MiB maximum per observed photo, 5 seconds per SQL statement, 3 seconds for lock waits and 5 seconds to acquire a connection. The maintenance pool has at most two connections. Provider reads use at most three SDK attempts with bounded SDK backoff inside each request's abort deadline. Each successful object checkpoint renews the fenced lease. Reads are additionally clipped to the remaining slice and lease budget, reserving time for the checkpoint; a healthy sequence of slower reads therefore makes durable progress without sharing one request deadline across the page. SIGTERM/SIGINT abort provider work and preserve the last committed checkpoint.

The default aged/stalled threshold is one hour. It is a report threshold, never proof of abandonment, upload expiry, cancellation or eligibility. The service rejects limits exceeding its fixed safety caps; deployments use the reviewed defaults.

A `continued` result means invoke the same command again promptly for the next slice. It keeps the same run ID and immutable page reports. A transport failure exits nonzero, retains its last cursor and permits retry after 15 seconds. `busy` means an unexpired competing lease or a not-yet-due scheduled run; it performs no inventory. `succeeded` means that the bounded pages exhausted this scan, including any reported discrepancies; it does not mean every asset is present or valid. A later scheduled scan has a new UUIDv7 run ID.

The image bundles both maintenance entrypoints and copies the shared launcher. The same `pnpm job:...` commands use TypeScript sources locally and the bundled ESM files in the non-root runtime image.

The run cutoff is its initial server start time. Newer records/objects belong to a subsequent scan. Provider inventory is an observation rather than a cross-system snapshot: concurrent uploads/reference changes can produce advisory findings, and every future repair or removal would require fresh domain authority through a separate approved path. Exact object version IDs are preserved in private mappings. ETags are never treated as SHA-256.

## Separate, restricted credentials

The commands require `MAINTENANCE_DATABASE_URL` and all of `MAINTENANCE_STORAGE_ENDPOINT`, `MAINTENANCE_STORAGE_REGION`, `MAINTENANCE_STORAGE_BUCKET`, `MAINTENANCE_STORAGE_ACCESS_KEY_ID`, `MAINTENANCE_STORAGE_SECRET_ACCESS_KEY`. Temporary read-only storage sessions may also use `MAINTENANCE_STORAGE_SESSION_TOKEN`. Do not reuse web write credentials. Configure values privately; never paste them into public commands, issues or logs.

For staging, use `WHR_ENV=staging` and the existing private `DATABASE_CA_CERT` binding. The maintenance pool validates the CA and supplies `rejectUnauthorized:true` to pg; URL TLS overrides are removed. It uses the dedicated maintenance database URL, not `DATABASE_URL`. The existing reviewed staging image entrypoint may remain in place. Local/test operation permits loopback database URLs only without staging TLS. Production execution deliberately refuses until the separately approved WHR-206 production TLS extension is implemented; this work does not bypass that release dependency.

Earl arranges a dedicated non-superuser runtime role with no CREATE on the application schema, no role/database creation or RLS bypass, and no business table INSERT/UPDATE/DELETE/TRUNCATE privileges, including inherited/PUBLIC and column-only INSERT/UPDATE grants. Grant USAGE on the application schema and SELECT on only these source tables: `photo_asset`, `purchase`, `purchase_hold`, `purchase_revision`, `correction_request`, `photo_receipt_observation`, `photo_receipt_fact`, `held_release_sheet`, `held_release_sheet_validation`, `held_release_proposal`, `card_export`, `report_export`. Grant SELECT/INSERT/UPDATE on `maintenance_run` and `maintenance_job`; SELECT/INSERT on `maintenance_object`, `maintenance_page` and `maintenance_finding`. Do not grant DELETE, TRUNCATE or schema ownership. Apply migrations with the separate owner/migration identity. A startup preflight refuses elevated roles or any domain write privilege; evidence queries additionally use read-only transactions. No command installs/grants privileges itself.

Storage policy grants only ListBucketVersions/ListBucket and GetObject/GetObjectVersion for the configured private primary bucket and evidence prefixes. Deny PutObject, DeleteObject, DeleteObjectVersion, AbortMultipartUpload and PutBucketLifecycleConfiguration. The adapter has no write, delete, multipart or lifecycle method. Verify actual provider permission denial with fictional data before scheduling. The integration tests exercise these denials against a scoped local MinIO STS session.

## Private reports and immutable history

`maintenance_finding` contains only closed discrepancy codes and UUID references: finding/run/object/asset/purchase IDs and bounded related source, hold, revision, correction-lease and proposal IDs. `maintenance_page` stores allowlisted aggregate counts. Neither stores names, phone numbers, card codes, URLs, photo bytes, raw exception/provider text or business record content. Generated IDs use the shared UUIDv7 generator.

`maintenance_object` is a private mapping from an inventory UUID to the provider key/version; run cursors also contain private provider pagination state. They must not be exported into logs, HTTP responses, telemetry or public evidence. No new admin HTTP endpoint is introduced. Protected operator inspection uses restricted database access under Earl's custody; the public health projection stays unchanged. Never publish `SELECT * FROM maintenance_run` or raw cursor/object mapping data.

Orphans report aged staged versions with their references, unreferenced final versions and aged delete markers. References include retained meter/sheet bytes, immutable receipt seals, rejected/superseded sheet sources/proposals, revisions, holds, correction leases and export artifacts, so export paths are not misclassified merely because they share `final/`. An object with no reference remains a candidate for human investigation only.

Reconciliation compares expected meter assets, every retained immutable receipt-observation seal (including interrupted or rejected finalizations without a complete-photo fact), sheet sources and display derivatives with actual server-read SHA-256/length observations. It reports missing objects/digests, digest/size mismatches, stalled uploads, missing complete-photo facts and mismatched receipt linkage. A display derivative has no persisted digest in the current domain schema; `missing_digest` records that fact without inventing one or rewriting its evidence. Every finding is advisory. First durable receipt time, holds, accepted revisions, credit, campaign membership and snapshots are unchanged.

## Leases, restart and WO-core-16c telemetry

Each `(job, scope=primary)` has one persistent lease. The scope covers the deployment's configured primary bucket; separate environments use separate databases/buckets. Each acquisition increments its fencing version. Page/report/cursor changes occur together under that fence, with an expiry check before and after page inserts. A stale worker cannot commit after takeover or after its transaction outlives its authority. Committed page reports and object mappings reject UPDATE, DELETE and TRUNCATE. Restart resumes the same run and next page; it never replaces a committed report. An incomplete run pins a non-secret digest of endpoint/region/bucket identity and refuses continuation against changed storage configuration.

Monitoring in WO-core-16c should read these protected fields, without dumping cursors or object mappings:

| Record            | Fields and meaning                                                                                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maintenance_run` | `id`, `job`, `started_at`/`created_at`, `completed_at`, `status`, `attempts`, `page_no`, `heartbeat_at`, `completion_deadline`, `watermark`, `error_code`, `outcome` allowlisted counts        |
| `maintenance_job` | `job`, `scope`, `run_id`, `fencing_version`, `lease_until`, `heartbeat_at`, `next_due_at`, `completion_deadline`, `last_outcome`, `error_code`, `last_succeeded_at`, `last_complete_watermark` |

`next_due_at` initializes at first invocation; before any invocation, monitoring must treat an absent required job row/heartbeat as missing, not healthy. Successful completion advances it by one hour/15 minutes. Continuations are due immediately; failed slices are due after 15 seconds. `completion_deadline` is the current slice's scheduled ten-minute deadline, not an evidence deadline. `last_complete_watermark` advances only after exhaustive success to the original run cutoff; partial/failed runs retain the prior value. `watermark` on a run remains null until complete. Sanitized failures are `storage_unavailable` or `database_unavailable`; a crash may leave `running` with an expired lease, which must alert independently of process exit. These fields do not represent backup coverage.

Logs contain only the job, run reference, status, allowlisted counts and a closed error code. Configure restricted log access and disable body/header/query capture separately. Earl's staging verification must include two concurrent invocations, interrupted slice/restart, provider read failure, permission denials, report redaction and receipt/revision byte-for-byte preservation using fictional fixtures. No deployed acceptance is claimed by the local test suite.
