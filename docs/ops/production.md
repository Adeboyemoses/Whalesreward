## 1. Backups and pilot recovery objectives

**Recommend managed recovery plus an encrypted, independently controlled database-and-photo copy.** Managed recovery is fast for database accidents; an independent copy also survives loss of the primary account or region. Bucket versioning helps undo overwrites but shares the primary account's failure boundary.

| Layer                   | Proposed implementation and reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Managed PostgreSQL 16   | Retain managed daily backups and the available point-in-time recovery (PITR) window. DigitalOcean documents seven days of backups and restore to a new cluster with latest-transaction or point-in-time selection. Earl must record the actual earliest/latest recoverable instants for the selected plan, test them and alert if the rolling window is shorter than seven days. Do not promise a finer end-to-end RPO from PITR alone.                                                                                                                                                                 |

**Recommend pilot RPO ≤24 hours and RTO ≤one business day for a complete database-plus-photo recovery.** RPO measures the incident instant minus the newest verified recoverable snapshot cutoff; RTO measures declaration to validated service restoration. Define the business-day working hours in the private operating agreement before launch; until then the RTO is an unaccepted target, not an SLA. PITR may improve database recovery but must not restore credit whose evidence is missing. Report actual drill times and coverage. Phone-only unsynced records are outside server backups; preserve original phones and account queues, and train staff to reconnect within the approved window. Do not represent local “Saved on phone” as backed up or credited.

### Protected backup manifest

WHR-29 must produce an immutable, versioned manifest in the independent destination for each recovery set. It contains:

- Run ID, UTC start/end, database snapshot cutoff/consistency marker, source environment, schema/migration version, deployed commit, dump size and SHA-256, encryption format and a non-secret key reference.
- Protected inventory of every referenced evidence asset at that snapshot: database asset/source IDs, object keys and version IDs where available, byte size, server digest, copied destination and independently checked SHA-256. Keep meter/sheet kind, pending/final state and immutable receipt/provenance linkage. Preserve other received objects in a separately enumerated inventory; extra copied objects do not grant credit.
- Policy approval/configuration histories, meter profile/verifications, revisions, idempotency receipts, audit and giveaway snapshots in the database export. Inventory required retained admin/lookup receipt key **identifiers**, never key bytes; actual keys use the separate secure recovery procedure.
- Enumerated missing/mismatched objects and copy errors, object/byte totals, coverage cutoff, restore tool version and verification status. Status is `complete` only after the consistent snapshot's referenced bytes are copied and hashes checked. Interrupted/partial runs stay incomplete and never advance last-success or RPO coverage. A successful process exit without a complete manifest is not a backup.

Use a consistent database snapshot, enumerate its references, copy them, then recheck closure before marking the pair complete. Concurrent new sales belong to the next cutoff; do not advance the cutoff to job end. Do not infer a content digest from an S3 ETag. Newer PITR recovery is permissible only after proving evidence closure at that exact target; otherwise select the latest complete pair and report the lost interval. Manifests/dumps contain personal/domain data: private encrypted storage and restricted operator access only. Public records contain counts, run references and pass/fail, never inventories or raw manifests.

## 2. Combined restore drill

**Recommend before the first pilot, monthly during it, and after material schema, storage, encryption, activation or backup-tool changes.** A database-only restore can succeed while every photo link is broken. Alternate managed PITR and independent-export exercises; the pre-pilot drill must include the independent path. Earl runs this checklist; Cloudrock prepares the tools and reviews redacted results under the later WO.

- [ ] Obtain Earl's explicit authorization for a disposable recovery environment and identify its account, isolated database, private bucket and intended recovery cutoff privately. Record a non-secret drill ID, source commit and start time. Never target the production database for overwrite.
- [ ] Choose a complete paired manifest within the proposed RPO. Verify dump integrity, decryption access, schema/tool compatibility and independent account access. Separately demonstrate the managed PITR window and a new-cluster restore; do not destroy the source cluster or rely on deleting data to free quota.
- [ ] Isolate restored data before opening the app: no public ingress, no real email/SMS, no running maintenance/mail workers, no production write credentials and no scheduled jobs. Any restored live data remains production-sensitive in an Earl-only restricted enclave; never give it to agents, ordinary staging, CI or training. Agent/tool checks use fictional fixtures separately.
- [ ] Restore database and all referenced meter/sheet evidence into the disposable target, preserving bytes, versions, receipt times, original IDs and lineage. Use the manifest mapping rather than rewriting accepted records to hide missing objects. Keep outbound traffic blocked and copying read-only with respect to the source.
- [ ] Verify every referenced object's bytes/size/digest and private access, plus exact protected counts and exact-kobo totals at the snapshot. Compare originals, pending uploads/holds/corrections, operation receipts, policy histories, audit and frozen giveaway snapshots. Missing evidence is a failed drill, never automatic cancellation, acceptance or regeneration.
- [ ] Handle the copied database identity deliberately: the dump may carry `whr.environment=production`. Never activate a non-production target by relabelling a non-null copied comment. Follow the existing operator stop-on-mismatch rule. For the drill use isolated read-only validation; any future clean non-production activation requires separately reviewed import/bootstrap tooling that excludes the source identity and production-scoped activation state, creates a fresh target with a null comment and uses the correct target label. Do not pretend production approvals authorize a test environment.
- [ ] In a separate fictional-data recovery test at the same code/schema version, verify identical operation retries do not duplicate credit, different payloads conflict, unauthorized photos stay denied, pending assets remain pending and snapshots stay immutable. Real-data validation itself makes no sales or policy mutations.
- [ ] Record recovery cutoff, recovered byte counts, exact protected comparison results, elapsed time, measured RPO/RTO, missing items and operator sign-off privately. Publish only drill ID, date, commit, counts, durations and pass/fail. Test alert delivery for a deliberately incomplete synthetic recovery set.
- [ ] Earl closes access after verification. Do not delete copied client data under this WO; obtain a separate authorized handling decision consistent with WHR-56. Prefer fictional rehearsals for routine tooling development to avoid accumulating real-data copies.

**Pass criteria:** zero missing/digest-mismatched referenced assets; exact financial/history/snapshot comparisons; working independent decryption/access; preserved identity and isolation; synthetic retry/privacy checks pass; measured complete-pair RPO ≤24 hours and RTO within the agreed business day; alert test received. Any miss blocks pilot readiness and produces a tracked fix and repeat drill. A dry run or database-only success cannot satisfy this gate.

Each implementation needs a durable `MaintenanceRun` record (or reviewed equivalent), per-job/scope lease with fencing, bounded pages/DB/provider deadlines, resume cursor and idempotent destination naming. Overlapping/restarted jobs cannot erase or replace committed work. Record run ID/type, UTC start/end, outcome, counts, watermark and sanitized error code, never object URLs or record contents. Proposed timeout: 10 minutes per inventory/reconciliation/copy slice, with continuation; export deadline set from the measured drill and alerted if missed. Retry transport-safe reads/copies with bounded backoff; never replay uncertain business mutations. Leases and schedules never implement the midnight cutoff, extend offline capture/upload deadlines, or change original server receipt time.

Test concurrent runs, lease expiry/fencing, pagination, interruption after copy before manifest commit, partial object failure, dump failure, clock boundaries, no deletion permissions and zero business mutations. Existing in-web admin-mail polling remains distinct (T-16/T-17); its production policy/delivery gate is still closed until approved and implemented. Do not duplicate it with a cron sender.

## 6. Promotion, migrations and rollback

**Recommend explicit releases from reviewed staging with additive migrations and a preserved known-good image/configuration.** This permits application rollback without erasing accepted sales.

1. WHR-31 prepares `.do/app.production.yaml` in a reviewed core PR, alongside a production configuration inventory and safe re-apply procedure. It must declare **all** non-secret structural settings, component scopes, runtime binding names, job schedules, `main` source, manual production deployment, migrations, DB attachment/owning role, health check and gallery/seed omissions. Private identifiers/values use named placeholders and a private mapping; retain no real client IDs/domain or encrypted secret blobs. This spec WO creates no app spec.
2. Before each change Earl compares live console settings privately with the committed inventory. A raw apply of a placeholder spec is forbidden: empty SECRET entries or absent env entries can erase working settings. Reconcile the proposed structural delta in the console, preserving every secret/private binding, policy apply result, receipt-key history and job override. The later implementation must provide a dry comparison that reports names/scopes only, refuses missing/empty required values, and demonstrates a second apply preserves settings. Never retrieve populated specs into agent tools or commit them. Keep non-secret changes in the repo so future reconciliations do not undo them.
3. EM opens `staging` → `main` promotion listing included PRs, migration order, environment names, approval/activation prerequisites, smoke and rollback limits. Earl normally merges it himself. EM may merge only with Earl's **current-session go naming that PR**, using `WHR_MAIN_GO=<today>` and exact-head matching, with his words recorded in the authorized release record. Do not automatically deploy on a push to main: production deployment needs a separate Earl go and Earl-run action. This WO opens only a spec PR to staging.
4. Before deployment Earl verifies a fresh complete backup, previous deploy/image and private configuration recovery access. Review each migration for old/new app compatibility, locks and required headroom; rehearse on disposable fictional data. Use PRE_DEPLOY `pnpm db:migrate:deploy` with the certificate-verifying entrypoint and dedicated owning role. Never `migrate reset`, reseed or modify accepted rows to force success. Migration failure stops the release; inspect sanitized output and migration state before retrying uncertain completion.
5. Deploy the exact reviewed artifact. Run protected/public health, authority/privacy, approved delivery/storage, policy, receipt replay and focused sales/Settings/finalization smoke; verify version matches. Keep new use paused until release gates pass. Do not manufacture live sales or remove them afterward as a test; the later runbook must define client-authorized verification without contaminating rankings.
6.
