### 4.1. Trusted client-IP header — Earl only

Unset, empty or `noop` means no loop, no mail database pool and no timer, even though Mailpit remains the local adapter default. Builds never start the loop. Existing production provider/auth-policy gates remain closed; this structure does not authorize production activation.

The loop starts one batch immediately, then waits five seconds between batches, including an empty outbox or a failed database attempt. Each batch stops after ten steps or after its 20-second claim budget expires, checked before starting each next step. Each step claims at most one pending message and cleans up at most 25 expired sending leases. It never overlaps itself. Multiple web instances use the existing transactional security lock, message status, lease nonce and fencing checks, so only one instance sends each message. No global cron lease is needed. A crashed/expired send is failed and its link revoked, never blindly replayed; the user requests a fresh link.

A dedicated two-connection mail pool has 5-second connect/statement timeouts, 6-second query timeout and 10-second idle/idle-transaction limits. It does not consume the health or request pools. Provider calls retain their 10-second deadline. Telemetry reports step, delivered, failed and error counts only; no addresses, tokens, links, bodies or provider error objects. Empty batches are quiet.

SIGTERM/SIGINT stops new claims, waits for the current step and closes the mail pool before passing the signal to Next's original HTTP cleanup. A 30-second drain deadline forces a nonzero exit if draining stalls; any unfinished lease is recovered conservatively by another instance after its existing two-minute expiry. The container starts Node directly through the existing strict-TLS entrypoint, without a package-manager process between the entrypoint and Next. Repeated signals and instrumentation reloads cannot create another loop or duplicate cleanup. Recheck this pinned Next lifecycle integration when upgrading Next.

The 60-second expectation applies to a healthy database/provider and a small queue; it is not a promise for arbitrary backlog, persistent failures or the recipient's external mail server. Larger backlogs are drained in bounded batches. Earl confirms actual inbox delivery after deploying; this work order performs no provider or cloud action.


## Safe mail diagnostics (WO-core-5c)

Each failed attempt emits one `warn` event, `email.send_failed`, containing only `adapter`, `reason` and applicable `status`, `error_code` or `setting` fields. No raw response, exception, provider message/request ID, address, sender, subject, body, token or link is logged. Validated provider error codes match the entire `[A-Z]{2,5}_[0-9]{1,5}` string; unsafe codes are omitted. These codes are diagnostic only and never authorize a retry.

| Reason | Meaning and safe next check |
|---|---|
| `config_invalid` | Validation or the recipient allowlist rejected the attempt; `setting` names the failed setting only. Privately check that setting. This replaces the old `email.recipient_refused` event for allowlist refusals, so there is still only one warning. |
| `network` | Transport failed; no raw exception is retained. Check connectivity without replaying the link. |
| `timeout` | The bounded request/response deadline expired. The uncertain link is revoked, never reconstructed. |
| `http_status` | HTTP status was not 200 or 201. Safe `status` is retained even for empty, malformed or oversized bodies; a validated provider `error_code` is included when available. |
| `provider_error` | HTTP 200/201 carried a validated provider error code rather than an accepted result. |
| `response_invalid` | HTTP 200/201 lacked a valid acceptance body or exceeded the response bound. |

One startup state event is emitted per Node process, including repeated instrumentation registration: `email.loop_started`, or `email.loop_disabled` with `reason=build_phase`, `production`, `provider_unset` or `noop` (in that precedence). Disabled startup creates no mail pool or timer. Production deliberately remains disabled pending WHR-42, as preserved by T-17 and T-16; this change does not activate production delivery. Invalid configuration still terminates startup, with `email.config_invalid` containing a safe reason and setting name only. Any non-email startup failure uses the fixed `email.startup_failed` event without its exception.
