# Registration, customers and cards smoke — WO-app-6 (WHR-13)

Written before implementation. Earl's staging smoke for WO-app-5 and WO-app-6 will be batched into one workbook later. This runbook supplies the WO-app-6 scenarios; it does not accept WHR-11 or WHR-77. Agents run only local fictional fixtures. Record deployed version, browser and configured test phone/print policies. No cloud/provider change, live staging Owner control or manual staging-data operation is authorized by this runbook.

1. As an authorized test admin, open Loyalty cards. Confirm the persistent portal shell, server counts, Generated/Printed/Active meanings, pagination and empty/error states. Read-only card access offers no generation, print, activation or export authority. Customer names on linked cards are unavailable without customer-view permission; linked state remains visible.
2. Generate a uniquely named fictional batch. Enter a whole count in the supported 1–1000 range. Review the name/count and Generated consequence, then Keep editing or Cancel: no write. Explicit Generate cards creates one batch with reserved seven-character codes. A double click or deliberate same-key retry must not create a second batch or different codes. Creation has the server's fixed audit reason, with no invented required reason field.
3. Inspect batch inventory and complete history across pages. Generated cards have zero available to assign. Mark as printed requires the reason/printing reference and explicit reviewed confirmation; Cancel changes nothing. The result is Printed, still unavailable for assignment. A separate reviewed activation with reason produces Active. There is no shortcut, reverse transition, unretire or unlink action. The server supplies actor, versions and time.
4. Prepare PDF print sheet and Excel register exports. Pending, ready, failed and expired results have plain notices and deliberate retry/new-export choices. Preview/download never changes lifecycle status or regenerates codes. The PDF contains only snapshot-unassigned, non-retired cards with real matching QRs; Excel includes all snapshot cards/codes/states/eligibility and no customer personal data. Snapshot metadata is distinguished from current inventory.
5. Preview the protected prepared PDF and download both formats through the authorized same-origin route. Verify codes/QR equality and PDF filtering, text codes in Excel, and unchanged batch codes/status after repeated export. An empty printable batch refuses PDF safely. Missing print-layout policy shows print unavailable while Excel works; no prototype dimensions are presented as approved. Physical printer/stock acceptance remains separate.
6. On an attendant phone at 390 and 360 px, open Register from the bottom navigation and from A24's Register this customer. Show Internet required, name, phone, fixed six-option category, and scan-or-type card entry. Use an unused Active card. Register and link card succeeds only online; offline submission says Connect to register and creates no offline draft/outbox entry.
7. Complete a fictional registration. The server receipt supplies customer ID, name, category, linked card, phone, actor and registration time. Show Card linked and the next-sale consequence. Register another customer clears the form and receipt. Record a sale first performs current card lookup; registration receipt/replay alone cannot authorize capture or establish current linkage. Scan and typed code resolve identically.
8. Try the same normalized phone with another unused card. A25 states that the phone already has an account; the attempted card remains unassigned. Existing customer name/code/card come only from the separate exact-phone lookup, never from an invented duplicate-error payload. Registration stays disabled for that phone. Open the existing customer only if a fresh card lookup succeeds; no card or an unusable card gives manager-help guidance without replacement or phone-change controls.
9. In local fixtures, hold/drop a registration response after commit, then deliberately retry the frozen operation/body as the same account. Receive the original historical receipt without duplicate customer/link. Editing material inputs needs a new operation after certainty; changing accounts, signing out or expiry clears visible PII and cannot replay another account's receipt. Check card conflicts, invalid input, unavailable phone policy and network loss without false success. No phones/searches/drafts/receipts enter Dexie, SW caches, URLs or logs.
10. In admin Customers, search by supported name/full phone/visible suffix/card/customer code and filter the fixed category. Empty results are explicit; later cursor pages use the same filter. Return from profile preserves the in-memory search/category. Phones remain server-masked, including profile. Registration provenance is historical; legacy unknown actor/station stays unknown.
11. Inspect profile totals and customer-scoped purchases with customers AND sales permission. Exact recorded spend/completed counts stay separate from upload-pending values; held/cancelled purchases remain visible without being credited. Duplicate flags alone do not remove valid spend. Product quantities preserve litres versus kilograms. Customer-only access sees no purchase rows or photos. No M3 phone change, replacement, recovery or sale-decision controls are introduced.
12. Locally revoke permissions during read, review, export preparation/download and late responses; switch routes/accounts while requests are pending. No old response may restore protected content or start a download. Stale versions require reread and fresh review; uncertain same-key retries retain the original body. Preserve WO-app-4a tab/route behavior and WO-app-5 first-password, assignment and queue isolation.
13. Check keyboard labels/focus/error descriptions, phone controls at least 48 px, one-line phone wordmark/footer at 390/360, admin at 1440 and phone width, contained table scrolling and long names/reasons. Compare all scoped boards with the independent parity report, recording contract-required differences.

Automated local fixtures cover races and negative cases; Earl need not change real permissions or perform destructive checks on staging. READY requires integrated gates, independent code/security/integrity verdicts, board-fidelity evidence and green staging merges. Stop at READY, leaving WHR-11 and WHR-77 In Review for the later consolidated workbook.
